# 설정 내보내기 UI 정지·복구 백업의 비밀값 포함

> 2026-10-21 후속 독립 QA: `75e1f8a`에서 UI 압축 정지와 `.bak` 비밀값 재유입이 재현 조건상 해결됐다. 실제 UI 압축 중 heartbeat·원문 비밀값 재현·복원 결과와 Windows 미검증 범위는 [후속 독립 QA](설정백업_네트워크수정_후속독립QA_20261021.md)를 따른다. 아래는 수정 전 실패 기록이다. 과거 ZIP이 자동으로 안전해지는 것은 아니다.

- 날짜: 2026-10-21 (한국 시간)
- 조사 소스: `d269681b3e654b6096944cb6a459f10d557a8e6d`. 현재 파일과 실행 경로만 읽고 커밋 이력은 조회하지 않았다.
- 조사 도중 `115892a8c26d00d5e9fdb02ce237d1a1dc903183`이 푸시됐다. 관련 `config.py`, `ui/settings_tab.py`, `settings_sync.py`의 blob이 조사 소스와 동일한 것을 확인해 최신 푸시에도 본 결함이 남아 있음을 확인했다. 그 푸시의 다른 제품 변경을 이번에 QA 통과로 보고하는 것은 아니다.
- 사용자 제보: v0.10.0의 설정 내보내기 후 앱이 잠깐 Windows `응답 없음`으로 표시됨. 처음에는 디스코드 내보내기를 언급했고, 이어 “그냥 내보내기 하니까 잠깐 앱이 멈춘것처럼”이라고 설명했다. 영구 deadlock이나 크래시로 단정하지 않는다. QA에서는 두 버튼 모두를 별도로 재현했다.
- 결론: 공통 ZIP 생성이 UI 스레드를 차단하는 결함과, 자동 복구 설정 백업의 비밀값이 ZIP에 포함되는 결함을 확인했다. **제품·기존 테스트·공개 노트·워크플로는 QA에서 수정하지 않았다.**

## 1. Confirmed Bug — ZIP 생성·저장이 UI 스레드를 차단

- 심각도: **P2**, 일반 파일/디스코드 내보내기 공통.
- 조건: 사용자 데이터 폴더에 아이콘 외 수집 이미지·자동찾기 진단 등 파일이 누적된 상태에서 설정 내보내기를 실행한다. 일반적 데이터가 늘어나는 사용 경로이며 사용자 과실이 아니다.
- 영향: 압축이 끝날 때까지 창 갱신·입력·UI 타이머·UI에서 실행되는 판독/알림 처리가 지연된다. 실제 Windows에서는 제보처럼 일시적인 `응답 없음`이 보일 수 있다. 오래 걸리면 중단·진행 상태 확인도 어렵다.
- 원인: `ui/settings_tab.py:426`의 `_on_export_discord()`는 `config.export_bundle_bytes()`를 동기 호출한 **뒤에** 버튼 비활성화/상태 변경과 `_ConfigExportThread` 시작을 한다. 현재 워커가 옮긴 것은 네트워크 전송뿐이며 ZIP 준비가 아니다. 441~451행의 `_on_export_config()`도 `config.export_bundle()`을 동기 호출해 압축과 파일 쓰기를 UI에서 실행한다.
- 공통 원인 코드: `config.py:127`의 `_iter_user_files()`는 사용자 폴더 전체를 정렬·재귀 열거한다. 139~154행의 `export_bundle_bytes()`는 전부 메모리 ZIP으로 DEFLATE 압축하고 157~161행의 파일 내보내기는 그 바이트를 다시 파일에 쓴다. 설정·자산 외 폴더도 모두 들어가며 항목/원본/압축 크기나 시간 상한이 없다.
- 실제 누적 경로: `autofind_diagnostics.py:136`은 사용자 데이터 아래 `autofind_diagnostics`, `ui/halo_capture_section.py:53`은 `halo_timer_shots`를 사용한다. 따라서 설정 백업이 진단 원본·수집 자료까지 압축할 수 있다. 기록 1단계가 앞으로 추가될 때도 사용자 폴더 전체를 묶는 패턴을 그대로 확대하면 안 된다.
- 독립 재현: 임시 사용자 폴더에 합성 비압축성 24MiB 파일을 넣고 **실제 ZIP 함수와 실제 두 슬롯**을 실행했다. 파일 선택 창/결과 알림과 디스코드 전송만 대체했다. 압축 진입 스레드와 예약한 Qt heartbeat를 측정했다.
- 검증 결과: 파일 내보내기 **0.735초**, 디스코드 내보내기 **0.961초** 동안 압축은 실제 QApplication UI 스레드에서 실행됐고, 예약한 heartbeat가 압축 전/후 모두 0회였다. 슬롯이 반환한 뒤 이벤트를 처리하자 실행됐다. 주입한 sleep이나 실제 외부 통신을 사용하지 않았다.
- 한계: Linux Qt 오프스크린 실행이다. 24MiB의 관측 시간을 Windows의 정확한 정지 시간이나 `응답 없음` 판정 시간으로 치환하지 않는다. 사용자의 실제 파일 규모·지연 시간은 확인하지 않았으며 무한 대기나 네트워크 지연으로 단정하지 않는다. 화면에서 버튼 문구가 원래 상태인 점은 ZIP 준비 이전/도중 경로와 부합하지만 최종 call stack 증거는 아니다.

## 2. Confirmed Bug — 자동 복구 설정 백업에서 비밀값이 ZIP에 재유입

- 심각도: **P1**, 비밀값이 저장돼 있고 자동 백업이 생성된 경우 일반 파일/디스코드 내보내기에 영향.
- 조건: 배포판은 설정 파일과 사용자 자산 폴더가 같은 `%LOCALAPPDATA%/StarlineMabinogiAddon`이다. 설정이 두 번 이상 정상 저장돼 `config.local.json.bak`이 존재하고 이전 설정에 API 키·문의 웹훅 값이 남아 있다.
- 영향: `config.json`은 비밀값이 제거되지만 `userdata/config.local.json.bak`은 원문 그대로 ZIP에 들어간다. ZIP을 다른 사람/PC에 전달하거나 디스코드 릴레이로 보내면 제외돼야 할 값도 함께 전달될 수 있다. 실제 사용자 ZIP에 해당 비밀값이 있었거나 제삼자가 취득했다는 뜻은 아니다.
- 원인: `config.py:69`의 `_write_local_config()`는 기존 정상 설정을 `.bak`으로 보관한다. 96~99행은 `_SECRET_KEYS`를 sanitized `config.json`에서 제거한다. 하지만 127~136행의 `_iter_user_files()`는 최상위에서 **정확히 `config.local.json`인 파일만 제외**하고 `.bak`·임시 설정 사본 등에는 같은 보호를 적용하지 않는다.
- 독립 재현: 배포판과 같은 디렉터리 배치의 임시 폴더에서 실제 `_write_local_config()`를 두 번 호출해 자동 `.bak`을 생성했다. 가짜 API 키/웹훅만 사용한 뒤 실제 `export_bundle_bytes()`의 모든 멤버를 검사했다.
- 검증 결과: sanitized `config.json`에서는 키가 제외됐지만 `userdata/config.local.json.bak`에서 가짜 비밀값이 그대로 발견됐다. 실제 키·사용자 설정·외부 전송은 사용하지 않았다.
- 대응: 현재 내보낸 설정 ZIP을 공개 저장소나 공개 채팅에 공유하지 않는다. 실제 유출 확인 없이 사용자에게 모든 키 폐기를 요구하지 않으며, 필요할 경우 사용자 PC 안에서 비밀값을 노출하지 않는 방식으로 포함 여부를 확인한다.

## 4. 개발 전달·회귀 기준

1. **동결과 비밀값 문제를 함께 수정한다.** 압축·사용자 자산 열거·ZIP 파일 쓰기·전송을 UI 밖의 소유권이 명확한 작업 경로로 옮긴다. 작은 설정/계정 snapshot을 필요한 시점에 확보하고 실제 QWidget/메시지 박스는 UI 스레드에서만 다룬다. 작업 스레드에서 QApplication.processEvents를 호출하는 방식으로 덮지 않는다.
2. 작업 시작 전 버튼/상태를 갱신하고 중복 실행을 막는다. ZIP 준비 중, 전송 중, 완료/실패를 구분하고 모든 오류에서 상태를 복구한다. 계정 변경·가져오기/초기화·종료가 겹쳐도 이전 작업이 새 설정을 덮거나 파괴된 UI에 결과를 쓰지 않아야 한다. 앱 종료 시 워커·QThread를 정상 정리한다.
3. 설정 백업의 파일 범위를 **복원에 필요한 카탈로그·사용자 아이콘/자산 중심으로 명시**한다. 진단 캡처·로그·수집 세션·프레임 기록·이전 ZIP·복구/임시 설정·비밀 원문은 포함하지 않는다. 파일 확장자 `.bak` 하나만 차단하는 것으로 범위 문제 전체를 끝내지 않는다. symlink 등 사용자 폴더 밖 파일도 따라가지 않는다.
4. sanitized 설정을 유일한 설정 원문으로 사용한다. 배포판과 같은 설정/자산 동일 폴더, 자동 `.bak`, 임시 파일·다른 사본 및 하위 폴더를 검증한다. 기존 설정·카탈로그·사용자 아이콘의 복원 기능은 유지하고, 이전 버전 ZIP 가져오기의 호환성과 기존 로컬 복구 `.bak` 자체를 파괴하지 않는다.
5. 열거 개수·원본/ZIP 크기·작업 큐/메모리·시간·전송 가능 크기에 상한을 두고 실패/취소/저장 중 종료를 안전하게 처리한다. 전송 제한을 넘는 자료를 모두 압축한 뒤에야 실패하게 하지 않는다. 대용량 바이트 복사/메모리 중첩을 피하고 임시 ZIP을 쓰는 경우 실패 시 정리·기존 파일 보존을 검증한다. 실제 Discord 제한을 무시한 임의 상수를 영구 정답으로 쓰지 않는다.
6. 원본 수집 이미지가 많거나 느린 디스크·디스크 부족·읽기 권한 실패·중간 삭제가 있어도 UI heartbeat와 다른 전투 기능이 계속 동작하는지 검사한다. `.bak`에서 실제 비밀이 빠지고 필요한 사용자 자산은 보존되는지 로컬/DM **공통 경로**에서 검사한다.
7. 네트워크 전송 성공은 릴레이 접수와 실제 DM 전달을 구분한다. 이번 동결 제보를 서버나 사용자 권한 탓으로 돌리거나 성공 문구만 바꿔 완료하지 않는다. 후속 독립 QA와 Windows 실사용을 통과하기 전에는 수정을 완료했다고 안내하지 않는다.

이 자료를 개발 세션에서 수정의 입력으로 사용한다. 사용자가 직접 원인 분석·레지스트리 수정·앱 재시작 반복을 할 필요는 없다. 응답 없음이 잠깐 나타난 뒤 복귀했다면 강제 종료가 필수인 상황으로 안내하지 않는다.
