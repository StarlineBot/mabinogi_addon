# 원버튼 검증·배포 개발 전달

- 날짜: 2026-10-20 (Asia/Seoul).
- 검토 기준: `a2c521a066d1918fa0f6b3c2892aedddcfe89b27`의 workflow와 후보/게시 코드.
- 결론: **코드 구조상 구현 가능하다.** 배포 조건 대부분은 이미 기계적으로 검증한다.
  다만 현행 실행 완료/태그 전제와 승인 전달을 분리해야 하며 실제 Actions 태그 생성 권한은 미검증이다.
- 상태: 사용자 요청의 재검토·개발 전달안이다. 이번 QA에서는 workflow·제품·태그를 수정하거나
  Release를 게시하지 않았다. 새 원버튼 자동화를 실행해 성공했다고 보고하지 않는다.
- 이 문서는 앞선 수동 절차 개선안의 후속 구체안이다. 실제 개발 시 관련 지침을 함께 갱신한다.

## 1. 사용자가 원하는 흐름

소스에 대한 개발·독립 QA는 먼저 완료한다. 그 뒤 사용자는 버전과 **검증 후 배포**를 선택해
한 번 실행한다.

**Windows 검증/빌드 → 배포 조건 자동 확인 → Actions의 태그 생성 → 동일 exe 게시**

중간에 Codex에게 성공 여부를 다시 묻거나 run ID/attempt/SHA를 받아 옮기거나,
로컬에서 태그를 푸시하거나 별도 승격 버튼을 누르지 않는다. 이 한 번의 명시적 실행을
해당 소스/버전이 검증에 성공했을 때의 조건부 게시 승인으로 취급한다.

- **검증만** 모드도 남기고 기본값으로 둔다. 검증만/일반 푸시는 게시 승인이 아니다.
- **검증된 후보 배포** 모드에서는 유효한 기존 후보를 확인하고 태그 생성/게시만 한다.
  테스트·빌드를 다시 하지 않으며, 후보가 없거나 만료됐으면 비용 드는 새 검증으로 조용히 전환하지 않는다.
- 기존 후보는 버전·승인한 소스/fingerprint·최신 attempt까지 정확히 맞아야 한다.
  후보가 여러 개여도 임의의 '최신 성공'으로 대체하지 않는다. 모호하면 실행 전에 후보를 식별하게 한다.
- 검증이 시작된 뒤 다른 소스가 푸시됐다고 승인 대상을 자동으로 바꾸지 않는다.
- Codex의 소스 독립 QA나 실게임 판단 전체를 자동화하는 것이 아니라, 현재 Codex가 읽어 확인하던
  **실행 결과/출처/버전/파일/수명 조건**을 코드에 맡긴다.

## 2. 현재 코드에서 확인한 재사용 지점

| 위치 | 이미 수행하는 검증/역할 |
| --- | --- |
| `scripts/release_candidate.py:148` check_context | 정확한 저장소·workflow·main/dispatch·SHA·attempt·완료/성공·필수 단계·artifact 출처/크기/만료 |
| `scripts/release_candidate.py:168` gate | GitHub API 조회, 후보 식별, 현재 중요 입력 fingerprint, 태그 SHA 일치 |
| `scripts/release_candidate.py:188` verify_bundle | manifest 출처/버전/수명, 파일 목록/해시/크기, JUnit 결과, 업데이트 메타데이터 |
| `scripts/release_candidate.py:98` seal | Windows exe 리소스 버전, JUnit·노트, 후보 생성과 SHA256 기록 |
| `scripts/release_delivery.py:36` promote | 게시 직전 재검사, 양 저장소 초안 업로드/재다운로드 해시, 동일 파일 게시·업데이트 반영 |

따라서 Codex가 run ID를 수동 전달해야만 가능한 고유한 검사 단계는 없다.
다만 이 함수들을 호출할 신뢰할 수 있는 자동 진입점과 승인 정보가 필요하다.

## 3. 단순 job 연결로 끝낼 수 없는 이유

1. `check_context:154`는 validation run 전체가 completed/success일 것을 요구한다.
   같은 run의 마지막 promote job이 자기 run을 gate하면 아직 in_progress이므로 실패한다.
   기존 테스트도 이 상태를 거부한다. 이를 회피하려고 실행 완료 검사를 삭제하지 않는다.
2. `gate:180`는 태그가 이미 있어야 한다. 현재는 사용자가 만든 태그를 전제로 한다.
   태그를 자동 생성하려면 '태그 생성 전 후보 검증'과 '태그 생성 후 최종 게시 검증'을 분리해야 한다.
3. 두 workflow가 같은 `verified-windows-candidate` concurrency 그룹을 사용한다.
   상위 run이 락을 잡고 같은 락의 하위 run 완료를 기다리는 구성은 서로 막힐 수 있다.
4. workflow와 scripts도 fingerprint에 포함된다. 자동화 코드를 바꾼 뒤 이전 후보를
   '기능은 같으니' 그대로 통과시키면 안 된다. 첫 자동화 배포에는 새 입력으로 검증한 후보가 필요하다.

## 4. 권장 구현: 두 workflow를 완료 이벤트로 자동 연결

화면에서 실행은 한 번이지만 내부 workflow는 검증/게시를 분리한다.

1. `windows.yml`의 수동 실행에 `version`과 모드(검증만/검증 후 배포)를 둔다.
   시작 SHA·버전·승인 모드를 고정하고 기존 전체 회귀·네이티브·exe·seal/보관을 수행한다.
2. 검증 workflow가 **완전히 끝난 뒤** `workflow_run: completed`로 후행 게시 workflow를 깨운다.
   실패/취소인 경우 게시하지 않는다. 검증만 성공은 후보 보관으로 끝낸다.
3. 후행 workflow는 triggering run의 ID/head_sha를 사용한다.
   attempt는 GitHub API와 해당 artifact/manifest에서 대조한다. 자기 `github.sha`/`run_attempt`나
   기본값 1을 원래 검증 실행의 값으로 사용하지 않는다.
4. API로 허용된 validation workflow ID/path·같은 저장소·main·원래 event=workflow_dispatch·
   정확한 run/attempt·필수 단계 성공을 확인한 뒤 해당 후보만 내려받는다.
5. 후보/manifest와 함께 저장한 **명시적 게시 승인**을 검증한다.
   원래 workflow 입력은 후행 workflow의 inputs로 자동 전달되지 않는다.
   신뢰한 main의 검증 단계가 승인 모드와 소스/버전/run/attempt를 후보에 묶어 기록하고,
   후행에서 출처·내용을 대조한다. 파일명이나 run title만 보고 승인됐다고 추정하지 않는다.
6. 기존 gate를 공통 출처/입력 검증과 태그 필수 최종 검증으로 최소 분리한다.
   태그 전 단계에서도 파일 해시·JUnit·버전·수명·출처·현재 중요 입력을 모두 확인한다.
7. 게시 승인과 후보 검증 성공 후에만 Actions가 **검증 SHA에** 태그를 생성한다.
   원격 태그 SHA를 다시 확인하고 기존의 태그 필수 gate/check/delivery로 같은 exe를 게시한다.
   기존 태그/Release가 있으면 force·삭제·덮어쓰지 않고 충돌/부분 실패로 중단한다.
8. 게시 직전에도 입력·후보 수명·업로드 바이트를 재검증한다.
   외부 두 저장소의 게시가 원자적이라고 가정하지 않는다. 부분 게시를 자동 덮어쓰기하지 않는다.

`workflow_run` 진입점은 실행 권한이 커질 수 있으므로 특히 다음을 지킨다.

- fork/PR/다른 workflow·브랜치 산출물을 받아 privileged 게시를 하지 않는다.
- 신뢰하지 않은 artifact의 Python/shell 코드를 실행하지 않는다. 신뢰한 기본 브랜치의 검증 코드를 사용한다.
- 후행 workflow가 실행되는 기본 브랜치와 검증 SHA가 다를 수 있다. 중요 입력 변경은 계속 차단하고,
  일반 Markdown 차이만 허용한다.
- 중복 완료 이벤트·재실행·동시 실행에서 다른 attempt/후보를 대신 게시하거나 이중 게시하지 않는다.
  게시 대상별 직렬화와 기존 후보 정리도 함께 설계한다.
- 자동화 후에도 성공 조건을 생략하거나 전체 run 성공 이전에 게시하지 않는다.

## 5. 태그 권한: 도구 제한과 저장소 정책을 구분

- Codex connector에 태그 생성 기능이 없는 것은 GitHub Actions의 태그 생성 권한과 별개다.
  Actions가 Git/REST API로 생성하므로 사용자 PC의 gh 설치도 필요 없다.
- 현재 게시 workflow에는 `contents: write`, `actions: read`가 이미 선언돼 있다.
  공개 저장소 쓰기는 기존 `RELEASES_TOKEN`을 사용한다. 토큰 값을 요청하거나 로그로 출력하지 않는다.
- **실제 태그 생성 성공은 아직 검증하지 않았다.** 토큰 권한과 저장소/조직 정책·태그 제한을 확인해야 한다.
  소스 저장소 rulesets 조회는 API 403(Free/private 관련 기능 안내)이었고 공개 저장소는 빈 목록이었다.
  이는 태그 생성 권한이 있다는 증명도, 자동화에 Pro 결제가 필수라는 증명도 아니다.
- 개발 시 소유자가 승인한 안전한 테스트 환경 또는 최초 명시적 배포에서 태그 생성을 확인한다.
  실패하면 권한/정책과 대상 ref를 명확히 알리고 게시를 멈춘다.
  보호를 우회하거나 태그 생성 검사를 빼거나 사용자에게 태그 푸시를 매번 요구하는 것으로 완료 처리하지 않는다.
- 태그 push가 또 다른 배포 workflow를 시작할 것이라고 가정하지 않는다.
  완료 이벤트로 시작한 후행 workflow가 태그 생성과 게시를 직접 이어간다.

## 6. 기존 후보 사용과 0.7.1 처리

- 이미 성공한 후보를 배포하는 경로는 자동 선택/검증 후 태그 생성/게시만 수행한다.
  실행 ID/attempt/SHA/version은 내부에서 해결하고 사용자에게 네 값을 다시 옮기게 하지 않는다.
- 단, **이번 자동화 구현은 workflow/scripts를 바꾸므로** 현재 0.7.1 후보의 fingerprint와 달라진다.
  기존 게시 게이트를 무시해서 그 후보를 새 자동화로 강제 배포하지 않는다.
- 현재 0.7.1은 기존 절차로 마무리한 뒤 다음 배포부터 자동화를 쓰는 것을 권장한다.
  자동화를 먼저 적용하려면 새 검증이 필요하며, 사용한 태그는 실패해도 재사용/이동하지 않는다.
- 이번 0.7.1의 기존 '검증만' 실행을 자동 게시 승인으로 소급 해석하지 않는다.

## 7. 개발 수정 범위와 완료 기준

- workflow, 후보 승인/선택·태그 전후 검사·필요한 회귀만 최소 수정한다.
  게임 판독·설정/오버레이 동작을 건드리지 않는다.
- AGENTS.md·CLAUDE.md·Windows 검증 문서의 '사용자 직접 태그/별도 승격' 규칙을
  '사용자가 원버튼 실행에서 조건부 게시 승인, Actions가 태그/게시 수행'으로 일관되게 갱신한다.
  검증만 기본값·일반 푸시 무배포·독립 소스 QA·버전/동일 파일/비용 원칙은 유지한다.
- 조건부 승인 없는 검증 성공, 실패/취소/필수 단계 skip, fork/PR, 잘못된 source/run/attempt,
  위조/잘못된 모드, 만료·퇴출·해시 오류·입력 변경·태그 충돌을 주입해 **게시 0회**를 검증한다.
- 성공 경로는 사용자 실행 1회 → Windows 무거운 검사/빌드 각각 1회 → 자동 확인 →
  태그 생성 → 같은 exe 게시로 끝난다. 추가 Codex 확인 요청이나 ID 전달·수동 태그가 없어야 한다.
- 유효한 기존 후보 경로는 검사/빌드 0회이고, 중복 이벤트/재실행에서 이중 게시가 없어야 한다.
- 한도(후보당 200MiB·1일·최대 2개), 태그 재사용 금지, 작성자 대사 보존, 부분 실패 조사를 유지한다.
  '워크플로가 끝날 때까지 자동으로 기다림'을 위해 같은 락의 부모/자식을 서로 기다리게 하지 않는다.
- 새 테스트는 기존 `tests/test_release_candidate.py`의 사례를 재사용/확장한다.
  이미 검증된 같은 조건을 새 경로로 중복 수집하지 않는다. 개발 후 독립 QA를 받는다.

## 8. 이번 검토의 실행 결과와 한계

- 현재 후보/게시 회귀를 직접 재실행: **69 passed / 2.03초**.
  현재 check_context가 in_progress를 거부하고 태그/입력 변경을 차단하는 기존 사례를 포함한다.
- 확인한 것은 현재 코드의 자동 검사 가능성과 연결 시 필요한 수정 경계다.
  새 workflow_run 이벤트, 승인 전달, Actions의 태그 생성/자동 게시는 구현·실행하지 않았다.
- 기존 0.7.1 성공 검사를 다시 돌리거나 태그·Release를 생성하지 않았다.
  이 문서와 통합 QA 링크만 변경하므로 현재 검증 후보의 중요 입력은 그대로다.
