# 배포 검증 수동 절차 개선 전달

- 날짜: 2026-10-20 (Asia/Seoul).
- 요청: 사용자가 Windows 검증을 실행했으며, 매번 같은 수동 절차를 반복하지 않도록
  기존 약속과 현재 동작을 정리해 개발에 전달한다.
- 기준 소스: `92ffdf2a223a7a1e91148e20e5640f04c113eba9`.
- 상태: 운영 기준 명확화와 개발 제안이다. CI/게시 구현을 고친 결과가 아니다.
  검증 생략이나 사용자 승인 없는 자동 게시를 승인한 문서로 해석하지 않는다.

## 1. 현재 동작과 반복 안내의 원인

- `.github/workflows/windows.yml`과 `release.yml`은 모두 workflow_dispatch만 받는다.
  일반 푸시로 Windows 검증은 시작되지 않고, 검증 성공만으로 게시도 시작되지 않는다.
- 현재 절차는 독립 QA → 사용자 Windows 검증 실행 → 결과 확인 → 검증 SHA에 사용자 태그
  → 사용자 승격 실행이다. 승격 시 run_id/attempt/source_sha/version까지 직접 입력한다.
- 따라서 '매 푸시마다 Windows 검사하지 않는다'와 '실제 배포 후보는 Windows에서 검증한다'는
  서로 다른 기준이다. 이전에 안내한 위험 기반 검증은 전자이며, 후자를 자동화한 구현은 아직 없다.
  최근 이름 이관은 시작·설정 저장 코드 변경이고 신규 0.7.1 후보도 없으므로 이번 최종 검증은
  현행 기준상 필요했다. 사용자가 불필요한 동작을 잘못 수행한 것으로 설명하지 않는다.
- 개선 대상은 작은 변경마다의 과잉 요청, 실행 상태를 확인하지 않고 재실행을 요구하는 안내,
  사용자가 여러 값과 화면을 반복해서 옮기는 배포 절차다. 회귀 테스트 자체를 없애는 요청은 아니다.

## 2. 지금부터 적용할 안내·운영 기준

1. 일반 개발 푸시·문구/UI 조정·QA 문서 갱신은 관련 로컬 검사로 확인한다.
   QA를 요청했다는 이유만으로 수동 Windows 검사를 요구하지 않는다. 작은 변경은 모아서 배포한다.
2. 로컬에서 이미 확인한 실패는 먼저 개발에서 수정·푸시·후속 QA로 처리한다.
   실패를 알고도 Windows에서 다시 확인하라며 사용자의 시간/무료 한도를 쓰지 않는다.
3. **배포할 변경 묶음의 소스와 버전을 확정한 뒤 Windows 후보를 한 번 만든다.**
   개발 중 별도 Windows 실행이 꼭 필요한 네이티브/시작/종료/설정·패키징 위험은
   이유와 확인할 항목을 명시한다. 최종 후보와 같은 입력이면 성공 결과를 중복 실행하지 않는다.
4. 실행을 요청하기 전에 현재 SHA·버전·중요 입력 fingerprint에 맞는 진행 중 실행 또는
   유효한 성공 후보가 있는지 조회한다. 실행 중이면 같은 실행을 확인하고 새 실행을 요구하지 않는다.
   성공 후보가 유효하면 승격에 사용한다. 일반 Markdown만 바뀐 경우 새 후보를 요구하지 않는다.
5. 이전 다른 제품의 녹색 실행, 파일 없는 성공, 만료/퇴출된 후보, 실패/취소/필수 단계 skip은
   재사용하지 않는다. 제품·빌드·테스트·실행 코드/검증 자산의 중요 입력 변경은 재검증 사유다.
   새 실행이 필요하면 '무엇이 바뀌어 이전 후보를 못 쓰는지'를 먼저 설명한다.
6. 최종 게시에서는 같은 exe를 승격한다. 전체 테스트·exe 빌드를 다시 실행하지 않는다.
   실패를 skip하거나 assertion을 완화해 통과시키지 않는다.
7. gh가 설치되지 않은 사용자에게 같은 CLI 실패를 반복시키지 않는다. 현재는 GitHub Actions UI의
   실제 워크플로 이름·필수 입력을 안내한다. 사용자에게 실행 SHA/run/attempt를 직접 조사시키지 않는다.

## 3. 개발 권장안: 사용자 조작 최소화

### 현행 게시 승인 정책 안에서 개선할 부분

- Windows 검증 요약에 버전·검증 SHA·run/attempt·테스트/빌드/보관 결과·후보 만료·다음 작업을
  한 곳에 표시한다. 실패 시 테스트/빌드/업로드/결제·러너 문제를 구분한다.
- 승격 입력은 하나의 정확한 후보 식별자로부터 나머지 값을 검증해 가져오도록 단순화한다.
  '가장 최근 성공'을 무조건 고르지 말고 저장소·워크플로·버전·SHA·attempt·유효 기간을 확인한다.
- 태그/후보/현재 중요 입력 불일치와 버전 재사용은 기존처럼 차단한다.
  사용자 최종 게시 승인은 계속 필요하며, 검증 성공을 곧 게시 승인으로 취급하지 않는다.

### 추가 정책 변경 제안: 명시적 배포 선택 1회

반복 조작을 더 줄이려면 사용자가 버전을 입력해 **'검증 후 배포'를 명시적으로 선택한 한 번의 실행**에서
전체 Windows 회귀 → 네이티브 → exe 빌드 → 증명/보관 → 동일 산출물 게시까지 이어지는 방식을 권장한다.
별도로 '검증만' 모드도 유지하고 기본값으로 둔다. 일반 푸시·검증만 실행에서는 절대 게시하지 않는다.

- 이것은 기존 '검증이 끝난 뒤 사용자가 태그·승격을 승인'하는 시점을 바꾸는 제안이다.
  **사용자가 사전에 조건부 게시를 승인하는 방식에 동의한 뒤에만 적용한다.**
  사용자의 이번 0.7.1 검증 실행을 이 모드의 배포 승인으로 소급 해석하지 않는다.
- 승인 시 AGENTS.md·CLAUDE.md·Windows 검증 문서를 함께 정리하고, 태그 생성 주체/시점,
  중단·실패·부분 게시 복구도 명시한다. 기존 수동 태그 규칙과 충돌한 채 자동화를 추가하지 않는다.
- 최초 승인 대상을 특정 소스/버전에 고정한다. 실행 중 main이 바뀌어도 새로운 코드를
  조용히 배포하지 않는다. 기존 gate/seal/check/delivery와 정확한 파일 검증을 재사용한다.
- 게시 job은 앞선 단계가 모두 성공했을 때만 실행한다. 알 수 없는 권한/비밀값을 추가하거나
  사용자의 일반 푸시를 자동 배포 승인으로 취급하지 않는다.
- reusable workflow/job을 구성할 경우 같은 concurrency 그룹의 상위 실행이 하위 실행을
  기다리며 서로 막는 구조를 피한다. 검증/게시 직렬화와 후보 퇴출 방지도 유지한다.

## 4. 비용·실패·회귀 완료 기준

- 일반 푸시/단순 문서 푸시로 유료 Windows 실행이 생기지 않는다.
- 같은 후보의 검증·게시 과정에서 무거운 회귀/빌드는 각각 1회만 수행한다.
  기존 배포 게이트와 파일 동일성 검증을 줄여 시간을 절약하지 않는다.
- 후보당 200MiB 이하·1일·최대 2개 보관과 같은 exe 재사용을 유지한다.
  저장 한도 관리만으로 계정 전체 무료 분/저장량 초과가 절대 없다고 보장하지 않는다.
- 실패/취소/만료/중요 입력 변경·태그 충돌·업로드 실패에서 게시되지 않음을 검증한다.
  같은 이름의 다른 파일/후보를 자동으로 대신 게시하지 않는다.
- CI 분기·후보 선택·승인 조건은 로컬 모델에서 먼저 검증하고, 필요한 Windows 최종 확인을 묶는다.
  정책 개선 자체를 검증하려고 제품 배포마다 수동 실행 횟수를 늘리지 않는다.
