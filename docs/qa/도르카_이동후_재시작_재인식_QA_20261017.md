# 도르카 원본 위치 이동 후 재시작 재인식 QA

> 후속 `1b7c8a4`: 등록된 게임 문맥의 옛 숫자 영역 오인은 원래 재현에서 수정 확인했다.
> 자체 창 가림 재현은 여전히 실패하고, Windows 검증은 네이티브 접근 위반으로 중단됐다.
> [통합 및 재시작 수정 후 독립 QA](도르카_투아림_통합_및_재시작수정_독립QA_20261017.md)를 참조한다.

- 날짜: 2026-10-17 (Asia/Seoul).
- 기준 main: `3d9e2d9773ff914e908a3a8c00bcebf7cc4d3ccc`. 직전 변경은 기획 문서뿐이고
  제품 소스는 `b4c6eb1`과 동일하다. `ui/dorcha_tab.py` blob은 `b334bfcb278b185910a833054309e570ed718932`다.
- 사용자 순서: 앱 실행 -> 도르카 사용/영역 지정 -> 게임 안 원본 도르카 위치 이동 -> 정상 작동 확인
  -> 앱 종료/재실행 -> **--/15** -> 자동찾기를 한 번 더 해서 복구.
- 이는 이전 '다른 테스터의 전체 오버레이 고정 유실'과 별도 조사다. 게임 원본 위치와
  앱 오버레이 표시 위치를 혼동하지 않는다. 사용자 조작을 결함 원인으로 취급하지 않는다.

## 결론과 확정 범위

사용자가 겪은 실제 실패 원인은 **아직 확정하지 않았다**. 다음을 구분한다.

1. 옛 등록 영역의 다른 숫자를 도르카로 믿고 재탐색을 생략하는 결함은 독립 재현했다.
   다만 결과가 숫자 0이므로 사용자가 확인한 --/15의 원인으로 단정하지 않는다.
2. 앱 소유 창이 원형 장식을 가리는 경우, 재시작 후 --/15가 되고 같은 입력에서
   명시적 자동찾기로 복구되는 흐름도 구성했다. Windows 실캡처가 아닌 통제된 합성 입력이므로
   자체 가림의 실제 Windows 영향과 당시 현상과의 일치는 미확정으로 분류한다.
3. 옛 영역이 비어 있고 현재 UI가 가려지지 않은 대조군은 재실행 후 자동으로 복구된다.
   따라서 '재탐색 좌표를 저장하지 않아서 무조건 실패한다'는 결론은 틀리다.

## Confirmed Bug: DORCHA-RESTART-STALE-ROI-QA-01

- 심각도: **P2**. 실제 자원과 다른 숫자가 표시되고 현재 원본으로의 복구가 막힐 수 있다.
- 조건: A를 등록한 뒤 UI를 B로 옮겨 정상 재탐색한다. 이후 게임 창 안의 A에 다른 읽을 수 있는
  숫자 0이 나타난 상태에서 앱을 재시작한다. B에는 실제 도르카 15와 장식이 계속 보인다.
- 기대: 초기 영역이 현재 도르카인지 검증하고 B의 현재 15를 읽는다. 확신할 수 없으면 보류한다.
- 실제: 30회 tick 모두 A의 0을 읽고 `_live_box=A`, 전체 화면 재탐색은 **0회**다.
  전체 입력에 `locate_dorcha()`를 직접 실행하면 B를 찾고 15를 판독한다.
- 원인: `ui/dorcha_tab.py:36`에서 재실행 시 실행 중 위치/게임 문맥이 비어 있다.
  `:151`은 옛 승인 영역부터 읽고 `:166`은 숫자만 읽히면 문맥을 유효하게 설정한다.
  `:171`은 None일 때만 재탐색한다. 같은 게임 창 내부라는 조건만으로 장식/현재 원본 여부가 확인되지는 않는다.
- B를 다시 자동찾기/승인하는 현재 경로(`:302`, `:344`)를 거치면 같은 화면에서 15로 복구한다.
- 사용자의 실제 표시가 --/15였으므로 **이번 라이브 실패와 다른, 조사 중 발견한 결함**으로 기록한다.

## Highly Likely Bug: DORCHA-RESTART-SELF-CAPTURE-QA-02

- 심각도: **P2**. 정상 사용 중 배치한 앱 창/오버레이와 원본이 겹치면 실행 중에는 읽히던 자원이
  재시작 뒤 --/15로 남고 수동 자동찾기를 반복해야 할 가능성이 있다.
- 조건: B의 숫자 영역은 비어 있지 않고 유효한 15지만, 원형 장식의 위쪽 45x17 픽셀만
  앱 소유 창이 가린다. 사용자가 저장한 오버레이 위치를 잘못이라고 전제하지 않는다.
- 재현: 실제 Qt QWidget을 해당 부분에 놓고 그 렌더를 원본 위에 합성한다. 실행 중 B를 읽는 기존
  인스턴스는 **15를 유지**한다. 이를 종료하고 A가 저장된 상태로 재생성하면 전체 재탐색이 한 번
  실행되지만 장식을 찾지 못해 **--/15**가 된다. 동일 합성 입력의 숫자 크롭 판독은 여전히 15다.
- 대조: 실제 `screen_grab.capture_for_autofind(require_game=True)`를 사용하면 보이는 Qt 창들을
  숨기는 동안 합성 캡처의 가림도 없어져 B 검출에 성공한다. 기존 승인 저장 경로를 적용하면,
  가리는 창이 복원된 뒤에도 B 숫자를 읽어 **15**로 돌아온다. 모달 확인창 클릭 자체는 모사했다.
- 기술적 원인: `ui/dorcha_tab.py:198`의 재탐색은 `:210`에서 `_grab_rect()`를 직접 호출하고,
  `:255`는 mss로 데스크톱의 해당 사각형을 읽는다. 자체 창을 숨기거나 캡처에서 제외하지 않는다.
  반면 `ui/screen_grab.py:129`의 명시적 자동찾기는 보이는 최상위 Qt 창을 잠시 숨긴다.
  같은 게임 좌표라도 검출기에 전달되는 화면이 달라질 수 있다.
- 환경 근거: 잠긴 의존성 mss 10.2.0의 Windows GDI 경로는 BitBlt에 SRCCOPY|CAPTUREBLT를 사용한다.
  제품 소스에서 SetWindowDisplayAffinity/WDA_EXCLUDEFROMCAPTURE 같은 자체 창 제외는 찾지 못했다.
- 검증 제한: Windows에서 실제 중첩 창을 캡처하지 않았다. 사용자의 당시 화면에 자체 창이 겹쳤다는
  자료도 없다. 가림이 없는 실제 화면에서도 실패할 수 있으므로 **당시 원인 확정이 아니다**.
  임의의 게임 UI 가림 자체가 모두 앱 버그라는 주장도 아니다. 앱의 자체 표시가 재복구를 막는 경로를 조사한다.

## 좌표 저장 계약과 후속 수정 기준

- 현 명세는 재탐색 물리 좌표를 실행 중 캐시로만 쓰고 사용자 승인 영역은 자동으로 덮어쓰지 않는다.
  `ui/dorcha_tab.py:246`에서 B는 `_live_box`에만 들어간다. `_save()`의 pos는 앱 오버레이 표시 위치다.
  원본 추적 좌표 B를 뜻하지 않는다. 이 계약 자체를 저장 실패 버그로 보고하지 않는다.
- 재시작 시 승인 영역을 신뢰하기 전에 실제 원본 문맥을 확인하고, 필요하면 새 위치를 안전하게 재탐색한다.
  자동 재탐색 결과를 무조건 승인 영역에 저장하거나 과거 숫자를 복원해 문제를 가리지 않는다.
- 명시적 자동찾기와 실행 중 복구의 캡처/자체 창 제외 정책 차이를 검증한다. 매 틱 앱 창을
  숨기는 식의 깜빡임·포커스 탈취나 데스크톱 전체 무제한 탐색으로 해결하지 않는다.
- 실행 중 재탐색의 입력 이미지/게임 대상/거부 이유/다음 재시도 시각이 없으면 이번 --/15 원인을
  확정할 수 없다. 필요하면 이 경로의 진단을 추가한다. 명시적 자동찾기 ZIP은 가림을 제거한 다른
  입력일 수 있으므로 그것만으로 직전 실행 중 실패가 재현된다고 가정하지 않는다.
- 기존 원본 0~15, 가림/복수 후보 거부, 게임 문맥 변경, 종료/취소/늦은 결과, 승인 영역/표시 위치
  및 투아림 독립성은 유지한다. 고정 유실 제보와 이번 판독 복구 문제를 한 수정으로 묶어 단정하지 않는다.

미해결 결함/가능한 실패 경로와 재현 자료를 개발 세션에 전달한다. QA에서 제품을 수정하거나
새 릴리즈 명령/태그를 실행하지 않았다.
