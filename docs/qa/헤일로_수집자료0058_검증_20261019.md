- 분류: 수집 자료 적합성 확인. 이번 자료에서 새 제품 버그를 확정하지 않았다.
- 앱/테스트/판독기 구현이나 원본 ZIP을 변경하지 않았다.

## 결론

**시간 판독기 개발 및 초기 회귀 검증에 사용할 수 있다. 추가 수집이 끝날 때까지 개발을
미룰 필요는 없다.** 다만 현재 제품에는 시간 판독기가 없으므로 이 확인을 실제 판독 성공률이나
헤일로 알림 정확도 검증으로 표현하지 않는다.

## 실제 확인

- ZIP CRC 검사 통과. PNG/JSON 75쌍이 존재하고 누락·시퀀스 중복이 없다.
- 75장 모두 원본 PNG 디코딩 성공, 119×42 BGR, JSON shape/등록 영역 크기와 일치.
- PNG 바이트는 75장 모두 서로 다르다. 이것만으로 숫자별 정답이 다르다고 판단하지 않았다.
- 0001~0074는 육안으로 읽을 수 있는 타이머이며 `14:41`부터 `13:00`까지 일부 구간이다.
- 0075는 타이머가 사라지고 어두운 배경/녹색 문구만 남았다. 손상 파일로 버리지 말고
  **타이머 없음/판독 보류**의 음성 사례로 분리한다. `00:00` 정답으로 지정하지 않는다.
- 지정 영역은 숫자/콜론 전체를 포함하고 4자리 숫자가 잘리지 않는다. 확대된 검사 시트에서
  평상시, 밝은 이펙트, 어두운 배경, 붉은 배경, 녹색 안내 문구가 겹치는 조건을 확인했다.
- 원본 0001:14:41, 0014:14:26, 0025:14:13, 0049:13:28, 0056~0074 안내 문구 겹침 등을
  서로 다른 조건의 개발/검증 사례로 사용할 수 있다.
- 메타데이터는 전부 `raw_time: null`, `read_status: not_implemented`, 앱 버전 0.5.1,
  `source: foreground_game_region`, backend mss다. 현재 수집 단계의 기록과 일치한다.
- 첫/마지막 캡처 시각 차이는 101.571399초다. 벽시계 시각 간격은 약 0.993~16.523초이며
  연속 영상이나 모든 초가 빠짐없이 있는 자료는 아니다. monotonic 기반 수집 간격과
  UTC 메타데이터 시각 간격을 동일한 타이밍 보증으로 취급하지 않는다.

## 이 자료로 미검증인 범위

- 분은 13/14뿐이다. 숫자 종류 0~9는 초 일의 자리에 포함되지만 분의 각 자리나 자릿수 전체를
  검증하는 자료는 아니다.
- 초 십의 자리 5, 즉 `xx:50~xx:59`는 없다.
- `15:00` 시작, 분 경계를 넘는 연속 쌍, `10:00→9:59` 자릿수/배치 변화, `1:00→0:59`,
  `0:00`, 다른 글꼴/DPI/창 크기/테스터 화면은 미검증이다.
- 이 ZIP은 지정된 119×42 영역의 잘라낸 원본뿐이므로 전체 화면에서 자동찾기의 위치 탐색 성능은
  검증할 수 없다. 자동찾기에는 타이머 주변을 포함한 기존 전체 화면 원본도 별도로 활용한다.
- 시간 OCR, 15분 내부 시계의 누적 오차, 63초 주기/5초 전 알림은 미구현이거나 이번 확인 범위 밖이다.

## 개발 전달 방향

이 74개 정답 사례와 1개 미검출 사례로 판독 경로를 만들고 배경/이펙트/녹색 문구 조건을 나눠 평가한다.
추가가 편한 때 한 자리 분과 50초대/분 경계를 보충한다. 처음부터 15분 전체를 다시 찍을 필요는 없다.
숫자 없는 화면이나 모호한 화면은 보류하고 이전 값/내부 시계를 OCR 정답으로 채우지 않는다.

## Windows 후보와의 관계

실행 중인 0.5.2 검증 run 39245884765는 `218134b35725e0f522944dd7f7593ed5220857b1`이 대상이며
이번 tests/data/0058.zip은 포함하지 않는다. 현행 fingerprint는 tests/ 전체를 대상으로 하므로
이 자료를 추가한 main과 이전 후보는 중요 입력이 다르고 그대로 승격하면 거부되는 것이 정상이다.
이번 실행 결과는 새 흐름 확인에 활용할 수 있지만 실제 현재 main을 배포할 때는 새 후보 검증이 필요하다.
이 자료 확인만을 이유로 지금 Windows를 다시 실행하거나 태그를 만들지는 않았다.
