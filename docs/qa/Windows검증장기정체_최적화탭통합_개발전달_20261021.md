## 2. CI 수정·조사 요구

### 관측된 배포 차단 상태

- 심각도: 높음. 이번 후보의 검증·빌드가 끝나지 않아 배포 승인 근거가 없다.
- 발생 조건/재현: 위 SHA의 `windows.yml`, `validate-and-publish` 실행에서 전체 격리 회귀 2-worker 단계. 원인 파악 전 같은 전체 실행을 무작정 반복하지 않는다.
- 사용자 영향: 과도한 대기·Windows 사용량 소모, 실패 위치를 판단하기 어려움. 게임 앱의 실제 런타임 멈춤으로 확대 해석하지 않는다.
- 기술적 원인: **미확정**. 마지막 활성 node/worker/fixture 단계와 스택이 필요하다. 새 테스트 수 증가만으로 원인을 설명하지 않는다.
- 검증 결과: 위 시간표와 GitHub 상태 API로 단계 장기 정체는 확인. 특정 제품/테스트 코드의 `Confirmed Bug` 판정은 보류한다.
- 관련 위치: `.github/workflows/windows.yml:59`, `:77`, `:82`; `pytest.ini`; `pyproject.toml`; `tests/conftest.py`의 Qt/worker 격리·정리 경로.

### Potential Risk: 개별 검사 정체의 식별·종료 근거 부족

- 심각도: 중간. 특정 테스트나 fixture가 끝나지 않으면 전체 후보 생성이 지연될 수 있다.
- 현재 코드는 job 전체 `timeout-minutes: 45`와 종료 시점의 `--durations=30`/JUnit을 사용한다. pytest 설정·의존성에서 개별 테스트 timeout/stack watchdog은 확인하지 못했다. job 제한만으로 멈춘 node를 특정할 수 없다.
- 이번 job은 설정 제한 시간 이후에도 API상 실행 중이지만, 이것만으로 GitHub 제한 기능 자체가 고장 났다고 단정하지 않는다.
- 재현 방법: 실제 실행 로그에서 진행이 끊긴 node·setup/call/teardown 단계·worker PID를 확인하고 해당 순서로 격리 재현한다. 취소·종료 후 로그가 열리면 원인을 이 문서에 후속 기록한다.
- 미검증: Windows의 마지막 활성 테스트, subprocess/Qt 정리 스택, 러너 실제 종료 상태. Windows 정체 원인을 Linux 97건 통과로 기각하지 않는다.

개발 처리 순서는 다음과 같다.

1. 해당 실행의 최종 로그·마지막 진행 node·worker별 진행/스택을 확보하고, 단일 사례와 필요한 선행 순서를 구성해 원인을 고친다. 테스트 본문뿐 아니라 fixture 생성·정리, QThread 종료, 외부 호출과 subprocess 정리도 확인한다.
2. 테스트/fixture가 정체돼도 마지막 활성 node·phase·PID·시각이 남고, 주기적 stack dump와 진행 기록을 회수할 수 있게 한다. 종료 때만 생성되는 durations/JUnit에 의존하지 않는다.
3. Windows/xdist에서 동작이 검증된 제한 방식으로 개별 실행·정리의 상한을 둔다. 실제 정상 소요와 긴 사례를 조사해 예산을 정하고, timeout을 실패로 남기며 worker·자식 프로세스 정리를 확인한다. 스택 출력만 하는 기능을 실행 중단 보장으로 설명하지 않는다.
4. 실패·timeout·취소 때 가능한 진단을 짧은 보관 기간/작은 크기로 저장한다. 강제 종료로 수집이 불가능한 경우도 결과에 명시하고, 로그에 비밀값·사용자 경로를 원문으로 넣지 않는다. 전체 job 제한은 최후 보호로 유지한다.
5. 수정 전 실패/정체 조건과 수정 후 관련 검사 결과를 남긴 뒤 독립 QA를 받는다. 전체 Windows 후보 검증은 수정본에 대해 필요한 한 번으로 모으고, 기존 검증→동일 exe 게시 구조를 유지한다.

테스트 skip·assertion 완화·누수 검사 삭제·근거 없는 worker 증설·45분 제한 확대·검증 우회 게시로 해결하지 않는다. 공개 배포 성공 여부와 검증 성공 여부도 구분한다.

## 3. 사용자 확정 요구: 최적화는 상위 탭

최적화는 알파 기능을 유지하되 **설정의 실행 버튼이 아닌 본창 상위 탭**으로 제공한다. 제작자가 볼 때 왼쪽부터 순서는 다음과 같다.

```text
전투 보조 | 파티 모집 | 편의기능 | 최적화 | 설정
```

- 최적화는 **편의기능 다음, 설정 앞**이다. 버튼을 탭처럼 꾸미거나 빈 탭을 누르면 기존 별도 창만 띄우는 방식은 요구를 충족하지 않는다. 본창 안에서 설정·FPS 기능을 사용하게 한다.
- 제작자 전용 알파 접근 정책을 완화하는 요구가 아니다. 일반 사용자/일반 로그인에는 새 적용·측정 진입점을 공개하지 않는다. 기존 제작자 판정과 backend 시작 경계도 유지한다.
- 접근 해제·로그아웃·복구 기록 손상/미완료·이전 측정 정리 필요 상태에서도 기존 CPU/네트워크/수집 프로세스 복구 경로를 잃지 않는다. 복구가 필요한 비제작자에게는 복구 전용 상태를 제공하되 새 적용·측정 권한은 주지 않는다. 구체적 노출 방식은 개발 시안에서 확인한다.
- 기존 최적화/FPS 하위 선택은 다른 기능의 하위 가로 탭과 같은 방식으로 제공하는 방향이다. 상위 탭 선택만으로 환경 검사·권한 상승·CPU/TCP/RSS 변경·측정/기록을 시작하지 않는다.
- 설정의 기존 일반 실행 버튼은 중복 진입점으로 남기지 않는다. 복구 예외 때문에 필요한 동선은 위 복구 정책에 맞게 정리한다.
- 본창/탭 전환마다 Engine·Collector·timer·overlay를 새로 만들거나 callback을 중복 연결하지 않는다. 기존 세션과 앱 종료·설정 교체 시 정리 책임을 보존한다.

## 4. 모든 화면 템플릿의 영역 구분까지 통일

여기서 템플릿은 **최적화·FPS의 화면 구성**이다. OCR/아이콘 매칭 템플릿 교체 요구가 아니다. 타이틀만 추가하거나 폰트만 맞추는 작업으로 끝내지 않는다.

- 다른 탭에서 쓰는 공통 `FeatureHeader`의 제목 크기·굵기, 은은한 회색 설명, 설명 아래 구분선, 여백을 그대로 사용한다. 별도 고정 글꼴 크기를 복제하지 않는다.
- 본문의 기능 영역도 기존 `QGroupBox`/폼/조작 행 기준으로 구분한다. 불필요한 중첩 박스나 새 디자인 체계를 만들지 않는다.
- 버튼·체크·선택 상자·잠금·상태 색상·본문 글꼴은 기존 앱과 일치시킨다. 내용이 길면 줄바꿈/스크롤로 처리하고 좁은 창·높은 DPI에서도 버튼/상태가 잘리지 않게 한다.
- 권한·연결 끊김 경고와 미적용/실패/복구 필요 상태를 감추지 않는다. 요청한 옵션과 실제 적용된 결과는 분리해 읽을 수 있어야 한다.

구체적인 영역 묶음은 다음 권장안을 실제 앱 렌더로 제시한 뒤 확인한다. **상위 탭 위치와 영역 구분 요구는 확정이며, 치수·상세 배치는 시안 확인 대상**이다.

| 화면 | 영역 묶음 권장안 |
|---|---|
| 최적화 | 환경/CPU 정보·환경 확인, CPU 배치·코어 배분, 네트워크 어댑터·TCP/RSS·영향 안내, 시작/중단/원복과 적용·실패·복구 결과 |
| FPS 측정 | 대상/측정 시작·중단, 오버레이 표시·배율·위치 잠금, 현재 상태·수집 품질·오류 |

앞서 요청한 [프레임 기록 1단계](../game-frame-recording-stage1-spec.md)는 별도 기능 요구로 유지한다. 이번 탭 이동이나 FPS 표시만으로 파일 기록·세션 요약·ZIP 수집까지 구현했다고 보고하지 않는다. 함께 개발한다면 해당 명세의 수집 영역도 같은 규칙으로 묶는다.
