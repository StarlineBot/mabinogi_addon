## 판정

확인된 16->6, 12->2, 14->4, 18->8 누락은 원래 입력과 assertion으로 해소됐다.
로컬 관련 검사에서도 새 결함을 발견하지 않았다. 현재 보유 근거로 표시 전체를 숨겨야 한다고
판단할 필요는 없지만, 모든 10%대/배경/배율의 신뢰도를 보장하지는 않는다.

**Windows 회귀·네이티브·exe는 시작되지 않았으므로 최종 QA/릴리즈 승인은 대기**다.
앱 assertion 실패와 아래 실행 기반 문제는 구분한다.

## 코드 범위 확인

- 제품 코드 변경은 `detect/tuarim_reader.py` 한 파일이다. 기존 5픽셀 이상 경로,
  작은 렌더/넓은 입력 및 100% 보류 경로, 정상 빈 십의 자리 경로는 유지한다.
- 밝은 픽셀 1~4개일 때만 현재 정렬과 좌우 1px를 검사한다. 같은 일의 자리 숫자에
  NCC 0.85 이상, 십의 자리 **1**에 기존 0.6 이상이 동시에 필요하다.
  호출자의 더 높은 threshold도 존중한다. `tuarim_reader.py:39,208-221`.
- 이 경로가 9를 십의 자리로 만들어 90%대를 내보내지 않는다. 증거가 부족하면
  기존 한 자리 오독 대신 None을 반환한다. 이 때문에 일부 저값 표시는 `--%`로 보류될 수 있다.
- 영역·타이머·캡처·워커·설정/로그인·도르카·알림 상태 머신은 변경하지 않았다.
  새 폴링이나 매 프레임 디스크 접근도 없다. 추가 비교는 기존 희박한 잉크 분기로 제한된다.
- 일반 CI가 원래 독립 재현도 수집하게 테스트를 추가했다. 기존 재현 스크립트 blob
  `c351225c5656a7bfb9007d176a39fad9ef8239a6`은 변하지 않았다.

## 기존 세션 전후 비교

원래 수정 전 리더를 별도 메모리 모듈로 실행하고 현재 리더와 **동일한**
`tests/data/raw_7603.zip` 원본 2,926장을 비교했다. 원본이나 제품 파일을 덮어쓰지 않았다.

- 246장 결과가 바뀌었다. 모두 이전의 0~9가 새 10~19 또는 None이 된 경우다.
- **기존 10% 이상 값과 기존 None은 이 집합에서 바뀌지 않았다.**
  기존 90%대의 새 저값 오독을 이 집합에서 발견하지 못했다.
- 예시 `v09_7537`, `v08_7522`, `v07_7490`, `v06_7466`을 직접 열어
  실제 19/18/17/16인데 이전 9/8/7/6에서 각각 복구됨을 확인했다.
- 이전 0 -> None의 대표 `v00_7315`, `v00_7314`, `v08_7313`도 직접 열었으며 실제 10%였다.
  잘못된 0을 표시하기보다 불확실하게 보류하는 사용자 허용 방향과 맞는다.
- 246장 전체를 사람이 독립 라벨링한 것은 아니다. 위 비교는 변경 범위와 일부 원본 확인이지
  수정 후 전 구간 정확도 100%나 모든 한 자리 값의 무회귀 증명이 아니다.
