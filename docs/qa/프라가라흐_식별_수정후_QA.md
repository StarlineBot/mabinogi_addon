## 1. 실제 변경 범위

현재 tree 비교에서 제품 변경은 `tracker/debuff_engine.py`의 프라가라흐 위치별 경쟁 판독과
`release_notes.md`의 0.4.74 설명이다. 구현 설명과 테스트 파일도 추가됐다.
원본 크롭 14종을 기본 이미지로 교체한 수정이 아니며, 기본/사용자 이미지와 1~3차 게이트,
보스바 설정 및 UI는 그대로다.

현재 코드는 두 프라가라흐 템플릿이 엔진에 모두 있을 때만 같은 위치의 컬러 점수를
비교한다. 다른 위치의 두 종류가 동시 적용된 경우는 각각 인정하고, 동일 사용자 이미지의
동점은 확정 근거에서 제외한다. 진단용 `best_scores()`는 경쟁 전 원시 점수로 유지된다.

## 2. Confirmed Bug: DEBUFF-IDENTITY-QA-02

### P2: 한쪽 숨김 후 재시작하면 남긴 쪽의 오인식이 재발

- 발생 조건: 두 프라가라흐가 있는 엔진으로 시작한 뒤 한쪽을 오버레이에서 숨기고,
  앱 재시작 또는 추적 재구성으로 새 엔진이 만들어진다. 게임에는 숨긴 종류만 적용되어 있다.
- 예상: 남긴 종류는 실제로 적용되지 않았으므로 미적용 항목으로 표시되어야 한다.
  숨김 설정이나 앱 재시작 때문에 디버프 종류 판정이 달라져서는 안 된다.
- 실제: 숨긴 직후 기존 엔진은 정상 판정하지만, 재구성한 엔진에서는 숨긴 쪽의 비교 이미지가
  없어져 실제로 없는 반대 종류까지 적용됐다고 판단하고 표시를 없앤다.
- 사용자 영향: 필요한 디버프가 적용된 것으로 오해할 수 있다. 재시작 전후 표시도 달라진다.
  크래시/게임 입력 간섭을 재현한 것은 아니다.
- 기술적 원인:
  `ui/main_window.py:1401`은 `_debuff_order()`에 있는 표시 대상만 골라 템플릿을 로딩한다.
  반면 `:1438`의 `_on_debuff_tracking_changed()`는 기존 엔진의 순서만 갱신해 상대 템플릿을 남긴다.
  `tracker/debuff_engine.py:244`의 `_detect()`는 상대가 `_variants`에 없으면 경쟁을 생략하고
  기존 독립 검색으로 돌아간다. 표시 대상과 식별용 비교 자료가 결합된 결과다.
- 검증: 실제 `MainWindow._debuff_order()`로 숨김 설정의 순서를 구성하고,
  `set_order()` 전환 및 시작 코드와 같은 템플릿 필터링으로 만든 새 `DebuffEngine`을 비교했다.
  저장소 원본에서 자른 실제 16px 아이콘을 0.15초 간격 12회씩 입력했다.
- 결과: 기본 28px 이미지/원본 16px 후보 각각, 마법/물리 양방향 **4개 재현 모두 실패**했다.
  재시작 전에는 `{추적 중인 종류}`가 표시되고 재구성 후에는 빈 집합이 된다.
- 범위 구분: 단일 템플릿의 기존 오인식이 이번 수정에서 해결되지 않은 것이다.
  모든 오인식을 이번 변경이 새로 만들었다고 판단하지 않는다. 구현 문서에도 단일 템플릿은
  기존 동작이라고 적혀 있지만, 정상 숨김/재시작 경로의 정확성 문제로 별도 보고한다.
- 실행 한계: Windows 앱을 실제 재시작한 시험은 아니다. UI의 실제 순서 계산 함수와
  확인된 재구성 호출 경로, 실제 엔진 실행을 결합한 통제 재현이다.

재현 코드: [`scripts/qa_debuff_identity_gate_followup.py`](../../scripts/qa_debuff_identity_gate_followup.py)

```bash
PYTHONPATH=src uv run pytest scripts/qa_debuff_identity_gate_followup.py -k hiding_peer -q --tb=short
```

예상 결과: 기준 제품에서 **4 failed, 50 deselected**. 4개를 통과 기대값으로 작성했으며,
실패를 skip/xfail하거나 오인식 결과를 정답으로 인정하지 않았다. 일반 테스트는
`pytest.ini`의 `testpaths=tests`를 사용하므로 이 미해결 재현은 자동 수집에 포함되지 않는다.

수정 검토 방향: 화면에 표시/추적할 항목과 식별용 상대 템플릿을 분리한다. 숨긴 상대까지
오버레이에 표시하거나 모든 등록 아이콘을 매번 전체 검색할 필요는 없다. 필요한 상대를
후보 위치의 비교 자료로 유지하고, 숨김 전환/앱 재시작/영역 재등록 후의 동일성을 검증한다.
사용자 설정 초기화나 두 종류를 반드시 표시하라는 사용법으로 대체하지 않는다.

## 3. 통과 범위

관련 회귀/기존 독립 재현을 직접 실행했다.

```bash

```

- **181 passed, 26.51초**. 새 식별 검사, 기존 라이브 판독/깜빡임/버프 연장과 벤치마크 포함.
- 비교기 수정 전 재현했던 두 종류 동시 오인식은, 두 템플릿이 함께 있을 때 해결됐다.
- 실제 원본의 바와 숫자를 넣어 게이트를 활성화한 추가 독립 검사도 수행했다.
  1~3차, 마법/물리 단독, 좌표 1px 이동/가로 이동, 역순 표시, 두 종류 동시 적용을 확인했다.
- 종류 변경/빈 입력/보스 종료/재등장을 모드·이미지 조합마다 12회 반복했다.
  엔진 상태 사전의 키가 누적되지 않았고, 다음 등장 때 정상 판독했다.
- 프라가라흐 외 이름 대응이 확인된 실제 75슬롯에서 두 종류를 잘못 인정하지 않았다.
- 바 캡처 `None` 후 복구, 검은 바/퍼센트 판독 불가 상태에서도 기존 아이콘 판독이 유지됐다.
- 추가 검사 전체는 **50 passed, 4 failed, 31.10초**였다. 실패 4개는 위의 미해결 항목이다.
  이후 숨김 재현에 실제 UI 순서 함수를 연결해 **4 failed, 50 deselected, 0.55초**로 재확인했다.
  최종 파일의 정상 시나리오는 `-k 'not hiding_peer'`로 **50 passed, 4 deselected, 37.20초**였다.
- 정상 검사 초기 작성 시 표본 개수를 89로 잘못 적은 수집 조건을 75로 정정했다.
  해당 첫 실패는 제품 오인식이 아니며 결과에 섞지 않았다. 제품 테스트는 변경하지 않았다.
- 엔진, UI 시작/설정 경로, 판독기, 요구사항 등 관련 파일 11개의 로컬 Git blob SHA도
  검토한 원격 제품 tree와 대조하여 모두 일치함을 확인했다.

과거 크롭 자료의 `metrics.json`은 수정 전 스냅샷으로 보존했다. 현재 엔진의 정상 수정 때문에
그 도구의 과거 엔진 결과 비교가 달라지는 것을 이미지 손상이나 제품 회귀로 판단하지 않는다.

## 5. 완료 판단
