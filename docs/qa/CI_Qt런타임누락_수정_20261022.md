# Linux CI Qt 런타임 누락 수정

## 확인한 실패

- 사용자 승인으로 실행한 `verify-only` [39714887083](https://github.com/StarlineBot/mabinogi_addon/actions/runs/39714887083),
  SHA `b1187448bbd1660589149223dd9720d01b5db55f`, attempt 1을 조사했다.
- 실행은 2026-10-22 12:04:57~12:06:00 KST에 failure로 완료됐다. 취소나 장기 정체가 아니다.
  회귀 단계는 3.35초에 6 ERROR, 종료 코드 2로 끝났고 Windows 작업은 skipped였다.
- 첫 `[ci-first-error]`와 전체 로그를 직접 회수했다. 모든 오류는 공통 fixture의
  `ExternalBoundaries.__enter__()` → `audio_boundary()` → `from PySide6 import QtMultimedia`에서
  `ImportError: libpulse.so.0: cannot open shared object file`로 발생했다.
  설정 저장이나 버프 판독 등 각 테스트 본문이 독립적으로 망가진 것이 아니다.
- 오디오 출력을 fake 객체로 바꾸기 전에 QtMultimedia 자체를 로딩해야 한다. Python wheel과
  Qt offscreen 설정만으로 시스템 공유 라이브러리가 공급되지 않는다. CI의 apt 목록에서
  이를 제공하는 `libpulse0`이 빠져 있었다. 로컬에는 이미 설치돼 있어 로컬 통과로 놓쳤다.
- `--maxfail=3`은 작동했다. xdist 진행 중 사례 때문에 최종 오류 수는 6건이었고,
  즉시 traceback 출력과 정리/진단 아티팩트 업로드도 성공했다. 진단 아티팩트는 3,385바이트였다.
- 회귀 직전 샘플은 메모리 available 14,870MiB, 디스크 available 84GiB,
  작업 cgroup의 oom/oom_kill 0이었다. 이번 실패는 공유 라이브러리 누락으로 특정되지만,
  이 한 시점의 측정이나 이번 오류로 과거 정체/OOM 여부를 확정하지 않는다.

## 최소 수정

1. `windows.yml`의 Linux Qt 런타임 apt 설치 목록에 `libpulse0`을 추가했다.
2. 설치 뒤 회귀 전에 필수 `Check Qt runtime imports` 단계를 추가했다. 1분 제한으로
   QtCore/QtGui/QtWidgets/QtNetwork/QtMultimedia를 실제 import해 누락 시 즉시 실패한다.
   실제 오디오 서버/장치 재생은 하지 않는다.
3. 기존 CI 계약 테스트 파일에 설치 목록, 사전 로딩 순서/대상, 제한 시간, 실패를 숨기지 않는
   조건을 검사하는 사례 1개를 추가했다. 앱 코드·버전·배포 승인/증명 정책은 바꾸지 않았다.
4. 저장소가 공개로 전환됐으므로 Actions 오류 콘솔도 공개라는 점을 현재 운영 문서에 명시했다.

## 개발 검증

- 추가 전 기존 CI 계약 34개를 `--collect-only --test-inventory`로 확인했다.
- 새 계약 검사로 수정 전 `libpulse0` 누락을 1 failed로 검출한 뒤 설정을 수정했다.
- 로컬 `dpkg-query`로 `libpulse0` 설치를 확인했고 Qt 모듈 5개 import에 성공했다.
  이는 개발 환경의 확인이며 깨끗한 Ubuntu 24.04 러너에서 apt 설치를 새로 실행한 결과는 아니다.
- 수정 후 관련 검사 **313 passed, 24.66초**, 감독 종료 코드 0. 실패한 설정/진단 사례,
  CI 계약, 창 기동/종료, 즉시 오류/자원 샘플러, 후보 차단/출처, Unicode 규칙을 포함한다.
  skip이나 assertion 완화로 실패를 우회하지 않았다.

## 미검증과 다음 행동

이 수정 뒤의 전체 Linux 회귀·GitHub Actions·Windows 검사/빌드는 아직 미실행이다.
개발 검증을 후속 독립 QA나 원래 정체 문제의 최종 해결로 안내하지 않는다.
푸시 후 후속 QA에서 설치/사전 로딩/게이트 보존을 확인하고, 사용자가 새 SHA의 `verify-only`
실행을 결정한다. 같은 실패 SHA의 Re-run은 수정본 검증이 아니다.
실행 URL을 받으면 첫 오류·리소스·Windows 단계 결과를 확인한다. 에이전트가 Actions나
태그/게시를 실행하지 않으며, verify-only의 성공도 배포 승인은 아니다.

사용자가 저장소를 공개로 전환했고 API에서 공개 상태를 확인했다. 현재 표준 GitHub 호스팅
러너의 실행 분은 공개 저장소 정책을 따르지만, 과거 비공개 기간의 청구가 취소되거나
저장 등 모든 자원이 무료라는 뜻은 아니다. 예산 증액이나 반복 실행을 해결책으로 삼지 않는다.
