# 최적화 네트워크: 관리자 실행 후에도 RSS·TCP 실패

> 2026-10-21 후속 독립 QA: `75e1f8a`의 구조적 GUID 비교·오류 구분과 관련 회귀를 검증해 소스 범위에서 차단 문제를 찾지 못했다. [후속 독립 QA](설정백업_네트워크수정_후속독립QA_20261021.md)를 최신 판단으로 따른다. 실제 Windows 장치 적용/원복과 사용자의 동일 PC 해결 여부는 아직 확인하지 않았다. 아래는 최초 실패 기록이다.

- 날짜: 2026-10-21 (한국 시간)
- 조사 소스: `3a6d253550d3ad1d3d0b117facd1bf141d091de6` (제품 수정 기준 `4ca6763`). 현재 소스와 실행 경로만 확인했으며 커밋 이력은 읽지 않았다.
- 라이브 제보: 일반 실행과 관리자 실행 모두 어댑터 `이더넷`을 선택한 뒤 `RSS`, `ack`, `nodelay`에 동일한 Windows 명령 실패가 표시됨. CPU는 게임 실행 대기 상태. 조회 시 공개 최신 릴리즈는 `v0.10.0`이었다.
- 결론: **장치 식별 문자열 계약 결함과 오류 정보 유실을 확인했다.** 실제 PC에서 이번 실패를 유발한 최종 예외는 현재 앱이 버리므로 단정하지 않는다. GUID 결함은 세 실패의 공통 경로이며 라이브 현상과 강하게 부합한다.
- 사용자가 추가로 조사하거나 관리자 재실행을 반복할 단계가 아니다. 조사·재현·개발 전달은 QA에서 수행한다. 게임 미실행은 정상적인 적용 순서이며 오류 원인으로 취급하지 않는다.

## 1. Confirmed Bug — 목록에서 선택한 정상 어댑터를 다시 찾지 못함

- 심각도: **P2**, 제작자 최적화 알파의 TCP·RSS·네트워크 복구 경로에 영향.
- 발생 조건: Windows 어댑터의 `InterfaceGuid`가 `{12345678-1234-1234-1234-123456789ABC}`처럼 중괄호가 포함된 정상 문자열로 반환됨.
- 사용자 영향: 환경 확인에서는 어댑터 목록이 표시되지만 적용 단계에서 `adapter unavailable`로 실패할 수 있다. CPU의 물리 코어 인식이나 관리자 권한과는 별개다. 이 공통 조회는 TCP/RSS 읽기·쓰기·어댑터 재시작에 사용되므로 복구 경로도 함께 수정해야 한다.
- 기술적 원인: `system/optimization.py:237`의 `adapters()`는 244행에서 `str(uuid.UUID(...))`로 GUID를 중괄호 없는 소문자 문자열로 바꾼다. 247~249행의 `_adapter()`는 저장값만 정규화한 뒤 PowerShell의 **원래** `[string]$_.InterfaceGuid`와 문자열 `-eq` 비교한다. PowerShell의 대소문자 비구분 비교도 중괄호 자체는 제거하지 않으므로 동일 GUID가 다른 문자열이 된다. 올바른 UUID 검증을 통과하는 입력을 같은 시스템의 후속 조회에서 배제하는 계약 결함이다.
- 영향 코드: TCP 읽기 265행, RSS 읽기 272행, TCP 쓰기 준비 290행, RSS 쓰기 준비 302행, 재연결 310행과 317행 모두 `_adapter()`를 공유한다. TCP 쪽도 원본 레지스트리 값을 읽기 전에 PowerShell 조회에서 실패하므로 관리자 실행으로 해결되지 않을 수 있다. 전역 autotuning은 이 공통 조회를 사용하지 않아 별도 판단해야 한다.
- 외부 입력 근거: Microsoft의 [Get-NetAdapter 사용 예시](https://devblogs.microsoft.com/scripting/weekend-scripter-use-powershell-to-find-auto-connect-wireless-networks/)는 `(Get-NetAdapter).interfaceGUID`를 중괄호 포함 형태로 보여준다. [Get-NetAdapter 공식 명세](https://github.com/MicrosoftDocs/windows-powershell-docs/blob/main/docset/winserver2025-ps/NetAdapter/Get-NetAdapter.md)도 함께 확인했다. 임의의 비정상 장치 ID를 만든 재현이 아니다.
- 독립 재현: 실제 Python `adapters()`에 정상 PowerShell JSON 형태의 행을 주입하고 실제 `_adapter()`의 생성 문자열을 검사했다. **중괄호 없는 소문자·대문자 대조군 2건은 통과**, 중괄호 포함 입력은 동일 UUID임을 확인한 뒤에도 생성된 문자열 조건에서 선택되지 않았다.
- 검증 한계: 이 재현은 현재의 단일 PowerShell 문자열 비교 조건을 제한적으로 모델링했다. 실제 Windows PowerShell·Get-NetAdapter·사용자 PC의 GUID 원문을 실행으로 확인한 것은 아니다. 모델은 생성 조건이 바뀌면 명시적으로 실패하도록 하여 범용 PowerShell 평가기로 오해하지 않도록 했다. 원인 코드 계약은 확인했지만 **사용자 PC의 같은 원인 여부는 Highly Likely**로 구분한다.

## 2. Confirmed Bug — 서로 다른 Windows 실패의 원인을 모두 버림

- 심각도: **P2**, 실패 진단과 권한/미지원/장치 부재의 구분 불가.
- 발생 조건: `_ps()`가 실행한 PowerShell이 실패 코드로 종료됨.
- 사용자 영향: 장치 조회 실패, 접근 거부, 명령/모듈/드라이버 오류가 모두 `Windows 설정 명령에 실패했어요. 권한·장치 상태를 확인해 주세요.`로 표시된다. 정상적인 사용자를 관리자 재실행 등 효과 없는 조작으로 유도할 수 있고 개발도 라이브 원인을 추적할 수 없다.
- 기술적 원인: `system/optimization.py:231`은 stdout/stderr를 PIPE로 받지만 233행에서 returncode만 분기한 뒤 반환 코드·stderr를 기록하거나 보존하지 않고 일반 OSError로 대체한다. 호출부는 그 일반 문자열을 상태에 표시할 뿐이다.
- 독립 재현: 실제 `_ps()`를 실행하되 Windows 실행 경계만 대체했다. `(returncode=1, stderr='adapter unavailable')`와 `(returncode=5, stderr='Access is denied')`를 각각 반환시키자 두 예외는 메시지 동일, errno 없음, 로그 없음으로 같았다. 이 코드는 실제 사용자나 네트워크 정보를 사용하지 않았다. 반환 코드 5는 오류 차이를 검증하기 위한 합성 값이지 실제 PowerShell이 Win32 코드를 그대로 반환한다는 주장이 아니다.
- 검증 결과: 다른 실패에 다른 진단 근거가 남아야 한다는 독립 assertion이 실패했다. 실제 PC의 상세 오류도 현재 소스에서는 보존되지 않으므로 앱 로그가 반드시 답을 갖고 있다고 안내하지 않는다.

## 4. 개발 세션 전달

1. `_adapter()`에서 양쪽 GUID를 **같은 구조적 GUID 형식**으로 검증·정규화해 비교한다. 표시 이름으로 임시 매칭하거나 임의의 첫 번째 장치를 선택하지 않는다. 잘못된 값·없음·둘 이상 일치·장치 교체에서는 안전하게 실패한다.
2. 목록 조회 → 저장된 GUID → 읽기/적용 → 재연결 → 원복의 전체 경로에 같은 식별 규칙을 사용한다. 중괄호 유무·대소문자·복수 장치·선택 장치 부재를 테스트한다. UUID 기준 기존 복구 기록의 호환성을 유지하고 기록을 삭제해 해결하지 않는다.
3. 네트워크 준비/조회/쓰기/확인/재연결/원복의 **단계·항목·실패 종류·반환 코드와 안전한 진단 근거**를 남긴다. stderr 인코딩을 처리하고 원문을 무제한 출력하지 않는다. URL/토큰/사용자 경로·개인 네트워크 식별 정보는 필요한 최소 범위로 제한·마스킹한다. 알려진 권한 부족과 장치 부재·미지원·일반 명령 실패를 구분한다.
4. 일부 실패를 전체 성공으로 표시하지 않는다. 전역 autotuning이 이미 normal인지, 적용됐는지, 실패했는지도 별도로 확인할 수 있게 한다. 관리자 권한 요구는 필요한 작업에만 안내하며 전체 앱/자동실행에 무조건 관리자 권한을 강제하는 것으로 덮지 않는다.
5. 게임 시작/접근 해제/중단 시 변경·재연결 보류와 CPU 독립 처리, 원본/부분 적용/미복구 기록 보존의 기존 수정은 유지한다. UI 에러를 숨기거나 실패 테스트를 약화하지 않는다.
6. 수정·회귀 후 푸시하고 후속 독립 QA에서 재현을 다시 확인한다. 실제 Windows의 읽기 전용 장치 조회를 포함한 검증을 추가하되 CI에서 실제 어댑터를 변경/재시작하지 않는다. 네트워크 적용·복구 자체는 명시적으로 승인한 실사용 조건에서 별도 검증한다.

사용자에게 당장 필요한 조치는 현재 세션의 `중단 · CPU 원복` 외에 없다. 원복 대기가 있으면 앱이 제공하는 명시적 복구 절차로 보존하며 기록 삭제·레지스트리 수동 편집·권한 재실행 반복을 요구하지 않는다. 이번 제보가 해결되기 전에는 네트워크 알파가 정상이라고 안내하지 않는다.
