# 배포 검사 범위 축소

## 사용자 요구와 원인

사용자는 앞선 15분 이하 간소화 요청이 실제 배포 검사 수 축소로 이어지지 않은 점을
지적했고, 다운로드용 exe의 검증/게시 목표를 5분으로 정했다. 전체 검사를 매 배포에
강제하지 않고 개발 중 관련 기능/공통 구조를 검증하며, 배포에는 이번 변경 관련 검사와
최소 기동/빌드 확인만 둔다. 별도 전체 검사를 매번 먼저 요구하는 방식도 금지한다.

기존 배포 경로는 전체 Linux 회귀 → Windows 최소 기동 → exe 빌드를 직렬 실행했다.
로컬 전체 회귀 기록은 2,579개 사례/501.81초였고, JUnit 사례 시간 합계는 990.56초였다.
이 기록은 최종 규칙 보완 전 1 failed가 포함된 개발 실행이며 실제 Actions 시간으로
대신하지 않는다. 적어도 5분 목표에 전체 8분 회귀를 필수로 둔 설계는 맞지 않았다.

## 실제 변경

- `packaging/release_checks.json`에 버전별 관련 검사 파일을 명시한다. 현재 0.10.1의 변경은
  설정 ZIP/비동기 내보내기와 최적화·네트워크·FPS/UI이므로 관련 6개 파일의 155개 사례를 선택했다.
  검사 파일이나 assertion을 없애지 않고 배포 시 실행 범위를 2,580개에서 155개로 줄였다.
- `scripts.run_release_checks`는 명시 목록만 기존 감독기로 실행한다. 버전 불일치·빈 목록·중복·
  없는 파일·경로 이탈·네이티브 파일은 실패한다. 오류를 전체 검사나 검사 생략으로 대체하지 않는다.
  개발자가 릴리즈 노트/버전과 함께 목록을 관리하며 사용자에게 검사 선택 입력을 추가하지 않는다.
- 배포 기능 검사 사례/무진행 제한은 60초, 전체 150초, 단계 3분/잡 5분이다. 상한에서
  실패하는 정책이지 5분 전체 배포를 보장하기 위한 성공 처리나 검사 누락이 아니다.
- 전체 개발 회귀는 별도 수동 `regression.yml`로 보존했다. 배포 workflow의 의존성이 아니며,
  게시 완료 이벤트에도 연결하지 않는다. 일반 푸시에 무거운 검사를 자동 실행하지 않는다.
- Windows 최소 창 기동·종료, 깨끗한 소스 검사, exe 빌드, 버전·출처·해시·TTL·사용자 승인과
  동일 exe 승격은 유지한다. `unit-results.xml`은 이제 이번 기능 검사 결과를 의미한다.
- 검증 프로필을 `release-features-windows-smoke-v2`로 바꾸고 필수 실제 단계 이름도 맞췄다.
  예전 전체 회귀 후보를 새 프로필로 소급 승인하지 않는다. 앱 코드/버전/사용자 노트는 바꾸지 않았다.
- `AGENTS.md`, `CLAUDE.md`, 현재 운영/기획 문서를 갱신해 다른 세션이 전체 필수 정책을
  되살리거나 매 배포 전에 전체 검사를 요구하지 않도록 했다.

## 개발 검증

- 실제 배포 검사 진입점 실행: **155 passed, 14.76초**, 감독 종료 코드 0.
- CI·후보/게시 차단·선택 목록·진단 정리·인코딩 검사: **239 passed, 7.43초**.
- 마지막 통합 표적 검사: **396 passed, 19.97초**, 종료 코드 0, skip 0.
  배포 목록 155개와 위 계약 검사 및 Windows 창의 offscreen 기동/종료 검사를 포함한다.
- 초기 표적 검사에서 shell fixture가 새 필수 환경값 APP_VERSION을 공급하지 않아 2개 실패했다.
  실제 workflow의 환경값을 fixture에도 명시한 뒤 재검사했다. 제한 시간/정리 assertion은 유지했다.
- 실제 Windows/Actions에서 새 정책을 실행하거나 전체 회귀를 다시 실행하지 않았다.
  전체 회귀를 배포 전에 다시 실행해야 한다는 선행 조건도 만들지 않는다.

```bash
PYTHONPATH=src:.:tests QT_QPA_PLATFORM=offscreen .venv/bin/python -m scripts.run_release_checks --version 0.10.1
PYTHONPATH=src:.:tests QT_QPA_PLATFORM=offscreen .venv/bin/python -m pytest tests/test_release_checks.py tests/test_windows_ci.py tests/test_release_candidate.py tests/test_ci_resources.py tests/test_unicode_io_contract.py tests/test_config_bundle.py tests/test_settings_export.py tests/test_optimization.py tests/test_optimization_network.py tests/test_optimization_contract.py tests/test_optimization_ui.py tests/test_startup_smoke.py -n 2 -q --maxfail=3 --tb=short --test-inventory=/tmp/release-policy-final-inventory-20261022.json --junitxml=/tmp/release-policy-final-20261022.xml
```

배포 기능 JUnit은 `/tmp/release-features-0.10.1-20261022.xml`에 보존했다.

## 아직 입증하지 않은 것과 다음 행동

로컬에서 검사 범위를 줄인 사실과 실제 전체 배포 5분 달성은 다르다. Windows exe 빌드 시간,
러너 대기·체크아웃·전송·게시를 포함한 총시간은 새 정책의 실제 실행으로 측정해야 한다.
측정 전 5분 달성이나 빌드 자체가 15분 걸린다고 주장하지 않는다. 빌드 옵션/캐시는 이번에
근거 없이 변경하지 않았다. 과거 러너 정체의 근본 원인 해결도 이 변경으로 주장하지 않는다.

사용자가 시작한 `39715832248`은 SHA `07850f0f`의 이전 전체 회귀 정책이다. 새 푸시로 해당
실행의 검사 목록이 바뀌지 않는다. 이 기록 작성 시 API의 회귀 상태만 in_progress였으며,
진행 중 로그 다운로드는 BlobNotFound였다. 정상 진행/정체 여부를 상태 문자만으로 단정하지 않는다.

이 세션은 수정·검증·푸시를 완료하고 추가 Actions 실행은 요청하지 않는다. 후속 QA 대상은
변경 기능 목록이 이번 노트와 맞는지, 전체 회귀가 배포 경로에서 빠졌는지, 기존 게시 차단 조건이
남아 있는지다. 이후 사용자가 새 실행을 결정해 URL을 주면 단계별 소요 시간을 확인한다.
사용자 대신 Actions/태그/Release를 실행하거나 응답 뒤 감시가 계속된다고 약속하지 않는다.
