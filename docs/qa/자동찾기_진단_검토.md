## AUTO-DIAG-01 / Confirmed Bug / P2

**처음부터 필수 템플릿이 없는 실행을 ZIP 재실행 완료로 표시한다.**

- 발생 조건: 버프 앵커 로드가 실패해 `anchor_template()`이 `None`을 반환하거나,
  보스/디버프 숫자 템플릿이 비어 있는 상태에서 자동찾기 -> ZIP 저장 -> 재실행을 수행함.
- 사용자 영향: 검출 준비 실패를 정상적인 미검출 재현으로 해석할 수 있다. 템플릿 누락을
  해결하기 전에 검출 점수나 화면 조건을 분석하게 만들 수 있다.
- 기술적 원인: `detector_assets()`가 빈 dict를 반환하면 기록의 `asset_names=[]`가 된다.
  `replay()`는 이 이름 목록에 있는 이미지의 누락만 검사하므로 검사를 통과한다.
  검출 반환값과 기록 값이 모두 `None`이면 `replayed=true`, `matches_recorded=true`가 된다.
- 요구사항: [자동찾기 진단 문서](../자동찾기_진단.md)의 재실행 절은 입력 또는 필수
  템플릿이 없으면 `replayed:false`를 반환하도록 정의한다.
- 재현 방법: 실제 화면 `tests/data/스크린샷 2026-10-09 190901.png`가 정상 템플릿으로
  검출되는지 먼저 확인한다. 동일 화면에서 앵커 로드를 `None`으로 또는 숫자 템플릿을
  `{}`로 구성한다. 실제 기록 -> 저장 -> ZIP 내보내기 -> `replay()`를 실행한다.
- 검증 결과: 버프·보스·디버프 세 경우에서 모두 재현했다. 정상 템플릿에서는 결과가
  있었고, 누락 상태에서는 `asset_names=[]`, `replayed=true`, `matches_recorded=true`였다.
  버프 trace는 `missing_anchor_template`, 보스/디버프는 실제 보스 후보의
  `percent_unreadable`을 표시했다.
- 코드 위치: [autofind_replay.py](../../src/mabinogi_addon/autofind_replay.py)의
  `detector_assets()`(19행), `replay()`의 누락 검사(84행)와 결과 반환(91행),
  [autofind_diagnostics.py](../../src/mabinogi_addon/autofind_diagnostics.py)의
  템플릿 수집 및 이름 기록(346행).
- 수정 방향: 기능별 필수 템플릿을 기록과 재실행 경로에서 별도로 검증한다. 실제로
  로드한 템플릿 이름만으로 필수 입력 충족 여부를 판단하지 않는다. 누락은 검출 준비/
  템플릿 오류로 기록하고, 재실행 불가 및 원인을 반환한다.
- 회귀 기준: 처음부터 누락된 템플릿과 정상 로드 후 PNG 저장에 실패한 템플릿을 구분해 검증한다.

Windows PowerShell에서 저장소 루트 기준 재현/재검증 명령:

```powershell
uv sync --group build --group dev
$env:QT_QPA_PLATFORM = "offscreen"
$env:PYTHONUTF8 = "0"

uv run pytest -q
```

`PYTHONUTF8=0`만으로 한국어 Windows의 코드페이지가 CP1252로 바뀌지는 않는다. 두 텍스트
실패의 동일 조건 재현은 기본 인코딩이 CP1252인 Windows CI/환경에서 확인한다.
수정 후에는 한글 Windows에서도 정상 동작해야 한다. 위 명령은 프로세스가 참조할 현재
PowerShell 환경에만 적용되며 사용자 설정 파일을 변경하지 않는다.

기존 `v0.4.63` 태그는 이미 존재한다. 이 QA 문서 갱신만으로 실패한 릴리즈가 다시 실행되거나
배포되지 않는다. 태그를 임의로 삭제/이동하지 않으며, 코드 수정과 Windows 검증 후 사용자의
명시적 릴리즈 요청에 맞춰 새 태그·릴리즈 노트 버전·대상 소스를 다시 확인한다.

  도달하지 못한다. 개발 실패 주입은 `builtins.open`, `io.open`, 네이티브 이미지 경로만
  제한하며 `sys.stdout` 인코딩은 바꾸지 않아 이 문제를 잡지 못했다.
- 재현 방법: 기존 테스트를 바꾸지 않고 아래 스크립트에서 콘솔 인코딩만 CP1252로 지정한다.
- 검증 결과: Windows의 두 실패와 같은 위치·예외가 Linux CP1252 콘솔에서도 재현됐다.
  동일 소스에서 UTF-8 콘솔만 지정하면 두 테스트와 회귀 assertion이 통과했다.
  대조 실행에서 1차 오탐 1개, 2·3차 오탐 0개, 보스 인식 9/9가 확인됐다.
- 코드 위치: `tests/test_debuff_bench.py:145,146,188,189`;
  실패 주입의 범위: `scripts/qa_windows_io_probe/sitecustomize.py`.
- 수정 방향: 테스트의 출력 경계가 CP1252에서도 안전하게 동작하도록 하거나 CI의
  stdout/stderr를 명시적 UTF-8 계약으로 설정한다. 후자라면 파일의 기본 인코딩과는 별개인
  `PYTHONIOENCODING`을 사용하고, 기존 CP1252 파일 I/O 독립 검증은 유지한다.
  `capsys` 우회 필요성도 검토한다. 테스트를 skip하거나 검출 assertion을 삭제하지 않는다.
- 완료 기준: 두 콘솔 조건의 재현/대조와 실제 Windows 전체 게이트·exe 빌드를 다시 확인한다.
  아직 수정하거나 배포하지 않았으며 기존 태그도 삭제·이동하지 않았다.

[콘솔 재현 스크립트](../../scripts/qa_bench_console_encoding.py)는 저장소 루트를 기준으로
기존 두 테스트를 별도 프로세스에서 실행하고 테스트 종료 코드를 그대로 반환한다.
호출한 현재 디렉터리에 의존하지 않으며 사용자 설정 파일이나 제품 구현을 변경하지 않는다.
환경 변수는 자식 프로세스에만 적용하며 일반 pytest 자동 수집에는 포함되지 않는다.

Windows PowerShell/Linux 공통 재현 명령 (QA 대상 `0a300a3`의 결과는 2 failed):

```bash
uv run python scripts/qa_bench_console_encoding.py
```

양성 대조 (QA 대상 `0a300a3`의 결과는 2 passed):

```bash
uv run python scripts/qa_bench_console_encoding.py --encoding utf-8
```

입력 읽기 수정은 확인됐지만 **콘솔 출력 수정 전에는 전체 Windows 통과·배포 준비 완료로
보고하지 않는다.** 실패 원인은 사용자 조작이 아니라 테스트의 출력 인코딩 의존성이다.

## 콘솔 출력 결함 개발 수정

2026-10-14 최신 QA `36e2356`을 받은 개발 세션에서 CI-WIN-04를 재현하고 수정했다.
수정 전 기존 재현 스크립트는 **2 failed in 2.94s**로 두 `UnicodeEncodeError`를 확인했다.
테스트 결과 출력 직후의 검출 assertion에 도달하지 못하는 실행 경로도 일치했다.

- `tests/test_debuff_bench.py`의 `_print_report()`는 현재 stdout 인코딩으로 표현할 수 없는
  문자만 `backslashreplace`로 이스케이프한다. UTF-8 콘솔에서는 원래 한글을 그대로 출력한다.
  실제 콘솔의 인코딩/오류 정책이나 파일 I/O, 제품·CI 설정은 변경하지 않는다.
- `capsys.disabled()`는 벤치마크 수치를 성공 실행에서도 표시하기 위해 유지했다.
  검출 계산·입력·임계값과 오탐/재현율 assertion은 변경하거나 건너뛰지 않았다.
- CP1252/strict와 UTF-8/strict `TextIOWrapper`를 사용한 출력 바이트 회귀 2개를 추가했다.
  한글 템플릿 이름과 숫자 결과가 CP1252에서는 복원 가능한 이스케이프로 남고,
  UTF-8에서는 원문 그대로 저장되는지 확인한다.

기존 재현 스크립트는 수정 없이 CP1252에서 **2 passed in 3.02s**로 통과했다.
UTF-8 대조도 **2 passed in 3.22s**다. 이 Linux 콘솔 재현은 실제
Windows 실행이나 독립 QA 판정을 대신하지 않는다.

콘솔·파일 실패 조건을 함께 적용한 첫 전체 실행은 **2 failed, 524 passed in 100.41s**였다.
실패한 생명주기 두 시나리오의 자식은 정상 종료했으나, CP1252 stderr의 `0x97`을
Linux 부모의 UTF-8 기본값으로 디코딩하면서 테스트가 실패했다. 이는 실제 Windows에서
새로 확인된 앱 결함이 아니라 추가로 구성한 교차 인코딩 조건의 테스트 수집 경계 문제다.
`tests/test_lifecycle.py`는 로그를 바이트로 수집하게 보완했다. 원본 로그와 종료 코드를
보존하며 종료/리소스 해제/결함 주입 assertion은 그대로 유지한다.

최종 수정본은 CP1252 콘솔/strict·CP1252 기본 파일 I/O·비 ASCII 네이티브 이미지 경로

건너뛴 테스트는 없으며 경고는 기존 mss/Qt API deprecation이다. 이 수를 이전 실행이나

### 아티팩트 저장 공간 실패

GitHub Actions 로그는 다음 오류를 반환했다.

```text
Failed to CreateArtifact: Artifact storage quota has been hit.
Unable to upload any new artifacts. Usage is recalculated every 6-12 hours.
```

이는 코드 테스트 실패나 PyInstaller 실패가 아니라 빌드 완료 후 산출물 전달을 막는
외부 저장 공간 제한이다. 전체 run의 `failure`만 보고 CI-WIN-04가 남아 있다고 판단하지 않는다.
exe를 내려받아 실행한 것은 아니므로 다운로드와 Windows 실제 실행 확인은 아직 하지 못했다.
기존 아티팩트 삭제·보존 정책/요금제 변경은 별도 판단 사항이며 이 QA에서 임의로 삭제하지 않았다.

현재 워크플로의 아티팩트 업로드는 `workflow_dispatch`에만 적용된다. 태그 push 릴리즈는
이를 건너뛰고 exe를 Release 자산으로 첨부하므로 이 Actions quota와 업로드 경로가 다르다.
다만 이번 결과로 정식 릴리즈 게시·자동 업데이트까지 성공했다고 주장하지 않는다.

### 태그 없는 수동 빌드의 앱 동작

`main`을 선택한 수동 실행은 내부 버전과 exe 파일 속성에 `0.0.0`을 주입하고 창 제목에는
`개발`로 표시한다. `updater.can_update()`가 false이므로 앱의 자동 업데이트 확인을 하지
않으며 시작 시 업데이트 노트도 생략한다. 진단 메타데이터의 앱 버전도 `0.0.0`이므로
자료 공유 시 이 빌드의 대상 소스/Actions 실행 번호를 함께 기록한다.
소스 분기를 직접 호출해 버전 표시와 업데이트/노트 조기 반환도 확인했다. frozen 여부를
대체한 로컬 검사이며 생성된 Windows exe를 실행한 것으로 보고하지 않는다.

트래커·자동찾기 자체를 끄는 개발 버전 분기는 없지만, frozen exe의 설정/사용자 데이터는
정식 exe와 같은 `%LOCALAPPDATA%/StarlineMabinogiAddon`을 사용한다. 테스트 설정 변경도
그 폴더에 남으며 별도의 데이터 샌드박스라고 판단하지 않는다.

관련 소스: `.github/workflows/release.yml`의 `Set version from tag`,
`packaging/make_version_info.py:18`, `src/mabinogi_addon/version.py:12`,
`src/mabinogi_addon/system/updater.py:67`,
`src/mabinogi_addon/ui/main_window.py:591,692`, `src/mabinogi_addon/paths.py:43`.

QA 완료는 태그/배포 실행 승인이 아니다. 앱·제품 테스트·CI 설정은 이 QA에서 바꾸지 않았고,
기존 태그를 삭제·이동하거나 새 Release를 만들지 않았다.
