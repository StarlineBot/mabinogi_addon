# 도르카 게임 첫 시작 판독 지연 독립 QA

- 대상 제품/지침: `c267a634af8ccc98af52db9cd2430fba3aff168b` 현재 소스. 커밋 이력은 조회하지 않았다.
- 제보: 게임 첫 시작에는 도르카를 읽지 못하다 수분 뒤 정상화. 게임 숫자가 이미 보였고,
  회복해서 5가 되어도 앱은 `--/15`였다. 앱/게임 실행 선후와 첫 실패 프레임은 미확인이다.
- 앱 구현/기존 테스트/자산은 변경하지 않았다. Windows 유료 CI 실행도 요청하지 않았다.

## P2 / Highly Likely Bug: 초기 실패 후 정상 화면 복귀를 장시간 확인하지 않음

- 발생 조건: 저장 영역의 첫 장식 검증 실패 → 게임 전체 탐색도 실패 → 해당 작업 비용에
  따른 대기 중 UI가 같은 저장 영역에 정상 표시됨. 일시적 로딩/캡처 실패는 구성 가능한 조건이지,
  제보 당시에 발생했다고 확인한 사실은 아니다.
- 사용자 영향: 실제 숫자 5가 판독 가능한데도 오버레이가 수십 초~수분 `--/15`에 머물 수 있다.
  정상적인 게임 시작/숫자 회복을 사용자 잘못이나 재등록 누락으로 취급하지 않는다.
- 기술적 원인: `dorcha_tab.py:264`의 초기 문맥 검증이 실패하면 `_tracking_lost=True`가 된다.
  `:254`, `:269`에서 이후 저장 영역 조회/캡처를 건너뛰고 전체 탐색만 기다린다.
  `:337`은 다음 탐색 시각까지 시작을 차단하며, `:370`은 완료 뒤 `elapsed * 20`을 추가 대기한다.
  `dorcha_search.py:20`의 elapsed는 CPU 시간이 아니라 스케줄링 지연을 포함한 벽시계 시간이다.
- 검증으로 확정한 것은 **조건부 지연 실행 경로**다. 실제 제보의 첫 실패 원인/실제 탐색 시간은
  확인하지 못했으므로 라이브 현상의 원인이 확정됐다고 분류하지 않는다.

## 재현 결과

`docs/qa/assets/dorcha_startup_20261018/probe.py`는 실제 Qt 컨트롤러/워커/판독기를 실행한다.
게임 활성/화면 캡처/시계는 대체하며, 탐색 소요만 지정한다. 검출/숫자 판독 결과는 조작하지 않는다.

1. 앱을 켠 상태에서 게임 비활성 → 활성, UI 없는 프레임으로 첫 검증/탐색을 실패시킨다.
2. 기존 원본 `스크린샷 2026-10-16 211352.png`의 장식과 숫자 5를 저장 위치에 배치한다.
3. 실제 판독기 결과 5, 전체 검출 좌표, 작은 영역 문맥 검증 성공을 대조한다.
4. 대기 중 여러 시점의 tick에서 **추가 캡처/워커 없이 `--/15` 유지**를 확인한다.
5. 대기 직후 현재 화면으로 재탐색하면 5로 회복하고 사용자 설정은 쓰지 않는 것을 확인한다.

## 개발 전달

- 전체 화면 재탐색 간격을 무조건 줄이지 말고, 초기 실패 후 저장 위치의 작은 문맥을
  낮은 빈도로 재검증하거나 게임 준비 전환 때 제한적으로 확인하는 복구 경로를 검토한다.
- 숫자만 보인다고 옛 좌표를 신뢰하는 수정은 금지한다. 장식+현재 숫자+동일 HWND/PID/창 경계,
  오래된 결과 폐기, 워커 하나/큐 없음, 캡처 크기/부하 제한과 설정 불변성을 유지해야 한다.
- 제보의 첫 실패를 좁히려면 실패 이유, 탐색 소요/다음 재시도 시각, 저장 영역 문맥 결과를
  진단에 남기는 것이 유용하다. 숫자 5가 항상 오독된다는 근거는 현재 원본/검사에 없다.
- 실제 Windows 첫 시작, 당시 첫 캡처/게임 프레임, 장시간 리소스와 포커스는 미검증이다.
  최초 실패 원인 확정과 개선 후 라이브 확인은 남아 있으며, 이번 QA로 해결됐다고 보고하지 않는다.
