## 추가 제보: Alt+Tab 후 판독 상실

- 사용자가 Alt+Tab 후 게임으로 돌아오면 도르카를 읽지 못하는 조건을 추가 확인했다.
  정상적인 창 전환은 재현 조건이지 사용자 과실이 아니다.
- 실제 컨트롤러에 같은 원본/같은 HWND·PID·경계/같은 숫자 좌표를 유지한 채
  게임 활성 → 비활성(앱도 비활성) → 게임 활성 순서를 구성했다.
- 현재 실행에서 직접 승인한 영역과 이미 추적한 영역의 두 출발 상태 모두 먼저 7을
  정상 표시했다. 비활성 tick 뒤 `_live_box`/`_live_target`이 None, `_tracking_lost`가 True가 된다.
  복귀 후 전체 워커 완료와 다음 2초 국소 검사까지 실행해도 `--/15`이고 원본 ROI는 여전히 7이다.
- `ui/dorcha_tab.py`의 `_active()`는 게임 또는 보이는 해당 앱 화면의 활성만 허용한다.
  `_tick()`의 비활성 분기는 `_hide()` → `_invalidate_search()`로 이어져 이전 추적 위치와
  승인 대상 정보를 비운다. 복귀 때는 작은 숫자를 곧장 읽는 대신 국소 장식 재검증/전체 탐색을
  거쳐야 하므로, 같은 정상 숫자라도 이미 추적 중일 때와 복귀 후 결과가 달라진다.
- 기존 원본 장식/15 대조군은 같은 활성 전환 뒤 정상 회복했다. 모든 화면/모든 Alt+Tab에서
  실패하는 것으로 일반화하지 않는다. 정상 장식 검증에 성공하느냐에 따라 갈리는 조건부 결함이다.
- 확장 재현 결과 **4 failed, 2 passed (10.56초)**. 기존 전체/국소 미검출 두 실패에
  승인/추적 출발의 Alt+Tab 복귀 두 실패가 추가됐다. 숫자 7 판독과 기존 장식/15 복귀는 통과했다.
- 실제 Windows Alt+Tab 키 입력/전체 화면 전환/게임 캡처 API를 실행한 것은 아니다.
  명시적으로 대체한 게임 활성/캡처 경계에서 실제 컨트롤러와 워커 실행 순서를 확인했다.
- 개발 시 정상 비활성의 표시 숨김과 추적 근거 무효화를 구분해 검토하되, 보관 좌표를
  무조건 신뢰하거나 옛 숫자를 그대로 표시하면 안 된다. 복귀 중 HWND/PID/창 경계/게임 UI가
  바뀐 대조군과 현재 픽셀 검증을 유지하면서 장식 미검출 및 재개 경로를 함께 보완해야 한다.
