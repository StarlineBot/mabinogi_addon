# 마우스 하이라이트 기획 호환성 검토

- 검토일: 2026-10-16.
- 소스/기획 기준: `a4f49d88a8a25a0082a7e43321306cd944b5f9f7`.
- 대상: `docs/mouse-highlight-spec.md`, 현재 트래커·캡처·창 판정·일시정지 구현.
- 이전 QA 공유본과 비교한 변경은 기획 문서 2개뿐이다. 제품 구현 변경은 없고 커밋 이력은 읽지 않았다.
- 사용자 실사용 사실: 현재 앱과 YoloMouse를 이미 함께 사용 중이다. 이를 충돌 사례로 취급하지 않는다.
- 이 문서는 개발 전 검토다. 새 기능의 실행 QA 통과나 YoloMouse 전체 버전의 호환 보장이 아니다.

## 결론

기획은 구현 가능하며 기존 기능과 필연적으로 충돌하는 요구사항은 발견하지 못했다.
커서 교체·입력 생성·후킹·게임 캡처 추가 없이 독립적인 클릭 통과 표시로 범위를 유지하는 방향은 적절하다.
다만 기존 공용 코드를 그대로 재사용하면 요구사항을 만족하지 못하는 지점이 있다.
아래 조건을 작은 Windows 시제품으로 확인한 뒤 본 구현에 들어가는 것을 권고한다.
기본값이나 사용자가 승인한 표시 정책을 다시 결정하라는 뜻은 아니다.

## Potential Risk

### MH-REVIEW-01: 판독 입력 오염

- 우선도: P1, 발생하면 기존 트래커 정확도에 영향. 현재 발생이 확인된 버그는 아니다.
- 조건: 하이라이트가 라이브 캡처에 합성되고 포인터가 버프/디버프 아이콘, 투아림 숫자,
  보스 HP 또는 자원바 위에 머문다. 직경 최대·내부 불투명도 최대 조합도 허용된 정상 사용이다.
- 영향: 아이콘 누락/오탐, 숫자 오독, 알림 누락/반복, 화면 복제에 원이 포함될 가능성.
- 근거: `capture/shared_live.py:201`은 dxcam 전체 프레임 또는 mss 폴백을 잘라 사용한다.
  `system/clickthrough.py:14`는 입력 통과만 설정한다. 현재 소스에는 창 캡처 제외 설정이 없다.
  클릭 통과나 비활성 창이라는 사실은 캡처 제외를 의미하지 않는다.
- 확인: Windows 실제 dxcam 및 mss 폴백에서 원 ON/OFF·대상 위 겹침 비교. 별도 mss를 쓰는
  자동찾기·진단과 캡처 기반 미러도 포함한다. 캡처 제외 API는 후보이며 성공 반환만으로
  효과를 보증하지 않는다. Windows/백엔드에 따라 검은 영역이 남는지도 확인한다.
- 승인 조건: 기존 트래커에 새 오인식을 만들지 않는다는 MH-18을 실행으로 증명한다.
  실패 시 사용자에게 포인터를 치우라고 요구하거나 기존 매칭 임계값을 완화해 숨기지 않는다.
  예외 처리나 미지원 환경 정책이 필요하면 사양 변경 승인을 받는다.

### MH-REVIEW-02: 기존 활성 판정은 실패 시 표시 허용

- 우선도: P2, 게임 밖 노출·잠금 복귀 잔상 가능성.
- 근거: `system/window_watcher.py:161`의 `_classify`는 조회 예외 시 `game`을 반환한다.
  `create_window_watcher`도 생성 실패 시 `AlwaysActiveWatcher`를 돌려준다.
  `is_active()`는 자기 앱 활성도 허용하므로 새 기능의 엄격한 표시 조건에 맞지 않는다.
- 실행: `WindowsWatcher.__new__`로 생성하고 `_foreground`에 OSError를 주입했을 때 실제
  `is_game_active()` 결과는 **True**였다. 현재 기존 기능의 호환 정책을 확인한 것이며
  아직 구현되지 않은 하이라이트에서 문제가 발생했다고 주장하지 않는다.
- 개발 조건: 새 표시에는 조회 성공 여부를 보존하는 엄격한 판정을 적용한다.
  기존 모든 트래커의 실패 정책을 일괄 변경하는 방식으로 해결하지 않는다.
  실제 포그라운드 HWND, 현재 등록 게임, 최소화/잠금/입력 데스크톱과 클라이언트 영역을 확인한다.
  조회 실패·로그아웃·일시정지에서 숨김을 검사한다.

### MH-REVIEW-03: YoloMouse 커서 상태와 새 원의 표시 순서

- 우선도: P2, 새 기능만 표시되지 않거나 외부 커서 가독성이 나빠질 가능성.
- 현재 동시 사용은 이미 정상 실사용 근거다. YoloMouse를 제거하거나 끄는 것을 전제하지 않는다.
- 외부 앱이 커서를 어떤 방식으로 표시하는지는 이 환경에서 확인하지 않았다. Windows 기본
  포인터가 숨김으로 보고되어도 외부 프로그램의 커서가 보이는 구성일 수 있어, 단순 숨김 플래그만
  적용하면 원만 사라질 가능성이 있다. 실제 사용자의 YoloMouse 구성으로 검증해야 한다.
- 일반 topmost 원과 외부 커서의 실제 표시 순서는 미검증이다. OS 커서와 외부 오버레이를
  같은 것으로 가정하지 않고 불투명 원·큰 직경·테두리까지 커서 및 클릭 기준점 가독성을 확인한다.
- 검증: YoloMouse OFF/ON, 새 기능 OFF/ON의 4조합으로 좌표·커서 숨김/복귀·클릭/드래그·
  카메라 조작·포커스와 캡처를 비교한다. 기존 앱+YoloMouse 조합의 동작은 유지해야 한다.
  새 기능 OFF는 원래 동작이며 기존 커서/Windows/YoloMouse 설정을 복원 명목으로 변경하지 않는다.
- 사양의 '동시 사용 보장 안 함'은 새 기능의 미검증을 뜻하도록 해석해야 한다.
  기존 정상 동시 사용을 미지원 처리하거나 확인된 구현 결함의 면책으로 사용해서는 안 된다.

### MH-REVIEW-04: 좌표와 게임창 선택

- 우선도: P2, 잘못된 위치나 다른 모니터에 원 표시 가능성.
- `ui/dpi.py:20`은 주 모니터 배율이고, `dwm_thumbnail.window_rect`는 외곽 창 사각형이다.
  혼합 DPI 포인터의 물리 좌표와 Qt 논리 좌표 변환이나 클라이언트 경계 판정에 그대로 사용할 수 없다.
  `find_game_window`는 같은 exe의 첫 번째 보이는 창을 반환하므로 포그라운드 창과 무조건 같지 않다.
- 개발 조건: 포인터가 놓인 화면 기준 변환 및 현재 게임 클라이언트 영역 판정. 음수 좌표,
  100/150/200% 간 이동, 제목 표시줄/테두리, HWND 재생성·빠른 재실행과 모니터 해제를 검사한다.
  새 기능 때문에 기존 트래커의 좌표 저장 규칙을 전역 변경하지 않는다.

### MH-REVIEW-05: 주기 작업 및 캡처 중 재등장

- 우선도: P2, 주 스레드 지연·자동찾기 오염·종료 후 잔상 가능성.
- `main_window.py:1172`의 상태 갱신은 700ms다. 여기에 포인터 표시를 연결하면 추적이 거칠며,
  반대로 기존 전체 상태 갱신이나 프로세스 조회를 포인터 주기로 가속하면 다른 기능 부하가 증가한다.
- `ui/screen_grab.py:120`은 최상위 창을 숨기고 `processEvents()` 후 캡처하며 마지막에 복원한다.
  새 표시 타이머가 숨김 중 원을 다시 띄우거나 복원이 정지/로그아웃 조건을 무시하지 않게 해야 한다.
- 개발 조건: 포인터 표시 갱신을 기존 캡처·판독과 분리하고, 새 화면 캡처나 고빈도 설정 파일 IO를
  만들지 않는다. 자동찾기·진단 중 숨김은 관련 캡처 전체에서 보장한다. 표시 재개는 조건을 다시 확인한다.
  전체 정지 연결만 추가하고 기존 투아림·메모의 예외 정책은 유지한다.
  설정 변경/게임 전환마다 창·타이머를 새로 누적 생성하지 않으며 실제 종료에서 중지·해제한다.
- 검증: UI 스레드에 부하가 있는 상태에서 추적 지연·기존 알림 지연·CPU 측정, 정지/복귀/로그아웃/
  트레이/자동찾기/종료 반복 후 자원 증가 검사. 저빈도 대기 또는 이벤트 복귀 경로를 확보한다.
  성능 기준은 사양대로 측정 후 승인받으며 현재 수치 통과를 주장하지 않는다.

## 개발 전달 요약

1. 입력을 건드리지 않는 작은 원 표시 시제품으로 캡처 오염·클릭 통과·추적 지연부터 검증한다.
2. 사용자 현재 YoloMouse 구성도 정상적인 검증 환경에 포함한다. 충돌이 이미 있다는 전제로 시작하지 않는다.
3. 새 기능의 엄격한 활성 판정과 DPI 변환은 기존 트래커의 호환 동작을 바꾸지 않는 범위로 구현한다.
4. 자동찾기/진단의 숨김과 전체 정지/로그아웃/실제 종료를 생명주기 검증에 포함한다.
5. 승인된 사양은 임의 변경하지 않는다. 시제품이 요구사항을 충족하지 못하면 제약과 변경안을 먼저 보고한다.

## 검증 한계

실제 실행은 기존 활성 판정의 예외 주입 1건이다. 나머지는 소스 기반 개발 전 위험 분석으로,
Confirmed Bug나 새 기능의 실측 결과로 분류하지 않았다. 새 기능이 구현되지 않아 Windows·YoloMouse·
게임 동시 실행 및 캡처 합성·입력 통과·자원 실측은 하지 않았다. 기존 제품의 Windows CI를
재요청하지 않으며, 이번 문서 검토만으로 새 릴리즈 명령이나 구현 완료 판정을 내리지 않는다.
