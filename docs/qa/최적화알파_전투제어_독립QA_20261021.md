# 최적화 알파·전투 제어 독립 QA

- 날짜: 2026-10-21 (한국 시간)
- 검증 소스: `7faf18a69d55d2fc2f3594235ec5ab901d2a89ba`
- 비교 기준: 직전 QA 및 v0.9.1 배포 소스 `951498399b66476512870b3acb11b7a08dac751b`의 현재 파일 트리. 커밋 이력·메시지는 조회하지 않았다.
- 결론: **확정 결함 2건으로 현재 후보 배포 보류.** 제품 코드·기존 테스트·공개 노트·워크플로는 수정하지 않았다.
- 이번 제품 범위: 제작자 최적화/FPS 알파, 개별 자동찾기 일반 공개, 전투 보조 표시·소리 일시정지, 안내·도움말 정리, 구형 QA 가림 모델 식별자 충돌 수정.
- 디스코드 배포 공지는 별개다. `scripts/release_delivery.py`와 `release.yml`은 v0.9.1 배포본과 동일하며, 기존의 오류 상세 미기록·알림 전용 재전송 부재는 이번에 수정되지 않았다. 실제 웹훅 호출은 하지 않았다.

## 1. Confirmed Bug — FPS 실행 모드와 CSV 판독 계약 불일치

- 심각도: **P1**, 새 FPS 기능 사용 불가. 일반 사용자의 기존 트래커 전체가 고장 난다는 뜻은 아니다.
- 조건: 제작자가 포함된 PresentMon으로 FPS 계측을 시작하고 정상 CSV가 들어옴.
- 사용자 영향: 첫 헤더에서 `지원하지 않는 프레임 데이터 형식이에요.`로 실패하며 FPS 수집을 종료한다. 권한·게임 성능·사용자 설정 문제로 판단할 사안이 아니다.
- 원인: `system/presentmon.py:85`의 `arguments()`는 `--v1_metrics --qpc_time`을 지정한다. 포함 버전 2.3.1의 v1 출력은 `msBetweenPresents`와 `QPCTime`을 사용하지만 `optimization/frames.py:39`는 `MsBetweenPresents`와 `TimeInQPC`를 필수로 요구하고 54~55행에서 그 이름으로 읽는다. 두 열 모두 불일치한다.
- 실제 실패 경로: `Collector._read()` → `OptimizationController._line()` → `FrameStream.feed()`의 ValueError → `_failed()` → `stop_frames()`.
- 근거: 포함 EXE 421,312바이트의 SHA256 `364e5d98d4d134bd54dd25c22ed2ca2f4883f8bc3ed6502bee0c151e3436d30c`를 확인했다. UTF-16 문자열에서도 두 CSV 계약이 별개로 존재한다. 고정 버전의 [WriteCsvHeader<FrameMetrics1>](https://github.com/GameTechDev/PresentMon/blob/v2.3.1/PresentMon/CsvOutput.cpp#L139)는 151~153행에서 소문자 `msBetweenPresents`, 171~172행에서 `QPCTime`을 출력하고, 241~242행은 QPC 원시 정수를 기록한다. [기본 모드 헤더](https://github.com/GameTechDev/PresentMon/blob/v2.3.1/PresentMon/CsvOutput.cpp#L286)는 앱 판독기가 요구하는 이름을 출력한다.
- 재현: 아래 독립 스크립트의 `test_pinned_v1_qpc_header_is_accepted`. 고정 도구 소스의 실제 헤더를 앱 판독기에 주입하자 40행에서 즉시 실패했다. 현재 판독기가 기대하는 별도 헤더를 넣은 대조군은 50 FPS 판독에 성공했다.
- 검증 한계: Windows EXE를 실제 게임 대상으로 실행한 것은 아니다. 고정 도구의 소스·바이너리 문자열과 실제 Python 판독 실행으로 계약 불일치를 확인했다.
- 개발 전달: 실제 실행 모드와 파서를 하나의 정확한 CSV 계약으로 맞추고, 해당 모드의 원본 헤더·행을 회귀 자료로 사용한다. 단순히 헤더 검사를 제거하거나 QPC의 절대/상대 시각 의미를 무시하지 않는다. 기존 테스트의 가상 `TimeInQPC,MsBetweenPresents` 입력만으로는 v1 실행 경로를 검증할 수 없다. Windows 테스트도 현재 `--help`만 실행하므로 이 문제를 잡지 못한다.

## 2. Confirmed Bug — 사전 검사 중 게임 시작 시 네트워크 적용을 보류하지 않음

- 심각도: **P2**, 명시적으로 최적화 알파의 네트워크 옵션을 사용할 때 게임 연결 방해 가능.
- 요구사항: `docs/game-optimization-cpu-tcp-rss-alpha-spec.md` 3·6·7절은 게임 실행 중 네트워크 변경을 미루고, 게임 시작/중단/원복 전환을 안전하게 처리하도록 요구한다.
- 조건: 네트워크 옵션을 선택하고 시작 → 최초 게임 확인에서는 미실행 → 프로세스 열거나 RSS 사전 조회 도중 게임 시작 → 네트워크 변경 단계로 진행.
- 사용자 영향: 게임이 이미 실행됐는데 TCP/RSS 설정 적용과 어댑터 재시작이 진행되어 로그인·접속 중 끊길 수 있다. 재시작 명령이 실제 연결을 끊는지는 Windows/장치에 따라 다르지만 실행 중 게임에 재시작을 요청하는 잘못된 순서는 재현됐다.
- 원인: `optimization/engine.py:60`의 게임 상태를 65행 분기에서 재사용한다. 중간의 `processes()`·`governor_running()`·`rss_plan()`·설정 읽기/쓰기 동안 오래될 수 있지만 74~79행의 적용·재연결 직전에는 게임을 다시 확인하지 않는다. 85행의 다음 게임 확인은 재연결 이후다.
- 재현: 독립 스크립트의 `LaunchDuringInspection.processes()`에서 게임을 시작 상태로 전환한다. 실제 Engine·Recovery를 실행하고 Windows API 경계만 가짜 backend로 교체했다. 최초에는 게임 없음, 변경 직전에는 게임 있음이 유지되도록 했다.
- 검증 결과: 실행 중 상태에서 `ack=1`, `nodelay=1`, `autotuning=normal`의 3회 변경과 해당 GUID의 `restart_network()` 1회가 호출됐다. 게임을 처음부터 실행 중으로 둔 대조군에서는 변경·재연결 0회였다. 실제 네트워크 장치나 시스템 설정은 바꾸지 않았다.
- 개발 전달: 변경 단계와 특히 재연결 직전에 현재 게임 상태를 재검증한다. 적용 도중 시작·중단·접근 해제가 겹친 경우도 이미 변경한 항목은 원본과 복구 기록을 유지하고, 재연결/원복을 안전하게 보류·안내해야 한다. 단순히 첫 분기 앞에 조회 하나를 추가하는 것으로 전체 배치의 안전성이 보장되지는 않는다. CPU 적용은 네트워크 보류와 분리한다.

- 일반 자동찾기의 버튼 외 실제 시작·후보 승인·저장 경로에서 로그인 제한을 제거하고 수집·진단·헤일로·제작자 알파 접근은 별도로 유지했다.
- 전투 보조 일시정지는 보스/헤일로/투아림 경고 소리를 막고 재생 중 소리를 정지한다. 잠금 해제된 경고·메모/미러 등 표시도 공통 상태를 따르며 추적 시계는 계속 진행한다. 파티·계산기는 중단 대상이 아니다. FPS는 측정과 표시를 분리한다.
- 제작자 접근 해제·설정 가져오기 후 재시작 대기에서는 새 알파 시작을 막고 기존 계측을 정리한다. 단순 화면 진입은 CPU/네트워크를 변경하지 않는다.
- 복구 기록은 설정과 별도 경로에 저장하며, 변경 전 기록 저장 실패는 OS 쓰기를 차단한다. CPU의 PID+생성 시각, 외부 변경 시 원복 보류, 원래 값 부재·손상 기록 보존, 재연결 대기 기록의 경계를 검토했다.
- FPS는 자신의 UUID 세션·자식 Job만 정리하도록 되어 있다. 이벤트 대상·큐·리소스 상한 및 시각 경계 테스트는 통과했지만 실제 도구 출력을 받는 통합 경로는 위 결함으로 실패한다.
- 구형 가림 재현 모델의 고정 HWND 충돌 수정은 현재 회귀에서 통과했다. 제품의 가림 판정을 약화하는 변경은 아니다.

## 5. 미검증·배포 판단

- Windows 네이티브 프로세스/Job/ETW, 실제 게임 프레임, 실제 TCP·RSS 권한/적용/부분 실패/원복, 장치 재시작, 장시간 CPU/메모리/handle 부하, 잠금/절전/Explorer 재시작과 exe 빌드는 이번 Linux 세션에서 실행하지 않았다.
- 현재 소스 SHA의 Windows 실행은 조회 시 없었다. 최신 성공 Actions는 v0.9.1의 `9514983` 검증 `39451190803` 및 게시 `39453653682`이며 이번 제품 변경의 통과 증거가 아니다.
- 기존 개발 문서의 전체 Linux 결과는 참고 자료일 뿐 독립 QA 전체 통과로 인용하지 않았다.
- 새 알파가 제작자 한정이라는 점은 실제 사용자 노출 범위를 줄이지만, 정상 출력 수신 불가와 게임 중 네트워크 재연결 결함을 통과로 바꾸지는 않는다. **두 문제 수정과 후속 독립 QA 전에는 릴리즈 명령을 제공하지 않는다.** 사용자에게 현재 단계에서 수동 Windows 검증을 다시 실행하도록 요청하지 않는다.
- 개발 시 제품 수정·정식 회귀 편입 후 푸시하고, 후속 QA에서 위 재현과 관련 전환을 다시 확인한다. 실제 Windows 검증·exe 빌드는 이후 기존 원버튼 정책을 따른다.
