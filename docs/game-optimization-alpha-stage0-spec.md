# 게임 최적화 알파: 0단계 프레임 수집·오버레이

> 2026-10-21 후속 요청: 실시간 FPS 표시만으로 저장·분석용 수집이 완료됐다고 설명하지 않는다. 사용자가 숫자를 지켜보지 않고 일반 플레이 기록을 공유할 수 있도록 [1단계 프레임 기록·분석 자료 수집](game-frame-recording-stage1-spec.md)을 개발 전달 기준으로 추가했다. 이 링크는 후속 범위이며 기존 0단계가 파일 기록까지 구현했다는 뜻이 아니다.

- 작성일: 2026-10-21
- 상태: 기획안. 프레임 수집·FPS 오버레이를 성능 검증의 0단계로 두고 CPU 설정의 적용·원복 개발과 병행하며, 관련 기능을 모두 알파로 두는 범위는 사용자 요청에 따른다. 세부 화면·조작 권장안은 12절에서 별도로 구분한다. 문서 전체의 기획 확정·구현·QA 완료를 뜻하지 않는다.
- 대상: Windows 데스크톱 마비노기. 모바일 마비노기는 대상이 아니다.
- 공유 용도: 0단계의 기술 검토와 개발 범위 협의, 후속 요구사항 확정, 독립 QA 기준 준비.
- 병행 설정의 최신 범위: [CPU 배치·TCP·NIC RSS 알파](game-optimization-cpu-tcp-rss-alpha-spec.md). CPU 배분은 가변이며 최초 알파 기본은 9800X3D만 7+1, 다른 CPU는 실제 P/E·물리 코어 구조별 기본 배분이다. RSS도 실제 배분과 연동한다. 그래픽·메모리·오버클럭은 이번 설정 기능에서 제외한다.

## 1. 목적

CPU 코어 배치 등의 성능 효과를 수치로 판단하기 위한 선행 기반으로, 마비노기의 프레임 데이터를 안정적으로 관측할 수 있는지 확인한다. 계측 경로의 첫 결과물은 현재 FPS를 게임 위에 보여주는 오버레이다.

CPU 설정의 적용·원복 기능은 프레임 수집 완료를 기다리지 않고 별도의 알파 작업으로 병행 개발·검증·사용할 수 있다. 설정이 실제로 바뀌고 원복되는지의 기능 검증과, 그 설정이 게임을 더 빠르게 만드는지의 효과 검증을 구분한다. 프레임 데이터가 아직 유효하지 않아도 명시적으로 선택한 설정은 알파로 사용할 수 있지만, 그 상태를 성능 개선 확인이나 최적값 판정으로 보고하지 않는다.

FPS 숫자가 나온다는 이유만으로 계측 성공이나 최적화 효과를 인정하지 않는다. 게임 상태 변화와 수집 실패를 구분하고, 관측값의 의미와 갱신 여부를 확인할 수 있어야 한다.

최종적으로는 체감뿐 아니라 프레임 기록을 통해 변경 전후를 비교할 수 있는 기반을 마련한다. 특정 코어 비율을 최적값으로 확정하거나 자동으로 시스템 설정을 바꾸는 기능은 0단계에 포함하지 않는다.

## 2. 공개 정책

- 0단계의 프레임 계측·FPS 오버레이와 병행하는 CPU·TCP·NIC RSS 설정은 모두 제작자 전용 알파다. 그래픽·메모리·오버클럭 변경은 현재 범위에 포함하지 않는다.
- 일반 사용자와 일반 Discord 로그인 사용자에게는 관련 진입점·설정·오버레이를 노출하지 않는다. 일반 베타 로그인만으로 사용할 수 없다.
- 화면을 숨기는 것만으로 제한하지 않는다. 계측 시작·데이터 전달·오버레이 생성·후속 설정 적용의 실행 경로에서도 제작자 접근을 확인해야 한다.
- 제작자 접근이 해제되면 0단계 계측과 FPS 표시를 종료하고 관련 워커를 정리한다. 다른 일반 기능은 중단하지 않는다.
- 데이터가 안정적으로 수집되거나 테스트를 통과해도 자동으로 베타·일반 공개하지 않는다. 공개 전환은 별도 사용자 결정이다.
- 이 정책은 기존 버프·디버프·자원 표시·자동찾기 등 다른 기능의 공개 범위를 바꾸지 않는다.

## 3. 병행 작업과 합류 조건

0단계라는 이름은 계측·성능 비교 경로에서의 순서를 뜻한다. 모든 최적화 개발을 막는 공통 선행 조건이 아니다.

| 작업 | 목적과 범위 | 의존·합류 조건 |
|---|---|---|
| A·0단계 | 게임 프레임 관측과 현재 FPS 오버레이. 이 계측 기능은 시스템 설정을 변경하지 않음 | 실게임에서 대상 식별·값의 의미·수집 안정성·상태 전환·부하를 확인 |
| A·1단계 | 사용자가 시작·끝을 정해 프레임 기록을 저장하고, 설정을 바꾸지 않은 반복 측정의 편차 확인 | 0단계 계측 검증 후 기록의 누락·무효 구간 구분과 동일 조건 반복 비교를 검증 |
| B·CPU·TCP·RSS 알파 | 실제 코어 구조를 확인해 선택한 CPU 배치·RSS와 TCP 설정을 적용·원복 | A 작업과 독립적으로 개발·기능 검증·알파 사용 가능. 세부 범위·미결정 정책은 별도 설정 명세를 따름 |
| 합류·효과 비교 | 검증한 프레임 기록으로 CPU 설정 변경 전후 비교 | A의 계측·기본 편차와 B의 적용·원복이 모두 검증되어야 함 |
| 범위 밖 | 그래픽·전원·메모리 등 추가 튜닝 | 현재 개발 대상이 아님. 추가하려면 별도 기획·승인 필요 |

모든 작업은 알파다. 병행 승인이 CPU 기능의 미정 동작이나 다른 후속 기능의 상세 구현을 임의로 확정하는 뜻은 아니다.

### 3.1 CPU 설정 알파의 독립 검증

- 사용자가 선택한 배치가 실제 지정한 프로세스에 적용됐는지 다시 읽어 확인하고, 적용 실패와 적용됨을 구분한다.
- 물리 코어와 SMT 형제 관계를 확인한다. 게임과 다른 앱을 물리 코어 단위로 나눈다고 하면서 같은 코어의 형제 스레드를 서로 다른 영역으로 나누지 않는다.
- 바꾸기 전의 실제 설정을 보관한다. 원복은 무조건 전체 코어로 만드는 동작과 구분하며, 기존 라쏘·사용자 설정도 임의로 지우지 않는다.
- 게임과 사용자가 선택한 대상만 바뀌는지, 권한 부족·프로세스 종료·PID 재사용 등에서 다른 프로세스를 잘못 변경하지 않는지 확인한다.
- 프레임 계측 기능을 실행하지 않았거나 수집이 실패해도 CPU 설정의 적용·현재값 확인·원복은 사용할 수 있어야 한다. 반대로 CPU 기능 없이도 FPS 계측은 사용할 수 있어야 한다.
- 이 검증을 통과하면 적용·원복 기능이 동작한다고 보고할 수 있다. FPS 증가·끊김 감소·최적화 완료라는 효과 판정은 합류 단계 전까지 보류한다.
- 적용 대상·가변 배분·RSS 연동·외부 도구 충돌·종료와 복구 정책은 [CPU·TCP·RSS 명세](game-optimization-cpu-tcp-rss-alpha-spec.md)를 따른다. 해당 문서의 미결정 사항을 확정하는 데 프레임 수집 완료를 기다릴 필요는 없다.

- CPU의 Baseline·BG-only·7+1·6+2·게임 프로세스의 SMT 사용 제한은 비교 후보이며 최적값이나 적용 순서로 확정하지 않는다.
- 계측 시작만으로 CPU를 분리하거나 특정 프로파일을 자동 적용하지 않는다. 별도 최적화 시작은 설정 명세의 CPU별 기본·선택 배분을 따른다. 게임이 실제로 사용하던 배치와 라쏘 등 외부 도구의 설정도 변경 전 상태로 구분해야 한다.
- 그래픽·전원·TCP·메모리 설정을 한꺼번에 바꾸고 FPS 증가를 특정 설정의 효과로 보고하지 않는다.
- TCP의 통신 지연 개선은 프레임 데이터만으로 검증할 수 없다. 통신·게임 반응에 맞는 별도 지표가 필요하다.
- 그래픽·메모리 정리·오버클럭은 이번 범위에서 제외한다. 프레임 수집이 된다는 이유로 추가하지 않는다.

## 4. 0단계 포함·제외 범위

### 포함

- 앱에 등록한 마비노기 게임창과 연결된 실제 게임 프로세스의 프레임 관측.
- 현재 FPS의 게임 오버레이 표시.
- 게임 대기·수집 준비·유효 수집·수집 중단·오류의 구분과 원인 안내.
- 잘못된 대상이나 오래된 값이 정상 FPS로 표시되지 않도록 하는 검증.
- 알파 검증에 필요한 수집 상태·진단 정보 확인. 무제한 원시 이벤트 보관은 하지 않음.

### 제외

- CPU affinity/CPU Sets·우선순위·전원 프로필·타이머 정밀도 변경.
- GPU 드라이버 프로필·FPS 제한·수직동기화 변경.
- TCP·RSS·네트워크 어댑터 설정 변경.
- 작업 집합 비우기·대기 메모리 정리·페이지 파일·RAM 오버클럭 변경.
- 자동 벤치마크, 게임 입력 자동화, 장면 반복 매크로, 최적 프로파일 자동 선택.
- CPU/GPU 사용률·온도 등 종합 하드웨어 모니터링, 사용자 간 순위 비교.
- 상시 프레임 파일 저장과 변경 전후 결과 비교 화면. 해당 범위는 1단계에서 정함.

## 5. 계측 대상과 FPS의 의미

- 기존 게임창 등록 정보를 기준으로 대상을 정한다. 단순히 실행 파일명이 같다는 이유로 다른 프로세스에 연결하지 않는다.
- PID뿐 아니라 프로세스가 다시 생성되었는지 구분한다. 게임 재실행 후 이전 세션의 데이터나 PID 재사용으로 생긴 다른 앱의 데이터를 섞지 않는다.
- 런처·애드온 본창·FPS 오버레이 자체·바탕화면 합성의 이벤트를 게임 프레임으로 합산하지 않는다.
- 같은 게임 프로세스에 여러 렌더링 대상이 있으면 실제 게임 화면을 측정하는지 확인한다. 선택 근거를 진단 정보에 남기고 모호한 대상을 무조건 합산하지 않는다.
- 게임 프레임의 이벤트/시간 정보를 바탕으로 FPS를 구한다. 애드온의 갱신 타이머 횟수나 화면 캡처 횟수를 게임 FPS로 사용하지 않는다.
- 게임이 제출한 프레임과 모니터에 실제 표시된 프레임은 다를 수 있다. 개발 검토에서 사용 가능한 지표를 확인하고 계측 위치·계산 기준을 기록한다. 서로 다른 지표를 같은 FPS로 섞지 않는다.
- 실제 렌더링 FPS를 확인하지 못하고 특정 이벤트 발생률만 수집한 경우 그 사실을 명시한다. 이를 모니터 주사율·입력 지연·서버 응답 시간으로 설명하지 않는다.
- NVIDIA 오버레이는 비교 참고 자료일 뿐 정답 데이터가 아니다. 그쪽의 9999 표시를 복사하거나 동일한 값이 나와야 한다는 기준을 두지 않는다.

## 6. 사용자 관점의 기본 흐름

1. 제작자가 계측 기능을 연다. 일반 사용자는 해당 화면을 볼 수 없다.
2. 계측을 시작하면 기존 게임창 등록 상태와 대상 프로세스, 계측 사용 가능 여부를 확인한다.
3. 게임이 없으면 게임 실행을 기다린다. 게임창이 미등록이면 등록이 필요하다고 안내한다.
4. 유효한 프레임이 관측되면 게임 위 FPS 숫자를 갱신한다.
5. 게임 활성 상태·수집 상태를 확인하면서 전투·이동 등에서 갱신이 이어지는지 확인한다.
6. 수집을 중단하거나 앱을 종료하면 이 기능이 만든 워커·보조 프로세스·이벤트 세션·오버레이를 정리한다.

화면 설명은 `마비노기의 프레임을 측정해 현재 FPS를 보여줘요.`로 한다. 알파라는 내부 단계 표기와 로그인 요구 문구를 기능 설명에 반복해서 넣지 않는다.

## 7. 상태와 예외 동작

| 상태·상황 | 기대 동작 |
|---|---|
| 사용 전·수집 중단 | 계측하지 않고 실제 게임 FPS 오버레이도 표시하지 않음 |
| 제작자 접근 없음 | 진입점·계측·표시 차단. 실행 중 접근 해제도 같은 원칙 적용 |
| 게임창 미등록 | 설정 화면에서 등록 필요 안내. 임의의 전체 화면이나 다른 게임을 대신 측정하지 않음 |
| 게임 미실행 | 실행 대기 표시. 존재하지 않는 게임의 FPS를 0으로 표시하지 않음 |
| 게임 실행·연결 준비 | 유효 이벤트가 모이기 전에는 `측정 준비 중` 또는 값 없음으로 안내 |
| 유효한 수집 | 현재 대상을 나타내는 최신 FPS 표시 |
| 게임 종료·비정상 종료 | 이전 값과 대상 연결 해제, 오버레이 숨김. 종료 전후 이벤트 간격을 FPS 계산에 포함하지 않음 |
| 게임 재실행 | 새로운 실행을 다시 식별하고 새 유효 구간에서 계산. 이전 게임의 타임스탬프·이동평균 등 이월 금지 |
| Alt+Tab·최소화·Windows 잠금·절전 | 화면 표시를 중단하고 상태 전환을 구분. 복귀 시 구간 경계를 넘어 계산하지 않음 |
| 새 프레임 관측 없음 | 정상 FPS처럼 이전 숫자를 계속 유지하지 않음. 게임 상태·계측 상태에 따라 대기/값 없음으로 구분 |
| 계측기 중단·데이터 단절 | 값 없음과 수집 문제 안내. 실제 저FPS나 게임 미실행으로 잘못 보고하지 않음 |
| 권한 부족·필수 구성요소 없음 | 시작 불가 원인과 가능한 조치 안내. 앱의 다른 기능은 유지 |
| 전체 화면 방식 전환·해상도 변경 | 렌더링 대상이 바뀌었는지 다시 확인. 지원하지 못하는 모드는 계측 제한으로 안내 |
| 중복 시작·빠른 시작/중단 | 중복 세션·오버레이가 생기지 않고 늦게 도착한 이전 데이터가 다시 표시되지 않음 |
| 다른 계측 도구 실행 | 충돌 여부와 지원 조건을 확인. 타 프로그램의 계측 세션이나 NVIDIA 오버레이를 임의 종료하지 않음 |

- 오버레이는 게임이 포그라운드일 때 표시하는 기존 원칙을 따른다. 앱에서 배치 미리보기를 제공한다면 실제 게임 FPS와 예시를 구분한다.
- 중단·복귀 시 관측 경계를 구분한다. 새 유효 구간이 확보되기 전 오래된 숫자를 현재 수치처럼 복원하지 않는다.
- 프레임 지연이 길다는 이유만으로 데이터를 버리지 않는다. 실제 끊김과 계측 누락·백그라운드 전환은 서로 다른 상태다.
- 로딩도 게임의 실제 작업이다. 이후 비교 기록에서는 용도에 따라 구간을 표시하며 로딩이라는 이유만으로 자동 삭제하거나 성능이 좋아 보이게 제외하지 않는다.

## 8. 잘못된 수치와 수집 신뢰성

- 수집 타임스탬프의 역전·중복·연결 단절, 잘못된 대상, 관측 구간 부족을 검증한다.
- 9999 같은 큰 숫자를 오류용 대체값으로 만들거나 고정 표시하지 않는다.
- 숫자가 크다는 이유만으로 임의 상한에 맞춰 정상값으로 고치지 않는다. 유효한 이벤트에서 계산된 값인지 검증하고, 근거가 없으면 값 없음으로 처리한다.
- 오버레이 갱신과 원본 수집은 구분한다. 숫자를 덜 자주 그리더라도 그 사이 실제 프레임을 임의로 누락시켜 계산하지 않는다.
- 이벤트 손실·재연결·무효 구간을 확인할 수 있어야 한다. 데이터가 끊긴 구간을 매끄러운 FPS로 보간해 숨기지 않는다.
- 유효 데이터가 없는데 0 FPS로 단정하거나 무한대·NaN·이전 세션의 값 등을 표시하지 않는다.
- 최적화 효과 판정은 아직 제공하지 않는다. 수집 성공과 성능 개선은 별개의 판단이다.

## 9. 기존 앱·권한·성능과의 관계

- 기존 게임창 등록·제작자 식별·오버레이 조작 패턴을 활용한다. 도입을 이유로 사용자의 게임창 등록·다른 영역·배치 설정을 초기화하지 않는다.
- 계측은 읽기 전용 범위다. 게임 실행 파일·게임 데이터·네트워크 내용을 수정하거나 게임에 키 입력·클릭을 보내지 않는다.
- 계측에 추가 권한이나 구성요소가 필요하면 사유와 범위를 설명한다. 몰래 서비스·드라이버·상주 작업을 설치하거나 기존 앱 전체의 관리자 실행을 강제하지 않는다.
- 게임 접근이 차단되거나 계측이 지원되지 않으면 실패로 안내한다. 접근 통제를 우회하는 방식으로 진행하지 않는다.
- 모든 내부 버퍼·진단 정보는 크기가 제한되어야 한다. 창 갱신과 사용자 설정 조작이 수집 때문에 멈추지 않아야 한다.
- 반복 시작/중단과 게임 재실행에서 워커·프로세스·핸들·이벤트 세션 수가 누적 증가하지 않아야 한다. 타 프로그램이 만든 자원은 정리 대상이 아니다.
- 계측 자체와 오버레이 표시의 부하는 따로 확인한다. 0단계 도구를 켜서 생긴 부하를 최적화 효과로 오해하지 않는다.
- 허용할 CPU·메모리·프레임 부하 수치는 현재 미확정이다. 먼저 실제 수치를 제시하고 사용자의 알파 화면에서 받아들일 수준인지 확인한다. 수치를 확인하지 않고 저부하라고 보고하지 않는다.

## 10. 0단계 Acceptance Criteria

1. 일반 사용자와 일반 로그인 사용자는 기능 진입점이 없고 저장 설정을 바꿔도 계측·표시가 시작되지 않는다. 제작자는 계측을 시작할 수 있다.
2. 등록한 게임과 연결된 프레임만 측정하며 런처·애드온·FPS 오버레이의 프레임을 합산하지 않는다. 실제 사용한 지표와 대상 선택 근거를 확인할 수 있다.
3. 게임이 활성 상태이고 유효 데이터가 수집될 때 FPS가 갱신된다. 숫자의 변화가 원본 프레임 시간에서 설명되어야 하며 앱 타이머 횟수를 FPS로 표시하지 않는다.
4. 게임 미실행·프레임 준비·계측 실패를 정상 수치와 구분한다. 오류용 9999나 이전 값을 정상 FPS로 계속 보여주지 않는다.
5. 게임 종료 후 오버레이가 사라지고 재실행 후에는 새 대상의 유효 구간에서만 다시 계산한다. 이전 실행의 데이터나 PID 재사용 대상이 섞이지 않는다.
6. Alt+Tab·최소화·잠금·절전 복귀와 화면 모드 전환에서 지원 여부와 무효 구간이 구분된다. 경계 전후의 긴 공백을 하나의 정상 프레임 간격으로 계산하지 않는다.
7. 느린 유효 프레임과 계측 실패를 구분한다. 실제 끊김을 평균에서 숨기거나 9999를 그럴듯한 상한값으로 바꾸지 않는다.
8. 반복 시작/중단·앱 종료·제작자 접근 해제 후 전용 워커·세션·오버레이가 정리된다. 다른 앱의 세션과 기존 기능은 영향을 받지 않는다.
9. 별도의 CPU 설정 조작 없이 0단계 계측만 시작·종료하면 CPU 배치·우선순위·전원·타이머 정밀도·GPU 프로필·TCP·메모리 정리 설정이 변경되지 않는다. CPU 설정 알파를 병행할 때는 명시적인 CPU 조작과 계측 동작을 구분할 수 있다.
10. 원본 수집과 FPS 표시의 부하를 측정해 보고한다. 실게임에서 수집하지 않았다면 계측 검증 완료나 성능 비교 진행 가능으로 보고하지 않는다. 이는 CPU 설정 알파의 독립 개발·기능 검증을 막는 조건은 아니다.

## 11. 성능 비교와 후속 기능에서 확정할 기준

- 프레임별 파일 기록, 수집 시작/종료, 저장 경로·용량·보관·삭제와 비정상 종료 시 파일 복구.
- 기본 상태 반복 측정과 후보 프로파일 비교의 구간·워밍업·횟수·순서·환경 기록.
- 평균 FPS, 1% Low, P99 프레임타임, 긴 프레임 기준의 정확한 정의와 계산 방식. 단일 최저 FPS나 한 번의 최고 점수로 최적값을 고르지 않음.
- 로딩·전환·계측 누락과 실제 성능 저하 구간을 어떻게 표시하고 비교에 포함할지.
- 개선이 불분명할 때 기본 상태 유지, 유망한 결과의 재검증, 추천 결과와 사용자 승인.
- CPU 프로파일의 적용 대상·기존값 보관·외부 도구 충돌·실패 원복·게임/앱 종료 후 처리. affinity와 CPU Sets는 동일한 제한 방식으로 취급하지 않음.
- 병행하는 TCP·RSS의 별도 효과 지표와 설정 기능 명세의 미결정 정책. GPU·메모리 튜닝은 현재 범위 밖이다.

프레임 기록·효과 비교는 계측 검증 후 진행한다. CPU·TCP·RSS 적용·원복은 별도 명세에 따라 병행할 수 있다. 그 밖의 최적화는 현재 범위가 아니며 상세 구현 지시가 아니다.

2026-10-21 사용자 후속 정정: 최적화 알파는 **제작자에게만 상위 최적화 탭을 노출**한다.

진행하며 탭 밖 자동 팝업으로 대체하지 않는다. 앞선 비제작자 복구 예외 시안보다 이번 사용자 정정이 우선한다.
