# 게임 최적화 알파: CPU 배치·TCP·NIC RSS

- 작성일: 2026-10-21
- 상태: 사용자 동의에 따른 알파 동작 기획 확정. 9800X3D 기본 7+1, 다른 CPU의 구조별 기본 배분, 제외 목록 기반 백그라운드 자동 분류, TCP 세 항목, 게임별 적용·원복과 라쏘 충돌 처리를 정의한다. 구체적인 화면 배치는 개발 전 목업으로 확인한다. 구현·실게임 QA 완료를 의미하지 않는다.
- 대상: Windows 데스크톱 마비노기. 최초 실사용 검토 환경은 Ryzen 7 9800X3D이며 다른 CPU·네트워크 장치의 지원을 검증 없이 보장하지 않는다.
- 접근: 관련 설정·실행·계측은 모두 제작자 전용 알파. 일반 Discord 로그인만으로 공개하지 않는다.
- 관련 문서: [프레임 계측 0단계](game-optimization-alpha-stage0-spec.md). 두 작업은 병행할 수 있으며 효과 비교에서 합류한다.

## 1. 목적과 범위

게임용 CPU와 백그라운드 작업의 경합을 줄이는 배치, TCP 통신 설정, 게임용 CPU와 RSS 수신 처리의 분리를 한곳에서 관리한다. 적용 전 상태로 복구할 수 있어야 한다.

### 이번 범위

- CPU: 게임과 대상 백그라운드 프로그램의 사용 코어 배치, 현재값 확인, 재적용·원복.
- TCP: 현재 설정 확인과 사용자가 선택한 변경, 적용 결과 확인·원복.
- NIC RSS: 지원 어댑터의 RSS 수신 처리 CPU를 게임용 코어 밖에 배치하고 확인·원복.
- 명시적 시작, 게임 실행 대기·감지, 게임 종료 후 복구와 비정상 종료 후 복구 지원.

### 제외

- GPU 드라이버 설정, FPS 제한, 수직 동기화, 그래픽 최적화. **예외(2026-10-23 사용자 결정)**: NVIDIA 마비노기 프로필의 최대 프레임 속도 400 상한만 13.6절 "그래픽 효율 최적화"로 포함한다. 수직 동기화와 그 밖의 드라이버 설정은 계속 제외한다.
- 메모리 정리·RAM 부스트·XMP·EXPO·RAM 타이밍·전압 조절.
- CPU 오버클럭·전압·PBO, CPU 우선순위 변경, 전원 계획·타이머 정밀도 등 추가 Windows 튜닝. **예외(2026-10-24 사용자 결정)**: 게임 프로세스 우선순위 "높음"만 13.7절로 포함한다. 다른 프로그램의 우선순위 변경과 "실시간"은 계속 제외한다.
- 입력 자동화, 게임 메모리 접근·게임 데이터 수정·프로세스 주입·보안 기능 우회.
- 자동 벤치마크와 최적 프로파일 자동 선택. 측정되지 않은 배치를 최적으로 표시하지 않는다.

CPU 배치·TCP·RSS 변경은 오버클럭이 아니다. 읽기 전용 계측과 시스템 설정 변경의 권한·범위를 구분한다.

## 2. 사용자 관점의 사용 흐름

사용자가 원하는 기본 흐름은 `앱 실행 → 최적화 시작 → 게임 실행 → 적용 상태로 이용 → 게임 종료 → 원래 설정으로 복구`다.

1. 앱 실행만으로 설정을 변경하지 않는다. 제작자가 최적화 화면에서 항목과 CPU 배분을 확인하고 명시적으로 시작한다.
2. CPU 구조·대상 장치·지원 여부·권한을 확인하고 변경 전 값을 보관한다. 연결 중단 가능성이 있는 작업은 실행 전에 알린다.
3. 선택한 네트워크 설정을 준비하고 게임 실행을 기다린다. 게임 프로세스가 없는 동안 CPU 배치를 적용했다고 표시하지 않는다.
4. 등록된 게임과 연결된 실제 프로세스를 식별하면 게임·대상 백그라운드 프로그램에 CPU 배치를 적용한다.
5. 설정값을 다시 확인해 항목별 성공·실패·미지원·미적용을 구분한다. 일부 실패를 전체 성공으로 표시하지 않는다.
6. 게임이 종료되면 CPU 배치를 자동 복구한다. TCP·RSS는 연결 중단 가능성을 안내하고 확인받아 복구하며, 미루면 `복구 대기`로 유지한다.
   사용자 원복은 **`중단 · 원복` 버튼 하나**로 적용했던 CPU·TCP·RSS를 한 번에 되돌린다(2026-10-23 사용자 결정, 0.11.4).
   네트워크 항목이 있으면 시작할 때처럼 연결 끊김 확인을 한 번 받고, 거절하면 CPU만 되돌리고 네트워크는 `원복 대기`로 남긴다
   (같은 버튼을 다시 누르면 이어서 원복). 별도 네트워크 원복 버튼은 없다.
7. 복구 검증까지 마치면 해당 최적화 세션을 종료한다. 복구 대기가 있으면 완료가 아닌 `복구 대기`로 남긴다.

게임이 이미 실행된 경우도 고려한다. 현재 연결을 끊을 수 있는 네트워크 변경을 게임 중에 조용히 적용하지 않으며, CPU만 적용하거나 네트워크 적용을 미룰 수 있는 동작을 제공하는 방향으로 화면에서 확인한다.

## 3. CPU 배분은 고정값이 아닌 선택 가능한 설정

- `6+2`, `7+1`은 물리 8코어 환경에서의 `게임용 물리 코어 수 + 백그라운드용 물리 코어 수` 예시다. 논리 CPU 번호나 SMT 스레드 수를 뜻하지 않는다.
- 9800X3D의 물리 8코어·논리 16스레드 구조를 실제로 확인한다. CPU 이름이나 홀수·짝수 번호만으로 물리 코어 관계를 추정하지 않는다.
- 완전 분리 배치에서는 같은 물리 코어의 SMT 형제를 게임용과 백그라운드용으로 갈라놓지 않는다. 게임·백그라운드 코어 집합은 겹치지 않아야 한다.
- 게임용과 백그라운드용에 각각 최소 한 개의 물리 코어가 필요하다. 지원하지 못하는 구성을 억지로 적용하지 않는다.
- 9800X3D의 최초 알파 선택값은 게임 7코어·백그라운드 1코어(7+1)다. 제작자가 프레임 수집과 비교를 시작하기 위한 값이며, 성능이 검증된 최적값·일반 사용자 권장값이 아니다. 앱 실행만으로 자동 적용하지 않는다.
- 제작자가 6+2 등 지원되는 배분으로 변경할 수 있다. 다른 CPU에 7+1을 임의 적용하지 않으며, 아래 구조별 기본 배분을 따른다. 특정 논리 CPU 번호 범위를 하드코딩하지 않는다.
- 실제 지원하는 배분만 선택할 수 있어야 한다. 다른 코어 수·하이브리드 CPU·다중 프로세서 그룹의 지원 범위는 별도로 확인하며 8코어용 숫자를 그대로 적용하지 않는다.
- 기본 상태(Baseline)·백그라운드만 제한(BG-only)·게임 프로세스의 SMT 사용 제한은 비교 후보일 뿐, 이번 MVP에서 모두 제공하기로 확정한 옵션이 아니다.
- **2026-10-23 사용자 결정**: 게임 프로세스의 SMT 사용 제한(게임 코어마다 논리 CPU 1개만 허용, 이하 `SMT 끄기`)을 실험 옵션으로 추가한다.
  9800X3D 알파의 기본 실험안은 `게임 7코어 · SMT 끄기`이며 `SMT 켜기(현재 방식)`와 `6+2`를 비교 옵션으로 둔다.
  **2026-10-24 갱신**: 여러 던전에서 SMT 끄기는 체감되지 않았고, 우선순위 높음은 무거운 던전에서 확실히 체감됐다(사용자). 우선순위 높음은 13.7절로 확정하고,
  SMT 끄기와 CPU 배치(7+1 등)는 **우선순위 높음을 깐 상태에서** 효과가 있는지 데이터로 검증하는 실험 옵션으로 둔다(9.2절). 검증 전에는 기본으로 켜지 않는다.
  근거는 커뮤니티 후기들이 일관되게 SMT 비활성화를 마비노기 핵심 설정으로 권한다는 점이다([리서치](game-optimization-feasibility-research.md)).
  측정 전 효과 확정이 아니다. SMT 끄기에서도 백그라운드 집합은 게임 코어의 형제 논리 CPU를 포함하지 않는다(게임 코어의 남는 형제는 비워 둔다).
- 게임 프로세스에도 직접 배치를 적용하는 현재 방식을 유지한다(2026-10-23 사용자 결정). SMT 끄기 실험에 필요하고, 커뮤니티에서도
  작업 관리자·Process Lasso로 `Client.exe`에 직접 지정하는 방식이 일반적이다. 제재 보고가 없다는 것이지 안전이 확인된 것은 아니다.
- 처음에는 선택한 배분을 적용하는 기능이다. 프레임을 보며 코어 수를 자동 변경하거나 자동으로 가장 좋은 배분을 선택하지 않는다.

### CPU 구조별 최초 기본 배분

| 확인한 CPU 구조 | 게임용 | 백그라운드용 |
|---|---|---|
| Ryzen 7 9800X3D, 물리 8코어·논리 16스레드 확인 | 물리 7코어 | 나머지 물리 1코어 |
| 그 밖의 P/E 하이브리드 CPU | 렘 부스터의 기본 배분 기준에 따라 P코어 일부 우선 배정 | 나머지 P코어와 모든 E코어 |
| 그 밖의 P/E 구분 없는 CPU | 렘 부스터의 기본 배분 기준에 따라 물리 코어 일부 배정 | 나머지 물리 코어 |

- P/E 구분 없는 CPU를 임의로 P/E로 나누거나, P/E CPU에서 모든 P코어를 무조건 게임에 배정하지 않는다.
- 확인한 참고 소스의 기본 모드에서 성능 코어 수를 N이라 할 때, N≥2의 게임용 코어 수는 `min(N-1, max(4, ceil(N/2)))`다. 여기서 N은 하이브리드 CPU에서는 P코어 수, 동종 코어 CPU에서는 전체 물리 코어 수다. 예를 들어 P8+E8은 게임 P4 / 백그라운드 P4+E8이며, P6+E8은 게임 P4 / 백그라운드 P2+E8이다. 단순히 논리 스레드를 절반으로 자르는 규칙이 아니다.
- 성능 코어가 하나뿐인 구조, 토폴로지 확인 실패, 다중 프로세서 그룹 등 일반 분리 조건에 맞지 않는 환경은 지원 가능성을 검토한다. 참고 소스의 예외·코어 공유까지 자동 도입하지 않으며, 검증할 수 없으면 미지원으로 안내하고 적용하지 않는다.
- 기본 배분은 제작자의 명시적인 시작 시 사용할 최초 계획이다. 어떤 CPU에서도 성능 향상·최적 배분을 보증하는 값이 아니다.

### 대상 프로그램과 외부 도구

- 게임은 기존 게임창 등록과 연결된 실행 대상으로 식별한다. 이름만 같은 다른 프로세스·런처를 임의 변경하지 않는다.
- 백그라운드는 참고 앱처럼 현재 사용자 세션의 일반 프로세스를 자동 열거하고 제외 목록을 뺀 대상을 분류한다. 제작자가 프로그램을 하나씩 체크해야 시작하는 방식으로 만들지 않는다.
- 게임 실행 중 새로 시작한 일반 프로그램도 같은 분류·제외 기준으로 처리한다. 게임 대기 중에는 백그라운드 CPU 배치를 먼저 바꾸지 않는다.
- Windows 핵심·보안·안티치트·필수 서비스 등 변경 위험이 있는 대상은 제외하며, 권한 부족이나 보호된 프로세스는 건너뛰고 이유를 기록한다.
- Process Lasso가 없는 환경에서도 독립적으로 동작해야 한다. 라쏘 설치·규칙 설정을 전제로 하지 않는다.
- 라쏘나 다른 도구가 있으면 해당 도구의 규칙을 수정·제거하지 않는다. 서로 설정을 반복해서 덮어쓰는 경우를 식별하고 사용자에게 충돌을 안내한다. 무한 재적용으로 경쟁하지 않는다.
- Process Lasso Governor가 실행 중이면 CPU·RSS 적용을 보류하고 중단 방법을 안내한다. 실행 순서를 앞당겨 우선권을 얻는 방식으로 해결하지 않는다. 우리 앱이 라쏘를 강제 종료하거나 규칙을 바꾸지 않는다. 라쏘 창만 닫은 상태와 Governor 중단을 구분한다.
- 라쏘 중단이 기존 프로세스의 배치·우선순위를 자동 초기화한다는 가정을 하지 않는다. 원본 보관은 실제 현재값 기준이며, 라쏘로 변경된 값을 Windows 기본 상태로 잘못 표시하지 않는다.
- 프로세스가 새로 실행되거나 종료되어도 이전 PID의 원복값을 다른 실행에 적용하지 않는다. 실행 중 대상 감시·재적용은 중복 작업을 만들지 않아야 한다.

## 4. NIC RSS와 CPU 배치의 연동

> **2026-10-24 사용자 결정: RSS는 최적화 기능에서 뺀다(13.8절).** 아래 내용은 기존 구현과 원복 처리의 기록으로 남긴다.

RSS는 네트워크 수신 처리를 CPU에 분산하는 기능이다. 여기서의 격리는 지원되는 RSS 수신 처리 CPU를 게임용 코어 밖으로 옮기는 의미이며, 모든 인터럽트·송신 처리·게임 통신만의 완전한 격리를 뜻하지 않는다.

- RSS 대상은 실제로 선택한 백그라운드 코어 집합에서 계산한다. 전체 논리 CPU의 앞쪽 절반이나 `CPU 0~7` 등을 별도로 하드코딩하지 않는다.
- 6+2에서 7+1로 바꾸면 RSS 계획도 새 배분에서 다시 계산한다. 과거 배분에 대한 성공 표시를 그대로 유지하지 않는다.
- 장치가 지원하는 프로세서 범위·수신 큐·프로세서 수와 실제 적용값을 확인한다. 선택한 백그라운드 코어만 표현할 수 없는 장치·구성에서는 완전 격리 성공으로 표시하지 않는다.
- 조회된 RSS 그룹 값이 비어 있으면 `GetActiveProcessorGroupCount`가 1을 반환한 경우에만 그룹 0으로 보완한다. 그룹 수 확인 실패·다중 그룹은 추정하지 않으며, 명시된 그룹과 나머지 설정값의 비교는 그대로 유지한다. 적용 확인과 원복 조회에 같은 기준을 사용한다.
- 설정값 확인과 실제 패킷 처리가 해당 CPU에만 배치됐다는 검증은 구분한다. 설정 확인만으로 모든 네트워크 처리가 분리됐다고 단정하지 않는다.
- RSS 미지원·권한 부족·검증 실패 시 원인을 안내한다. RSS를 제외하고 CPU 기능을 사용할 수 있어야 하며, 필요한 경우 기존 RSS 상태를 복구한다.
- 어댑터별 설정이므로 마비노기 외 통신에도 영향을 줄 수 있음을 알린다. 관리자 권한과 네트워크 재연결이 필요할 수 있다.
- 적용 중 배분 변경은 허용하지 않는다. 제작자가 중단·원복을 완료한 뒤 새 배분으로 다시 시작한다. 네트워크 복구가 남아 있으면 새 세션을 겹쳐 시작하지 않는다.

## 5. TCP 설정의 범위와 확인 수준

공개 참고 앱과 동일하게 아래 세 항목을 이번 알파 TCP 범위로 한다. 구현 사례이지 모든 환경에 유효한 권장값이라는 의미가 아니다.

| 항목 | 적용값 | 이번 문서에서의 취급 |
|---|---|---|
| TcpAckFrequency | 사용 어댑터에 1 설정 | 패스트핑. 지원 Windows·네트워크에서 유효한지 확인 |
| TCPNoDelay | 사용 어댑터에 1 설정 | 패스트핑. 레지스트리 기록만으로 게임 소켓 동작 개선을 단정하지 않음 |
| TCP 수신 창 자동 조정 | Normal | 위 두 값과 별개의 Windows 전역 설정. 적용 전 실제값 보관·원복 대상에 포함 |

- 이미 같은 값이면 불필요하게 다시 쓰거나 어댑터를 재시작하지 않는다.
- 기존값과 해당 값이 원래 없었던 상태를 구분해 보관한다. 원래 없었다면 원복은 임의의 기본 숫자를 쓰는 것이 아니라 해당 변경값을 제거하는 동작이다.
- 설정 기록·적용 확인과 게임 체감·통신 지연 개선을 구분한다. 프레임 기록만으로 TCP 효과를 검증했다고 보고하지 않는다.
- 어댑터 단위 또는 Windows 전역 변경은 다른 앱에도 영향을 준다. 게임 프로세스만 대상으로 하는 설정처럼 설명하지 않는다.
- 참고 앱의 `network_manager.rs`는 Normal 적용을 포함하지만 복구 경로에서 같은 설정을 이전값으로 돌리지 않는다. 이 동작까지 복사하지 않는다. 우리 앱은 전역 자동 조정도 변경 전 실제값을 보관·복구해야 한다. 그룹 정책 등으로 변경이 막히면 정책을 우회하지 않고 실패·제한을 안내한다.
- VPN·가상 어댑터·복수 기본 경로 등에서 실제 대상이 불명확하면 임의로 여러 장치에 적용하지 않는다.

## 6. 변경 전 상태 보관과 원복 원칙

- 원복은 적용 전 실제 값으로 되돌리는 동작이다. CPU 전체 허용·TCP 기본값·RSS 임의 기본값으로 덮는 초기화와 다르다.
- 원본은 변경 전에 영속 보관한다. 반복 시작·재시도·프로파일 변경으로 최초 원본이 앱이 적용한 값으로 바뀌지 않아야 한다.
- CPU는 프로세스의 실행 식별 정보, 원래 값, 앱이 적용한 값을 함께 관리한다. 이미 종료된 게임 프로세스는 복구 대상 없음으로 구분하고, 살아 있는 백그라운드 대상의 복구는 진행한다.
- 네트워크 원본은 어댑터의 안정적인 식별 정보와 함께 보관한다. 유선에서 Wi-Fi로 바뀌었다고 유선 원본을 현재 Wi-Fi에 적용하지 않는다.
- 복구 시 현재값이 앱의 적용값과 다르면 외부 변경 가능성을 안내한다. 무조건 덮어쓰거나 복구 완료로 표시하지 않는다.
- 적용·검증·복구 중 어느 단계에서 실패했는지 항목별로 남긴다. 일부 성공·일부 실패에서도 무엇이 남아 있는지 확인할 수 있어야 한다.
- 원본 파일 손상·누락 시 추정값으로 복구하지 않는다. 적용·복구 제한과 수동 확인 방법을 안내한다.
- 복구 검증 전 기록을 지우지 않는다. 앱이 비정상 종료해도 다음 실행에서 미복구 변경을 확인할 수 있어야 한다.
- 모든 종료 경로에서 즉시 복구가 보장된다고 설명하지 않는다. 전원 차단·프로세스 강제 종료 시 네트워크 설정 등은 남을 수 있다.

## 7. 상태와 생명주기

| 상황 | 기대 동작 |
|---|---|
| 최초 실행·일반 재실행 | 자동 적용하지 않음. 미복구 기록이 있으면 신규 시작과 구분해 복구 필요 안내 |
| 게임 미실행 상태에서 시작 | 사전 검사·선택한 네트워크 준비 후 게임 대기. CPU 적용 완료로 표시하지 않음 |
| 게임 실행 | 새 실행 식별 후 선택한 CPU 배분 적용·확인 |
| 게임 정상·비정상 종료 | 게임 관련 CPU 작업 중단, 살아 있는 변경 대상 복구. 네트워크 원복 대기는 별도 유지 |
| 게임 빠른 재실행 | 이전 복구와 새 적용이 충돌하지 않음. 복구 미완료 상태를 새 원본으로 저장하지 않음 |
| 게임 대기 중 취소 | 이미 바꾼 네트워크 등이 있으면 복구 절차 진행. 변경 없이 단순 대기였으면 정리 후 종료 |
| 수동 최적화 종료 | 게임 실행 여부와 관계없이 해당 세션의 적용 중단·복구 절차 진입 |
| Alt+Tab·최소화·화면 모드·해상도 변경 | 게임 종료로 취급해 설정을 반복 적용·원복하지 않음 |
| Windows 잠금·절전·복귀 | 일시적인 관측 실패를 게임 종료로 단정하지 않음. 복귀 후 프로세스·장치·현재값 재확인 |
| 네트워크 장치 변경·분리 | 새 장치에 자동 확장 적용하지 않음. 기존 변경·복구 대상을 보존하고 대상 변경 안내 |
| 관리자 권한 거절·적용 실패 | 변경하지 못한 항목과 이미 변경한 항목을 구분하고 필요한 복구 제공 |
| 앱 정상 종료·제작자 접근 해제 | 새 적용 중단, 변경 상태 정리·복구 절차 진입. 접근 해제가 복구 경로까지 막지 않아야 함 |
| 앱 강제 종료·Windows 재부팅 | 다음 실행에서 미복구 기록·실제값을 비교. 재부팅으로 CPU 제한이 사라졌어도 네트워크까지 복구됐다고 추정하지 않음 |
| 중복 실행·빠른 반복 클릭 | 동일 대상에 중복 세션 생성·중복 재시작·중복 원본 저장 금지 |

게임 종료 후 최적화 세션을 종료한다. 다음 게임에 자동 재적용하지 않으며, 제작자가 다시 시작한다. 게임 대기 중 취소나 앱 종료에서도 CPU 복구는 진행하고, 네트워크 복구는 확인받으며 미루거나 실행할 수 없으면 미복구 기록을 유지한다.

## 8. 기존 앱과 권한·자원

- 일반 트래커·오버레이·계산기는 이 기능을 시작하지 않아도 기존처럼 사용할 수 있다.
- 전투 보조 일시정지와 최적화 종료·원복을 같은 동작으로 묶지 않는다. 전투 표시·소리를 잠시 끄는 버튼이 네트워크 연결을 끊어서는 안 된다.
- 추가 권한이 필요한 이유와 대상 작업을 설명한다. 일반 기능 사용을 위해 앱 전체의 관리자 실행을 강제하지 않는다.
- 감시·상태 확인이 UI를 멈추지 않아야 한다. 반복 실행에서 워커·핸들·진단 파일·재시도 작업이 무제한 증가하지 않아야 한다.
- 장치 재시작을 반복하는 무한 재시도는 하지 않는다. 재연결 실패 시 중단·원인 안내·복구 경로를 제공한다.
- 접근이 막힌 프로세스나 장치의 보호를 우회하지 않는다. 기존 앱의 게임 접근·입력 자동화 금지 원칙은 유지한다.

## 9. 프레임 계측과 효과 검증

- CPU·TCP·RSS의 기능 개발과 알파 사용은 프레임 계측 완성을 기다리지 않고 진행할 수 있다.
- 프레임 계측만 시작하면 CPU·네트워크 설정이 바뀌지 않는다. 최적화만 실행해도 프레임 오버레이·파일 수집이 강제로 시작되지 않는다.
- 기능 검증은 실제 적용값·복구값·범위·실패 처리의 검증이다. 성능 검증은 같은 조건에서 변경 전후 데이터를 비교하는 별도 작업이다.
- 6+2와 7+1 비교 시 TCP·RSS·그래픽·게임 환경 등 다른 조건을 기록한다. RSS도 함께 바뀌는 비교는 순수 CPU 배치 효과와 구분한다.
- 평균 FPS 외 프레임타임·하위 프레임 지표와 체감 기록을 참고한다. 체감 개선을 부정하지 않되 설정별 원인을 측정 없이 확정하지 않는다.
- 사용자 경험담은 시도의 근거지만 특정 배분이 모든 사용자에게 최적이라는 근거로 사용하지 않는다.
- TCP·RSS의 반응성 효과는 프레임 자료만으로 확정하지 않는다. 통신·CPU 경합 등 추가 검증 방법을 별도로 정한다.

### 9.1 실험 절차와 검증 단계 (2026-10-23 사용자 결정)

- **판정 지표**: 커뮤니티 후기가 말하는 효과가 "잔렉·끊김"이므로 평균 FPS보다 1% low와 긴 간격(분당 횟수)을 중심으로 본다.
  입력 반응 체감은 프레임 자료로 완전히 잡히지 않으므로 체감 기록을 함께 남긴다.
- **고정·기록할 조건**: 렌더링 엔진(DX9·공식 Vulkan·직접 설치 DXVK), FPS 제한·수직 동기화, 주변 캐릭터 간소화,
  메모리 정리 도구(ISLC 등)·Process Lasso·노기렘 실행 여부, 블랙박스 사용 여부, 장면(장소·채널·인원).
- **비교 방식**: 같은 장면에서 조건 A·B를 번갈아(ABAB…) 각 5회 이상 측정한다. 진입 직후 30초는 버린다. 붐비는 장면은 서버 영향이 커 참고로만 쓴다.
- **FPS 제한 (A안으로 측정 완료, 2026-10-23)**: 측정 결과 끊김 개선 효과는 없고 과잉 프레임(로딩 2000FPS 이상)의 발열·전력을 줄이는 효과만 확인됐다([리서치 7.1](game-optimization-feasibility-research.md#71-fps-제한-120-2026-10-23-제작자-pc-9800x3d-nvidia-앱-0134)). 이에 따라 400 상한을 "그래픽 효율 최적화"로 기획했다(13.6절). 아래는 측정 절차 기록이다. 사용자가 직접 설정하고 앱은 전후를 측정한다. 제한값은 고정하지 않고,
  제한 없이 무거운 장면을 측정한 1% low와 모니터 주사율을 근거로 고른다. 무거운 장면에서 이미 제한값보다 낮게 나오면 그 장면에서는 효과가 없다.
- **검증 단계**: ① 제작자 알파는 제작자 PC(고사양)에서 "고사양에서도 무거운 장면의 끊김이 줄어드는가"와 측정 도구 동작을 확인한다.
  고사양에서 효과가 없더라도 저사양에서 효과가 없다는 증거가 아니다. ② 베타로 넓힐 때 사양이 다른 PC 2~3대(저사양 노트북·인텔 P/E 등)의
  요약 저장 파일을 받아 확인한다. ③ 그 결과로 일반 공개와 CPU 구조별 기본값을 결정한다. 다른 사용자에게는 고정값보다
  "내 PC에서 측정해 고르는 방법"을 제공하는 방향이다.
- 자동 적용(켜 두면 알아서 적용)은 실험 비교에 방해되므로 효과 확인 뒤 다시 기획한다(2026-10-23 사용자 결정).

### 9.2 SMT 끄기·CPU 배치 검증 실험 (2026-10-24 사용자 결정)

- 목적: 우선순위 높음(13.7, 확정)을 깐 상태에서 SMT 끄기와 7+1 배치가 **추가로** 효과가 있는지 데이터로 확인한다. 체감이 아니라 측정으로 판단한다.
- 사전 조건: Process Lasso는 관리자(Governor)까지 종료하고 게임을 새로 켠다(켜 두면 게임 설정을 자동으로 바꾸므로, 리서치 7.5). FPS 제한·블랙박스 끔, 렌더링 엔진 고정.
- 조건(모두 게임 우선순위 높음): `높음`(선호도 전체) / `높음+smt끔`(짝수 CPU) / `높음+7+1`(앱 CPU 배치 7+1, 네트워크 항목 끔).
  같은 무거운 던전, 같은 게임 실행 안에서 판 단위로 번갈아 측정한다. FPS 명세 9절(조건 즉시 적용·선호도·우선순위 자동 기록)이 들어가면 조건 확인을 자료로 한다.
- 판정: 무거운 구간(간격 중앙값 10ms 이상)의 느린 1% 프레임·1% low·긴 간격/분을 비교한다. 차이가 사분위 범위 안이면 효과 없음으로 보고 해당 옵션은 기본에서 끈다.

## 10. Acceptance Criteria

1. 일반 사용자·일반 Discord 로그인 사용자에게 진입점이 없고, 설정을 직접 바꿔도 적용이 시작되지 않는다. 제작자는 명시적으로 시작할 수 있다.
2. 게임 미실행 상태에서 시작하면 게임 대기가 표시되며, 게임 프로세스가 생성된 뒤 CPU 배치를 적용하고 실제값을 확인한다.
3. 9800X3D 알파에서 최초 선택값은 7+1이며 자동 적용되지 않는다. 8코어 테스트 환경에서 6+2와 7+1 계획을 각각 만들 수 있다. 완전 분리 계획의 코어 수·SMT 형제 관계가 맞고 게임·백그라운드 집합이 겹치지 않는다.
4. 6+2와 7+1의 RSS 대상은 각 배분에서 다시 계산된다. 지원 장치에서 설정 확인 결과 게임용 코어와 겹치지 않으며, 표현할 수 없거나 검증 실패한 구성은 격리 성공으로 표시하지 않는다.
5. RSS 미지원이어도 CPU 기능은 독립적으로 사용할 수 있고, TCP·RSS 항목별 상태를 확인할 수 있다.
6. 프로세스가 종료되고 PID가 재사용되어도 이전 원복값을 새 프로세스에 쓰지 않는다. 보호·제외 대상은 변경하지 않는다.
7. 원래 제한된 CPU 설정과 TCP 값의 원래 부재를 포함해 적용 전 상태를 저장하고 복구할 수 있다. 재시도·배분 변경으로 원본이 덮이지 않는다.
8. 게임 종료 후 살아 있는 CPU 변경 대상은 복구된다. TCP·RSS 복구가 남으면 전체 복구 완료가 아니라 남은 항목과 이유를 표시한다.
9. 네트워크 중단 가능성을 알리기 전에 어댑터 재시작을 실행하지 않는다. 유선·Wi-Fi 전환 후 다른 장치에 원복값을 잘못 쓰지 않는다.
10. 앱 강제 종료 후 재실행하면 미복구 기록과 실제 상태를 확인할 수 있다. 기록 손상 시 추정값을 쓰거나 정상 복구로 보고하지 않는다.
11. 외부 도구가 설정을 변경하면 이를 무시하고 무한 재적용하지 않는다. 반복 시작·중단·재실행에서 중복 작업과 무제한 자원 증가가 없다.
12. 이 기능 실행으로 GPU·메모리 정리·오버클럭·전원·우선순위 설정이 변경되지 않는다(13.6절의 NVIDIA 최대 프레임 속도 400 상한만 예외). 전투 보조 일시정지는 최적화 원복을 실행하지 않는다.
13. 적용 성공을 FPS 향상·입력 지연 감소·최적값 판정으로 표시하지 않는다. 실게임 미검증 결과는 미검증으로 보고한다.
14. TCP 수신 창 자동 조정도 적용 전 값으로 복구된다. Normal 적용만 하고 원복 대상에서 빠뜨리지 않는다.
15. 게임 종료 후 CPU는 자동 복구되고 네트워크 복구는 확인을 기다린다. 다음 게임을 실행하거나 적용 중 배분을 바꿔도 새 세션이 자동 시작되지 않는다.
16. Process Lasso Governor 실행 중 CPU·RSS 적용은 보류된다. 다른 앱을 강제 종료하거나 라쏘 규칙을 바꾸지 않는다.
17. 9800X3D가 아닌 CPU에 7+1을 기본 적용하지 않는다. 예시 P8+E8은 게임 P4·백그라운드 P4+E8로 계획하며, SMT 형제와 RSS 대상은 실제 구조·배분에 따라 결정한다. 토폴로지를 확인할 수 없는 환경에 논리 번호 절반 분할을 임의 적용하지 않는다.
18. 백그라운드 대상 선택 목록을 작성하지 않아도 제외 목록 밖의 일반 프로그램이 자동 분류된다. 게임 중 새 대상에도 같은 기준이 적용되며 제외 대상·다른 사용자 세션은 변경되지 않는다.

## 11. 공개 코드 참고 시 경계

- 참고: [rubystarashe/nogirem](https://github.com/rubystarashe/nogirem)의 현재 소스. 커밋 이력이나 사용자 평가만으로 구현을 판단하지 않았다.
- `desktop/backend/src/affinity.rs`, `topology.rs`: CPU 구조·배분·원복 구현 사례.
- `desktop/backend/src/network.rs`, `powershell/network-query.ps1`, `powershell/network-autotuning.ps1`: TCP 변경·상태 확인 사례.
- `desktop/backend/src/nic.rs`, `powershell/nic.ps1`: RSS 설정·어댑터 재시작·복구 사례.
- 확인한 RSS 계획은 논리 CPU 앞쪽 절반 기준이다. 우리 앱의 가변 코어 배분과 일치한다고 가정하지 않고, 실제 배분 결과와 연동해야 한다.
- 공개 열람 가능과 재사용·재배포 허용은 별개다. 코드·실행 파일을 가져오기 전에 라이선스·의존성·배포 조건을 확인한다. 라이선스가 확인되지 않으면 복사 승인을 전제로 개발하지 않는다.
- 공개 소스는 구현 가능성의 참고다. 우리 앱 통합·권한·복구·환경 대응이 간단하거나 성능이 보장된다는 뜻은 아니다.
- 백그라운드 배치는 `config.json`의 이름·패턴 제외와 `affinity.rs`의 대상 판정을 참고한다. 일반 프로그램 자동 분류 원칙은 사용자가 승인했으며, 제외 목록 유지·변경 시 시스템·보안 프로세스 보호 기준을 보존한다. 입력 도구 전용 처리나 우선순위 변경 등 참고 앱의 추가 동작은 이번 범위에 자동 포함하지 않는다.

## 12. 개발 전달과 화면 검토

이 문서의 동작 기준으로 적용·검증·원복 기능의 개발과 독립 QA 기준 준비를 진행할 수 있다. 제품 코드 변경이나 성능 개선 검증이 완료된 상태는 아니다.

- 화면은 제작자 도구의 진입 위치, 항목 선택·코어 배분·복구 대기 표시, 권한 요청과 네트워크 중단 안내를 목업으로 보여주고 배치를 확인한다. 배치 미승인을 이유로 이미 확정한 동작을 임의 변경하지 않는다.
- 최소 지원 환경과 실패 처리, 실제 분리 가능한 장치·CPU는 기술 검토·테스트 결과로 명시한다. 미검증 하드웨어까지 지원 완료로 보고하지 않는다.
- [프레임 계측 0단계](game-optimization-alpha-stage0-spec.md)의 화면·조작 미결정 사항은 그 문서의 범위다. 최적화 적용 기능과 독립적으로 후속 목업에서 확인한다.

## 13. 기획 검수 후속 (2026-10-23 사용자 결정)

실제 화면 렌더와 코드 검토 결과를 바탕으로 사용자가 결정했다. 개발 전달용이며 구현 완료가 아니다.
`시안값`은 개발 렌더로 확인할 값이다.

### 13.1 선택값 저장과 환경 확인 자동화

- **현재 문제**: 환경 확인 결과와 선택값을 저장하지 않는다. 그래서 앱을 켤 때마다 `환경 확인` 클릭 → 어댑터 선택 → `최적화 시작`을 반복해야 한다.
  환경 확인은 읽기 전용이다(CPU 구조: Windows API, 어댑터: PowerShell 조회). `최적화 시작`은 이미 CPU 구조를 다시 읽어서 계획을 만든다.
  따라서 사용자가 화면을 채우려고 매번 직접 확인할 필요는 없다.
- **저장**: CPU 배치 체크, 물리 코어 배분, 네트워크 어댑터(안정 식별자), TCP·RSS 체크를 저장하고 다음 실행 때 복원한다.
  이는 선택값을 기억하는 것일 뿐이며, 자동 적용은 아니다. 2절 1항(앱 실행만으로 변경하지 않음)과 7절(다음 게임에 자동 재적용하지 않음)은 유지한다.
- **장치 고유 값**: 설정 내보내기·가져오기(다른 PC 이동)에는 포함하지 않는다. 시안이며 개발 시 확인한다.
- **환경 확인 자동 실행**: 최적화 탭을 처음 열 때 백그라운드에서 자동으로 실행한다. UI는 멈추지 않는다. 버튼은 `다시 확인`으로 남긴다.
  어댑터는 USB 랜이나 Wi-Fi 전환으로 바뀔 수 있으므로 저장된 목록을 쓰지 않고 매번 새로 읽는다.
- **저장값을 쓸 수 없을 때**
  - 저장한 배분을 현재 CPU에서 선택할 수 없으면 구조별 기본 배분을 표시하고 그 이유를 안내한다.
  - 저장한 어댑터가 없으면 선택을 비우고 안내한다. 네트워크 항목은 지금처럼 시작 전에 어댑터 선택을 요구한다.
- `최적화 시작` 시점에 CPU 구조를 다시 읽고 확인하는 기존 안전 동작은 유지한다.

### 13.2 상단 상태 표시 (제작자 전용)

- 상단 오른쪽 `● 전투 보조: 켜짐` 옆에 최적화 상태를 짧게 표시한다. 예: `최적화: 적용 중 7+1`, `게임 대기`, `원복 대기`, `오류`.
  아무 작업도 하지 않을 때는 숨긴다. 블랙박스 표시는 [블랙박스 명세 11절](game-blackbox-spec.md#11-기획-검수-후속-2026-10-23-사용자-결정)을 따른다.
- 이 기능에 실효가 있는지 판단하는 알파 단계이므로 **제작자에게만** 표시한다. 비제작자·로그아웃 상태에는 표시하지 않는다(2026-10-21 탭 노출 정정과 같은 기준).
- 상태를 보여줄 뿐 성능 개선을 뜻하지 않는다. 클릭하면 최적화 탭으로 이동한다(시안).

### 13.3 블랙박스와 함께 쓸 때 (실험 조건)

- 사용자 의도: 9800X3D(P/E 구분 없는 물리 8코어)에서 7코어를 게임에, 1코어를 나머지 전체에 주는 7+1이 실제로 효과가 있는지 실험한다.
  효과가 확인되면 6+2 정도로 타협해, 블랙박스 같은 보조 작업을 백그라운드 2코어에서 돌리는 방향을 검토한다.
- 현재 블랙박스 인코더(`ffmpeg.exe`, `blackbox_codec_host.exe`)는 일반 프로그램으로 분류되어 백그라운드 코어에 배치된다. 이는 위 의도와 맞는다.
  그러나 7+1에서는 Discord·브라우저와 함께 물리 1코어를 나눠 써야 하므로 녹화가 밀릴 수 있다.
  그래서 성능 비교를 할 때는 블랙박스를 켰는지 껐는지를 측정 조건으로 고정하고 기록한다.
- 결함 후보(Highly Likely, 코드 경로, 실게임 미검증): 블랙박스 인코더는 0.25초 구간마다 새로 실행된다. 최적화는 2초 주기 검사 때마다 이를 새 대상으로 적용·기록한다.
  이 기록이 관측 한도(4096)에 도달하면 장시간 사용 중 최적화 세션이 중단될 수 있다. 배분과 무관하게 개발 수정 대상이다.

### 13.4 FPS 수집의 실험 적합성 점검 (2026-10-23)

현재 소스에서 FPS·최적화 관련 테스트 106건이 통과했다. 실제 요약 코드에 합성 PresentMon 자료를 넣어 실험 흐름을 시뮬레이션했다.
A(끊김 많음) → B(끊김 감소) → C(100FPS 제한)를 각 90초씩 측정한 결과, 1% low는 약 30에서 70으로, 긴 간격은 60초당 40회에서 10회로 나타나
**끊김 차이는 구분된다.** 다만 실험에 쓰려면 아래 보완이 필요하다. 상세 요구는
[FPS 구간 요약 명세 7절](game-frame-recording-stage1-spec.md#7-최적화-실험-사용을-위한-보완-2026-10-23)에 둔다.

- 실게임 검증 전이다. FPS 오버레이 표시는 0.11.1 사용자 제보로 실제 동작이 확인됐지만, 구간 요약·수집 모드의 실제 Windows 검증은 남아 있다.
- `SMT 끄기` 옵션은 아직 없다. 외부 도구(작업 관리자·Process Lasso)로 SMT를 끈 채 우리 앱의 CPU 배치를 함께 켜면
  "다른 도구가 바꿨어요"로 관리 제외되므로, 외부 도구로 시험할 때는 앱의 CPU 배치를 끈다.

### 13.5 결과 표시 원칙 (2026-10-23 사용자 의견)

배경과 사용자 비유는 `TODO.md`의 해당 항목(알파 화면 통일 정리 아래)에 있다.
PT 상담에서 "뱃살만 빼는 운동은 없습니다"라고만 하면 등록하지 않듯이, 결과는 전체 과정으로 안내한다.

- **할 수 있는 말(사실)**: "최적화 완료 · 설정이 목표 상태로 맞춰졌어요". 선택한 항목이 이미 목표값이어서 바꾼 것이 없는 경우도 포함한다.
- **하지 않는 말(측정 근거 전)**: "성능이 좋아졌어요", "끊김이 줄었어요". 10절 13항(적용 성공을 FPS 향상·최적값으로 표시하지 않음)과 같은 선이다.
- **알파**: 항목별 상세(무엇이 적용·미적용·이미 목표값인지)를 지금처럼 보여준다.
- **버튼: 토글 하나 (2026-10-23 사용자 결정, 렌더 시안 2안)**. `최적화 시작`·`중단 · 원복` 두 버튼을 `FPS 표시`·`블랙박스 사용`과 같은
  토글 버튼(`LOCK_STYLE`, 글자 크기만큼 왼쪽 정렬) 하나로 바꾼다.
  - 꺼짐: `최적화 시작`. 누르면 지금의 시작 동작(네트워크 확인 1회 포함)을 실행한다.
  - 켜짐(민트): `최적화 적용 중`. **선택한 항목이 전부 이미 목표값이어서 바꾼 것이 없어도 똑같이 켜짐으로 보여준다.**
    설정이 목표 상태인 것은 사실이므로 결과 첫 줄도 `최적화 적용 완료`로 쓰고, 항목별 상세에서만 `이미 목표값 · 그대로 둠`으로 구분한다.
    게임 대기·CPU 적용 중·네트워크 원복 대기 같은 세부 상태는 버튼 아래 상태 줄과 상단 상태(13.2)에 쓴다.
  - 켜진 상태에서 누르면 지금의 `중단 · 원복`을 실행한다(네트워크 원복은 확인 1회, 거절하면 CPU만 원복하고 네트워크는 `원복 대기`로 켜짐 유지 — 0.11.4 결정 유지).
    되돌릴 변경이 없으면 바로 꺼지면서 `원래부터 같은 값이라 되돌릴 것이 없어요`라고 알려 원복 실패로 오해하지 않게 한다.
  - 게임이 끝나 CPU가 자동 원복돼도 네트워크 변경이 남아 있으면 켜짐을 유지한다. 남은 변경이 없으면 꺼진다.
  - **"적용 중"과 "원복 대기"를 구분한다 (2026-10-23 보정, 0.13.4 QA 지적)**. 네트워크를 실제로 바꾼 PC에서 적용 직후에도
    `네트워크 원복 대기`·상단 경고색이 떠서 정상 적용이 문제처럼 읽혔다. 앞선 13.5 문구가 두 상태를 묶은 것이 원인이다.
    | 상태 | 언제 | 버튼 | 상단(13.2) |
    |---|---|---|---|
    | 적용 중 (정상) | 네트워크를 바꿨고 아직 원복을 요청하지 않음. 네트워크만 한 세션 직후, 게임 종료로 CPU만 원복된 뒤 포함. 바꾼 것 없이 켜진 상태도 여기에 해당 | `최적화 적용 중` | `최적화: 적용 중`(기본색) |
    | 원복 대기 (확인 필요) | 원복을 요청했다가 네트워크 확인을 거절해 미룸, 원복 실패 후 재시도 필요, 지난 실행에서 되돌리지 못한 기록이 남아 재실행됨 | `최적화 적용 중 · 네트워크 원복 대기` | `최적화: 원복 대기`(경고색) |
    적용 중 상태의 상태 줄에는 `네트워크 설정 적용 중 · 끄면 원래 값으로 되돌려요`처럼 다음 동작을 안내한다. 바꾼 것 없이 켜진 상태도
    상단에 `최적화: 적용 중`을 보여 탭과 상단이 다르지 않게 한다.
  - 앱 재실행 후 미복구 기록이 있으면 켜짐(원복 대기)으로 시작한다. 기존 복구 기록·손상 차단 규칙(6·7절)은 그대로다.
    바꾼 것 없이 켜졌던 상태는 되돌릴 기록이 없으므로 재실행하면 꺼짐으로 시작한다.
- **항목별 문구(알파 포함)**: 현재 값이 이미 목표값이라 다시 쓰지 않은 항목은 `기존 값 일치·변경 없음`처럼 실패로 읽히는 문구 대신
  `이미 목표값 · 그대로 둠`처럼 성공으로 읽히게 쓴다(2026-10-23 사용자 결정). 동작은 바꾸지 않는다(5절: 같은 값이면 다시 쓰지 않고 원복 대상도 없다).
  자주 생기는 경우: TCP 자동 조정 Normal은 Windows 기본값이고, 패스트핑은 이전에 직접 설정했거나 다른 도구가 이미 바꿔 둔 PC에서 처음부터 목표값이다.
- **공개 전환 때**: 결과 한 줄 요약을 먼저 보여주고 항목별 상세는 접어 둔다. 정확한 문구는 공개 기획 때 정한다.

### 13.6 그래픽 효율 최적화: 최대 프레임 400 상한 (2026-10-23 사용자 결정)

- **배경**: 실측(리서치 7.1)에서 FPS 제한은 무거운 장면의 끊김을 바꾸지 못했고, 로딩·캐릭터 선택 화면이 제한 없이 2000FPS 이상 헛도는 것은 확인됐다.
  커뮤니티에서 말하던 "프레임이 2천까지 올라 그래픽카드 발열이 심하다"가 실제로 나타난 것이다.
- **이름과 문구**: "그래픽 효율 최적화". "그래픽을 낭비 없이 효율적으로 돌려요", "보이지 않는 프레임에 쓰던 전력·발열을 줄여요"처럼 쓴다.
  "끊김 개선", "FPS 향상", "렉 감소"는 쓰지 않는다(측정으로 효과가 없음을 확인함, 13.5절 원칙).
- **값**: 일괄 **400 상한**. 렘부스터와 같은 값이다. 실제 플레이 장면은 거의 400에 닿지 않아 체감 변화가 없고, 2000FPS 헛돌기만 막는다.
  360Hz 모니터나 일부러 높은 프레임으로 입력 지연을 줄이는 사용자에게도 손해가 없어, 주사율 감지나 G-Sync 보정 같은 판단이 필요 없다.
- **적용 방식**: 최적화 토글(13.5)에 포함해, 시작할 때 NVIDIA 드라이버의 마비노기 프로필(`mabinogi.exe` 등 게임 실행 파일 프로필)의
  최대 프레임 속도를 400으로 쓴다. 사용자가 켜고 끌 수 있는 항목으로 두며, 다른 항목처럼 원래 값을 먼저 저장하고 끌 때 되돌린다(6절 원칙).
- **사용자 값 존중**:
  - 이미 400 이하로 제한해 둔 경우(예: 노트북 60 제한)는 건드리지 않는다. 더 높은 상한으로 덮어쓰면 오히려 제한이 풀린다. 이 경우 `이미 목표 이하 · 그대로 둠`(13.5 문구 원칙).
  - 수직 동기화는 바꾸지 않는다(렘부스터는 끄지만 화면 찢어짐 취향의 문제라 사용자 설정을 존중).
  - 적용 후 사용자가 제어판에서 직접 바꾼 값은 원복 때 덮어쓰지 않고 외부 변경으로 안내한다(6절과 같은 기준).
- **지원 범위**: 우선 NVIDIA만. NVIDIA 공식 드라이버 설정 API(NVAPI DRS)로 프로필을 읽고 쓴다. 드라이버 설정 반영 시점(게임 재시작 필요 여부)은
  실측 확인 대상이다(1차 실험은 게임을 다시 켠 뒤 적용된 상태로 측정됐고, 재시작 없이 바로 적용되는지는 확인하지 않았다). AMD·인텔은 방식이 달라 기술 검토 후 결정한다. 미지원 그래픽카드는 항목을 비활성화하고 이유를 안내한다.
- **적용 확인**: 쓴 값을 다시 읽어 확인한다. 게임 실행 중이면 FPS 측정 자료에서 프레임 간격이 2.5ms(400FPS) 아래로 내려가지 않는지로 실제 적용도 확인할 수 있다.
- **후속 선택지(기록만)**: 더 아끼고 싶은 사용자를 위한 "모니터 주사율 맞춤" 상한. 앱이 게임 창이 있는 모니터의 주사율을 Windows에서 읽어 추천값을 정할 수 있다(G-Sync는 주사율보다 약간 낮게).
- 렌더 시안: 최적화 화면에 항목이 추가되므로 개발 전에 렌더로 배치를 확인한다.

### 13.7 게임 우선순위 높음 (2026-10-24 사용자 결정, 확정)

- **근거**: 사용자가 렉 많은 무거운 던전에서 우선순위 높음의 효과를 확실히 체감했다. 원리도 맞는다. 무거운 장면에서 메인 스레드가 한계 가까이 일할 때
  다른 프로그램이 끼어들면 프레임이 밀리는데, 높음이면 Windows가 게임 스레드를 먼저 실행한다. 가벼운 장면은 원래 여유가 있어 차이가 작다.
  측정 확인은 9.2절 실험의 기준 조건으로 함께 남는다(별도 판정 실험은 하지 않음).
- **동작**: 최적화 토글(13.5)의 항목 `게임 우선순위 높음`(기본 켬). 게임 프로세스를 식별하면 우선순위를 "높음"으로 바꾸고, 바꾸기 전 값을 기록한다.
  토글을 끄거나 세션이 끝날 때 게임이 살아 있으면 원래 값으로 되돌린다. 게임을 끄면 값도 함께 사라지므로 되돌릴 것이 없다.
  게임을 다시 켰을 때 자동 재적용 여부는 CPU 배치와 같은 규칙(7절, 자동 적용은 후속 기획)을 따른다.
- **하지 않는 것**: "실시간"은 절대 쓰지 않는다(시스템 전체가 멈출 수 있음). 다른 프로그램의 우선순위는 낮추지 않는다(라쏘 ProBalance 방식은 이번 범위 아님).
  게임 프로세스의 우선순위를 사용자가 다른 도구로 바꾸면 덮어쓰지 않고 외부 변경으로 안내한다(6절과 같은 기준).
- **이미 높음인 경우**: 라쏘 등으로 이미 높음이면 `이미 목표값 · 그대로 둠`(13.5 문구 원칙).
- **부작용 확인**: 알파에서 Discord 음성 끊김, 앱 오버레이·탐지 지연, 블랙박스 녹화 밀림이 없는지 본다. FPS 명세 9절의 자동 기록에 게임 우선순위가 남는다.
- **유지 확인 필요(2026-10-24)**: 작업 관리자에서 "높음"으로 바꾼 측정에서 앱 기록은 매초 "보통"이었다(리서치 7.7). 변경이 적용되지 않았는지, 게임 등이 되돌리는지 확인한다.
  되돌아간다면 한 번 거는 것으로는 부족하므로, 세션 동안 주기적으로 확인해 다시 거는 방식(라쏘의 "항상" 규칙과 같은 효과)이 필요하다. 이 경우에도 외부 도구와 무한히 다투지 않도록 다시 거는 횟수와 간격을 제한한다.
- **우선순위 읽기 불일치(2026-10-24, 개발 조사 대상)**: 사용자는 게임을 새로 켜고 측정 전에 작업 관리자에서 "높음(H)"을 걸었고, 측정 뒤에도 작업 관리자는 같은 PID를 "높음"으로 보여 줬다.
  그런데 앱의 FPS 자동 기록(`perf_metrics.process_state`, `GetPriorityClass`)은 64분 동안 매초 "보통"이었다. 같은 경로로 읽은 선호도(SMT 켬/끔 전환)는 정확했다.
  13.7 구현 때 앱이 건 값을 다시 읽어 확인하므로, 이 불일치를 먼저 재현·원인 확인해야 한다(실제 Windows에서 작업 관리자 "기본 우선 순위" 열과 앱 기록을 같은 순간에 비교).
  원인이 확인되기 전에는 우선순위 적용 확인 실패를 "적용 실패"로 단정하지 않고 확인 불가로 표시한다.
- **보안 모듈**: 작업 관리자·라쏘로 `Client.exe` 우선순위를 바꾸는 것은 커뮤니티에서 흔하고 제재 보고는 없다. 안전이 확인된 것은 아니다(리서치 2절).
- **구현(0.17.0)**: `CPU 배치` 묶음의 체크박스 `게임 우선순위 높음`(기본 켬, 선택 기억). 유지 확인 2초마다, 원본 복귀 시 10분에 30회까지 다시 걸기
  (2026-10-24 실측: 게임이 재접속·맵 이동 때 '보통'으로 되돌림 — 유지 확인 필요 항목 Confirmed).
- **미리 높음인 경우(0.17.0 QA 보완)**: 시작 때 이미 높음이면 손대지 않고 지켜본다. 게임이 '보통'으로 되돌리면 그 '보통'을 원본으로 기록하고 높음을 건다
  (이후 유지·원복은 위와 같음, 세션이 끝나면 '보통'으로 원복). '보통'이 아닌 다른 값(보통 초과 등)으로 바뀌면 다른 도구의 변경으로 보고 손대지 않는다.
- **게임 창이 뒤에 있을 때(2026-10-24 사용자 결정)**: 게임에 집중할 때만 높음이면 된다. 뒤에 있는 동안 게임이 스스로 '보통'으로 낮추면 그대로 두고, 앞으로 왔는데도 '보통'이면 다시 건다.
  읽기는 `GetPriorityClass`와 프로세스 목록 기본 우선순위를 교차 확인(`system/process_priority`), 다르면 확인 불가. 진단 `scripts/diag_game_priority.py`.

### 13.8 RSS 제외 (2026-10-24 사용자 결정)

- RSS 수신 처리 배치는 최적화 항목에서 뺀다. 화면에서 RSS 체크를 없애고 새로 적용하지 않는다.
- 근거: 게임 패킷은 초당 수십~수백 개라 효과가 매우 낮다고 본다(리서치 1절). 적용·원복 때마다 어댑터 재시작으로 인터넷이 잠깐 끊기고,
  실사용에서 장치가 값을 바꿔 적용 확인 실패가 반복됐다(status 0.11.x 기록).
- 남은 원복: 예전에 적용한 RSS 기록(`recovery.json`)이 남은 사용자는 기존 원복 경로로 되돌릴 수 있어야 한다. 원복 기능은 기록이 모두 정리될 때까지 유지하고,
  새 적용만 막는다. 기록이 없으면 RSS 관련 표시는 보이지 않는다.
- 4절의 RSS 계획·확인 규칙과 10절 4·5항은 원복 처리에만 적용한다.
- **구현(0.17.0)**: RSS 체크 제거, 엔진은 RSS 계획·적용을 하지 않는다(요청이 와도 무시). 기존 기록 원복·재연결 확인 경로는 그대로.

### 13.9 TCPNoDelay 제외 (2026-10-24 사용자 결정)

- 패스트핑에서 TCPNoDelay를 빼고 TcpAckFrequency만 남긴다. 화면 문구 `패스트핑 · TCP 자동 조정 Normal`의 패스트핑은 TcpAckFrequency를 뜻한다.
- 근거(리서치 8절): 마비노기 커뮤니티의 TCPNoDelay는 원래 MSMQ 키 값이라 게임과 무관하고, 어댑터 키에 넣은 값이 게임에 반영된다는 근거가 없다.
  네이글은 보내는 쪽 기능이라 확실히 끄려면 게임이 소켓마다 설정해야 한다. 효과 근거가 없는 항목을 "적용됨"으로 보이지 않게 한다.
- 남은 원복: 예전에 TCPNoDelay를 적용한 기록이 있으면 기존 원복 경로로 되돌릴 수 있어야 한다(원래 값이 없었다면 값을 지움, 5절). 새 적용만 막는다.
  TcpAckFrequency와 같은 어댑터 재시작에 묶여 있으므로 원복 때 끊김이 따로 늘지는 않는다.
- **구현(0.17.0)**: 패스트핑 적용은 `ack`·`autotuning`만. 기존 `nodelay` 기록은 원복 경로로 되돌린다.


### 13.10 자동 적용 (2026-10-25 기획 요청, 초안 · 결정 대기)

근거: 사용자 질문(라쏘 "항상" 규칙처럼), 2절 1항·7절·9.1(자동 적용은 효과 확인 뒤 기획)·13.7. 그 뒤 우선순위 높음은 확정(13.7)됐고 SMT 끔은 이득이 없었다(리서치 7.7).
현재: CPU 배치·우선순위는 게임 종료·앱 종료 때 원복하고 세션을 끝낸다(게임마다 `최적화 시작`). 패스트핑은 레지스트리라 원복 전까지 유지된다.
렌더 시안(적용·복구 묶음의 자동 적용 체크, 상단 표시 A/B)을 제시했다.

| 항목 | 기획 권장안 |
|---|---|
| 1. 켜는 방식 | 토글 아래 체크 `마비노기를 켜면 자동 적용`. **기본 꺼짐**(스스로 시스템 설정을 바꾸는 기능이라 사용자가 고른다), 체크 상태는 저장. 켜 두면 게임을 끄면 그 게임에 건 값만 정리하고 토글은 켜진 채 다음 게임을 기다린다 |
| 2. 대상 | 위에서 **체크한 프로세스 항목**(게임 우선순위·CPU 배치)을 그대로 쓴다. 실험 중이면 CPU 배치 체크만 끄면 된다. **네트워크(패스트핑)는 자동으로 바꾸지 않는다** — 어댑터 재시작으로 끊기고, 레지스트리라 한 번 걸면 유지된다 |
| 3. 앱 시작 | 자동 적용이 켜져 있으면 앱이 뜨자마자 게임 대기(라쏘와 같은 체감). 2절 1항을 "사용자가 자동 적용을 켠 경우 앱 시작 시 게임을 기다리고, 게임이 켜졌을 때만 프로세스 항목을 적용한다"로 갱신. 게임이 없으면 아무것도 바꾸지 않는다 |
| 4. 상단 표시 | A: 대기 중에도 회색 `최적화: 게임 대기` / **B(권장): 대기 중에는 숨기고 적용될 때만 `최적화: 적용 중 …`**. 첫 적용 알림 창·토스트는 띄우지 않는다(상단 표시로 충분) |
| 5. 안전장치 | 그대로 유지: 라쏘 관리자 실행 중이면 보류(상단 `최적화: 보류`), 외부 변경 존중·다시 걸기 한도는 게임 실행마다 새로 계산, 게임별 복구 기록. 앱이 비정상 종료된 뒤 다시 뜰 때 게임이 아직 켜져 있으면, 자동 적용이 켜진 경우 원복 대신 그 게임을 다시 관리한다 |
| 6. FPS 수집 | 측정 메모는 사용자가 쓴 그대로 둔다. 자동 기록(FPS 9절)에 `최적화 자동 적용: 켬/끔`을 추가한다. 우선순위·선호도는 이미 자동 기록되므로 실험이 섞였는지 자료로 확인할 수 있다 |
